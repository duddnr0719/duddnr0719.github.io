> 4장(네트워크 계층: 데이터 평면)의 2부에서는 호스트와 라우터의 각 인터페이스를 식별하는 32비트 IPv4 주소체계와 서브넷 · CIDR(Classless InterDomain Routing) 구조를 다룬다. 이어서 호스트가 정적 설정이나 DHCP(Dynamic Host Configuration Protocol)로 IP 주소를 동적으로 획득하는 절차와, 네트워크가 ISP와 ICANN을 통해 계층적으로 주소 블록을 배정받는 방식을 정리한다. 마지막으로 사설 IP 공간과 변환 테이블을 활용해 IPv4 주소 고갈 문제를 완화하는 NAT(Network Address Translation)의 동작 원리와 쟁점을 다룬다.

### 4장 전체 목차와 다루는 범위
- **4장 전체 구성(`4장. 네트워크 계층: 데이터 평면`)**
  - **4.1 네트워크 계층 개요** = 데이터 평면 · 제어 평면
  - **4.2 라우터 내부에는 무엇이 있을까?**
  - **4.3 인터넷 프로토콜(IP)** = 데이터그램 형식 · 단편화 · IPv4 주소체계 · 네트워크 주소 변환 · IPv6
  - **4.4 일반적인 포워딩 및 소프트웨어 기반 네트워크(SDN)** = 매치 · 액션 · match-plus-action 작업의 OpenFlow 예
- **이번 범위(`2/3`)의 초점** = 호스트 · 라우터의 네트워크 계층 기능 및 **IPv4 데이터그램 포맷** 도입에 이어 **4.3절**의 **IPv4 주소체계**(IP 주소 · 서브넷 · CIDR · DHCP · 계층적 주소 · ICANN)와 **네트워크 주소 변환(NAT)**을 다룸

### IP 주소와 인터페이스
- **IP 주소(IP address)** = 호스트 또는 라우터의 인터페이스를 구별하기 위해 부여하는 **32비트 식별자**(IPv4 주소)
- **인터페이스(interface)** = 호스트나 라우터가 물리 링크와 맞닿아 연결되는 지점
  - **라우터**는 여러 개의 인터페이스를 보유하고, **호스트**는 일반적으로 1개 또는 2개의 인터페이스(예: 유선 이더넷 · WiFi)를 가짐
  - IP 주소는 호스트 · 라우터의 **각 인터페이스**에 연관되어 부여됨
  - 인터페이스가 어떻게 연결되는지는 6장과 7장에서 이어서 다룸

### 서브넷과 CIDR
- **서브넷(Subnet)** = 중간 라우터의 중계 없이 물리적으로 서로 도달할 수 있는 디바이스 인터페이스들의 영역
- **IP 주소의 비트 구성**
  - **서브넷 부분(상위 비트)** = 동일 서브넷에 속한 디바이스들이 공통으로 사용하는 주소 영역
  - **호스트 부분(하위 비트)** = 같은 서브넷 내부의 개별 인터페이스를 구분하는 영역
- **서브넷 판별(구성) 절차**
  - 호스트 · 라우터에서 각 인터페이스를 분리 → 각각의 고립된 네트워크 생성
  - 각 인터페이스의 끝이 고립 네트워크의 종단점 역할을 함 → 분리된 고립 네트워크 하나하나가 **서브넷**에 해당함
- **서브넷 마스크(subnet mask)** = `/24`처럼 슬래시 뒤에 비트 수를 적어 상위 24비트가 서브넷 주소임을 표기함
- **CIDR(Classless InterDomain Routing)** = 서브넷 부분이 임의의 길이를 가질 수 있는 주소 체계
  - 표기 형식은 `a.b.c.d/x`이며, `x`는 전체 주소에서 서브넷 부분이 차지하는 비트 수를 뜻함

### IP 주소 획득: 정적 설정과 DHCP
- **주소 획득의 두 가지 관점**
  - **호스트 부분 주소** = 개별 호스트가 소속 네트워크 안에서 자신의 주소를 얻는 방법
  - **서브넷 부분 주소** = 네트워크 자체가 사용할 IP 주소를 얻는 방법
- **호스트 주소 획득 1: 정적 설정** = 시스템 관리자가 OS별 설정 파일에 주소를 직접 기록함
  - **Windows** = `control-panel->network->configuration->tcp/ip->properties`
  - **UNIX** = `/etc/rc.config`
  - **Ubuntu Linux** = `/etc/network/interfaces`
- **호스트 주소 획득 2: DHCP(Dynamic Host Configuration Protocol)** = 서버로부터 주소를 동적으로 배정받는 **플러그 앤 플레이(plug-and-play)** 프로토콜
  - **도입 목적**
    - 네트워크 접속 시점에 서버로부터 IP 주소를 동적으로 할당받음
    - 네트워크에 연결된 동안만 주소를 유지 → **주소 재사용** 가능
    - 짧은 시간만 연결하는 **모바일 사용자** 지원
- **DHCP 메시지 교환 순서**
  1. **DHCP discover** = 호스트가 서버 발견 메시지를 네트워크에 브로드캐스트(방송)함
  2. **DHCP offer** = 응답 가능한 DHCP 서버가 제공 메시지로 회신함
  3. **DHCP request** = 호스트가 요청 메시지로 IP 주소 할당을 요청함
  4. **DHCP ack** = DHCP 서버가 `DHCP ACK` 메시지로 IP 주소를 전송함
- **DHCP가 함께 전달하는 부가 정보** = 할당된 서브넷 IP 주소 외에 세 가지 정보를 같이 내려줌
  - **첫 번째 홉 라우터의 주소**
  - **DNS 서버의 이름과 IP 주소**
  - **네트워크 마스크** (주소에서 네트워크 부분과 호스트 부분을 구분)
- **랩탑 인터넷 연결을 통한 DHCP 캡슐화 · 전달 흐름**
  - 인터넷 접속에 필요한 IP 주소 · 첫 홉 라우터 주소 · DNS 서버 주소를 얻기 위해 DHCP를 사용함
  - **요청 전송(클라이언트 → DHCP 서버)**
    - DHCP 요청 메시지 생성 → `UDP/IP/802.1 이더넷` 패킷으로 캡슐화
    - 목적지 `FFFFFFFF`의 이더넷 프레임으로 LAN에 브로드캐스트 → DHCP 서버 측 라우터가 수신
    - 수신 측에서 `이더넷/IP/UDP` 계층 캡슐을 해제 → DHCP 서버로 메시지 전달
  - **응답 수신(DHCP 서버 → 클라이언트)**
    - DHCP 서버가 클라이언트 IP 주소 · 첫 홉 라우터 주소 · DNS 서버 이름과 IP 주소를 담은 **DHCP ACK** 작성
    - ACK 메시지를 패킷으로 캡슐화해 클라이언트에게 송신 → 클라이언트 수신 후 IP 주소 · 첫 홉 라우터 주소 · DNS 서버 이름과 IP 주소 확보

### 계층적 주소 할당과 ICANN
- **네트워크(서브넷 부분)의 IP 주소 획득** = 연결을 제공하는 **ISP** 주소 공간 중 할당된 영역에서 얻음
- **계층적 주소와 라우팅 광고**
  - **라우트 집합(Route Aggregation)** = 계층 구조의 주소를 활용해 라우팅 정보를 효과적으로 광고함
  - **특정 라우트(Specific Aggregation)** = 조직 1이 ISP를 변경하는 상황의 처리 방식
    - 조직 1의 기존 호스트 주소를 바꾸는 대신, 새 ISP가 조직 1의 특정 주소도 함께 광고함
    - 라우터는 **최장 프리픽스 대응법**으로 동작 → 목적지 주소와 더 길게 일치하는 쪽으로 라우팅함
- **ICANN(Internet Corporation for Assigned Names and Numbers)**
  - **IP 주소 배분** = ISP가 주소 블록을 할당받는 기구로, **5개의 지역 등록소(RR)**를 통해 IP 주소를 배분함
  - **DNS 관리** = DNS 루트 영역을 관리하며 `.com` · `.edu` 등 각 TLD 관리 대행을 수행함
- **32비트 IPv4 주소 고갈과 대응**
  - **고갈 시점** = ICANN이 **2011년** 마지막 남은 IPv4 주소를 지역 등록소(RR)에 모두 할당함
  - **대응 수단** = **NAT**가 주소 부족 문제 해결에 도움을 주며, **IPv6**가 **128비트** 주소 공간을 제공함

### 네트워크 주소 변환(NAT)
- **NAT(Network Address Translation)와 사설 IP 주소**
  - 로컬 네트워크 내부 디바이스들은 로컬 전용 **사설(private) IP 주소 공간**(`10/8` · `172.16/12` · `192.168/16` 프리픽스)을 가짐
- **NAT의 4가지 이점**
  - **비용 절감** = 모든 내부 디바이스가 하나의 IP 주소만 사용하므로 ISP로부터 여러 주소를 할당받을 필요가 없음 (ISP 제공 고정 IP 1건 추가 시 평균 5만원 비용 발생)
  - **내부 주소 변경 용이성** = 외부 세계에 알리지 않고도 로컬 네트워크 내 호스트 주소를 바꿀 수 있음
  - **ISP 전환 유연성** = 지역 네트워크 디바이스 주소를 변경하지 않은 채 ISP만 바꿀 수 있음
  - **보안 효과** = 내부 디바이스들이 외부에서 명시적으로 주소 지정되거나 노출되지 않음
- **NAT 라우터 동작과 변환 테이블**
  - **외부로 나가는 데이터그램(outgoing datagrams)**
    - `(출발지 IP 주소, 포트번호)` → `(NAT IP 주소, 새로운 포트번호)`로 치환해 송신
    - 외부의 원격 클라이언트 · 서버는 응답 목적지로 `(NAT IP 주소, 새로운 포트번호)`를 사용함
  - **NAT 변환 테이블(NAT translation table)**
    - 변환 전후 쌍인 `(출발지 IP 주소, 포트번호)`와 `(NAT IP 주소, 새로운 포트번호)`를 테이블에 저장함
  - **들어오는 데이터그램(incoming datagrams)**
    - 수신한 `(NAT IP 주소, 새로운 포트번호)`를 NAT 변환 테이블에서 조회 → 원래 내부의 `(출발지 IP 주소, 포트번호)`로 복원함
- **NAT에 대한 논란과 사용 현황**
  - **논란의 근거**
    - 포트번호는 호스트 주소 지정이 아닌 **프로세스 주소 지정**에 쓰여야 함
    - 라우터는 **계층 3**까지만 처리해야 함
    - 호스트가 IP 주소와 포트번호를 수정하지 않고 직접 통신해야 한다는 **종단 간의 논의**에 위반됨
    - 주소 부족 문제는 **IPv6**로 풀어야 한다는 주장
  - **현재 활용** = 이 같은 논란에도 가정 · 기관 · 4G/5G 네트워크 등에서 여전히 광범위하게 쓰임
