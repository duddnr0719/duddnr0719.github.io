> 프로세스 = 실행 중인 프로그램. OS는 PCB로 상태를 저장해 컨텍스트 스위치를 하고, 큐와 스케줄러로 누가 CPU를 쓸지 정한다. UNIX는 fork + exec으로 프로세스를 만들고, 협력 프로세스는 공유 메모리나 메시지 패싱으로 통신한다.
### 프로세스
- 프로세스 = **실행 중인 프로그램**. 프로그램은 디스크의 수동적 파일, 프로세스는 메모리에 올라와 '살아 있는' 능동적 실체
  - 배치 시스템에선 작업(job), 시분할 시스템에선 프로세스 (같은 의미)
  - 같은 프로그램으로 여러 프로세스 가능: 크롬 창 3개 = 각자 메모리·PID가 다른 프로세스 3개
- 메모리 구조 (높은 주소 max → 낮은 주소 0)
  - **stack**: 함수 매개변수, 반환 주소, 지역 변수. 아래로 자람
  - (빈 공간)
  - **heap**: 실행 중 동적 할당 (`malloc`). 위로 자람
  - **data**: 전역 변수
  - **text**: 프로그램 코드
  - + 프로그램 카운터, CPU 레지스터 (현재 실행 위치와 상태)
### 프로세스 상태
- new: 생성 중
- ready: 실행 준비 완료, CPU만 기다림 (CPU가 바쁜 것)
- running: CPU에서 실행 중 (싱글 코어면 한 순간에 하나)
- waiting: I/O나 이벤트 대기 (디스크 읽기, 사용자 입력)
- terminated: 실행 종료
- 전이
  - new → (admitted) → ready → (scheduler dispatch) → running → (exit) → terminated
  - running → (interrupt, 타임 슬라이스 만료) → ready
  - running → (I/O·이벤트 대기) → waiting → (완료) → ready
### PCB (Process Control Block)
- OS가 프로세스마다 저장하는 관리 정보 (TCB라고도 함)
  - 프로세스 상태, PID
  - 프로그램 카운터: 다음에 실행할 명령어 주소 → "여기서부터 다시"
  - CPU 레지스터 값
  - 스케줄링 정보: 우선순위, 큐 포인터
  - 메모리 관리 정보: 할당된 메모리 영역
  - 회계 정보: CPU 사용 시간, 시간 한도
  - I/O 상태: 할당된 장치, 열린 파일 목록
- 비유: 게임 세이브 파일. 밥 먹으러 갈 때 저장하고, 와서 이어서 함 (슬롯은 프로세스마다 1개)
- Linux는 C 구조체 `task_struct`로 표현하고 연결 리스트로 관리. 현재 실행 중인 프로세스는 `current` 포인터
```c
struct task_struct {
    pid_t pid;                   /* 프로세스 ID */
    long state;                  /* 상태 */
    unsigned int time_slice;     /* 스케줄링 정보 */
    struct task_struct *parent;  /* 부모 */
    struct list_head children;   /* 자식들 */
    struct files_struct *files;  /* 열린 파일 목록 */
    struct mm_struct *mm;        /* 주소 공간 */
    /* ... */
};
```
### 컨텍스트 스위치
- P0 실행 중 인터럽트·시스템 호출 → P0 상태를 PCB0에 저장 → PCB1에서 P1 상태 복원 → P1 실행 → (반대로 반복)
- 컨텍스트 = 프로세스가 CPU를 쓰는 데 필요한 모든 정보
- 스위칭 중엔 어느 프로세스도 일을 못 함 → 순수 **오버헤드**. 보통 수 μs라 사람은 못 느낌
- OS와 PCB가 복잡할수록 오래 걸림. 레지스터 세트를 여러 개 가진 CPU는 포인터만 바꿔 빠르게 전환
### 스레드 미리보기
- 지금까지의 프로세스 = 실행 흐름 1개(단일 스레드)
- 멀티스레드: 한 프로세스 안에 여러 실행 흐름
  - 스레드마다 독립: 스택, PC, 레지스터
  - 공유: 코드, 데이터, 힙
### 프로세스 스케줄링
- 목표: CPU 이용률 최대화, 공정성, 응답 시간 최소화
- 큐
  - 작업 큐: 시스템의 모든 프로세스
  - 준비 큐: 메모리에 있고 CPU만 기다리는 프로세스
  - 장치 큐: 특정 I/O 장치를 기다리는 프로세스 (디스크, 네트워크, 터미널 …)
  - 각 큐는 head/tail 포인터로 PCB들을 연결 리스트로 관리
- 대기 다이어그램: 준비 큐에서 CPU를 받아 실행하다가
  - I/O 요청 → I/O 큐 → 완료 후 준비 큐
  - 타임 슬라이스 만료 → 준비 큐
  - 자식 생성(fork) → 자식 실행 → 준비 큐
  - 인터럽트 대기 → 발생 → 준비 큐
### 스케줄러
| 스케줄러 | 역할 | 호출 빈도 |
|---|---|---|
| 단기 (CPU 스케줄러) | 준비 큐에서 다음에 CPU를 줄 프로세스 선택 | 밀리초 단위 → 빨라야 함 |
| 장기 (작업 스케줄러) | 디스크의 작업 중 메모리에 올릴 것 선택 → **다중 프로그래밍 정도** 제어 | 초·분 단위 |
| 중기 | 메모리가 부족하면 일부를 디스크로 내렸다가(swap out) 다시 올림(swap in) | 필요 시 |
- I/O 바운드(웹 서버, 에디터: 짧은 CPU 버스트 + 잦은 I/O) vs CPU 바운드(비디오 인코딩, 수치 계산: 긴 CPU 버스트)
  - 장기 스케줄러는 둘을 잘 섞어(good process mix) CPU와 I/O 장치가 모두 바쁘게
- 스와핑 대상: I/O 대기 중, 우선순위 낮음, 오래 잠든 프로세스. running 프로세스와 커널 프로세스는 건드리지 않음
### 모바일 멀티태스킹
- 초기 iOS: 포그라운드 앱 하나만 실행, 나머지는 중단 (작은 화면, 배터리, 메모리). 백그라운드는 음악·위치·알림 등 제한적으로만
- Android: 포그라운드 + 여러 백그라운드 가능. 백그라운드 작업은 UI 없는 **서비스**로 (앱을 나가도 음악이 계속 나오는 이유)
### 프로세스 생성
- 부모가 자식을 만들고, 자식이 또 자식을 만들어 **프로세스 트리**. 각자 고유 **PID**
  - Linux: init(1) → kthreadd(2), sshd, login → bash → emacs, ps …
- 자원 공유: 전부 공유 / 일부만 공유 / 공유 안 함(보통)
- 실행: 부모와 자식이 동시에 실행 / 부모가 자식 종료까지 대기
- UNIX: **`fork()`** 로 부모 주소 공간을 통째로 복사한 자식 생성 → 자식이 **`exec()`** 으로 새 프로그램을 덮어씀
- `fork()` 반환값으로 구분: 부모는 **자식 PID(양수)**, 자식은 **0**, 실패는 **−1**
```c
#include <sys/types.h>
#include <sys/wait.h>
#include <stdio.h>
#include <unistd.h>

int main() {
    pid_t pid = fork();              /* 자식 생성 */
    if (pid < 0) {                   /* 오류 */
        fprintf(stderr, "Fork Failed");
        return 1;
    } else if (pid == 0) {           /* 자식 */
        execlp("/bin/ls", "ls", NULL);
    } else {                         /* 부모 */
        wait(NULL);                  /* 자식 종료 대기 */
        printf("Child Complete\n");
    }
    return 0;
}
```
- 실행: `gcc fork.c -o fork && ./fork` → 현재 디렉터리 목록 출력 후 "Child Complete"
- Windows는 fork + exec 대신 `CreateProcess()` 하나로 (인자 10개). 부모는 `WaitForSingleObject(pi.hProcess, INFINITE)`로 대기 후 `CloseHandle`
### 프로세스 종료
- 정상: 마지막 문장 후 `exit()` 로 상태 코드 전달 (0 = 성공, 그 외 = 오류)
- 비정상: `abort()`, `kill()`. 부모는 자원 초과나 더 이상 필요 없을 때 자식을 강제 종료할 수 있음
- 부모는 `pid = wait(&status)`로 자식 종료를 기다리고 PID와 상태를 받음
- **좀비**: 자식은 끝났는데 부모가 아직 `wait()`로 회수하지 않아 PCB(프로세스 테이블 항목)가 남은 상태. 자원은 회수됐지만 목록에 남음
- **고아**: 부모가 먼저 종료된 자식. Linux는 init(PID 1)이 새 부모가 되어 회수, Windows는 관계가 끊겨 독립 실행
- **계단식 종료**: 부모가 끝나면 자식도 전부 종료시키는 방식
### 크롬의 멀티프로세스 구조
- 예전 브라우저: 한 프로세스가 모든 탭 처리 → 탭 하나 크래시면 전부 다운
- 크롬
  - 브라우저 프로세스: UI(주소창, 버튼), 파일, 네트워크
  - 렌더러 프로세스: 탭마다 따로 HTML·CSS·JS 렌더링, **샌드박스**에서 제한된 권한으로 실행
  - 플러그인 프로세스: 플러그인 종류별로 따로
### 프로세스 간 통신 (IPC)
- 독립 프로세스(서로 영향 없음) vs 협력 프로세스(데이터를 주고받으며 영향)
- 협력하는 이유: 정보 공유, 계산 속도 향상(병렬), 모듈성, 편의성
| 모델 | 방식 | 장점 | 단점 |
|---|---|---|---|
| 메시지 패싱 | 커널을 거쳐 send/receive 시스템 호출 | 안전, 구현 쉬움 | 매번 커널 개입 → 느림 |
| 공유 메모리 | 같은 메모리 영역을 직접 읽고 씀 (설정만 커널이) | 빠름 | 동기화를 직접 해야 함 |
### 생산자-소비자 문제
- 생산자가 데이터를 만들고 소비자가 사용, 사이에 버퍼
- 무한 버퍼: 생산자는 계속 넣을 수 있음 / 유한 버퍼: 가득 차면 생산자 대기, 비면 소비자 대기 (편의점 삼각김밥 진열대)
- 유한 버퍼를 원형 큐로 구현
```c
#define BUFFER_SIZE 10
typedef struct { /* ... */ } item;
item buffer[BUFFER_SIZE];
int in = 0;    /* 다음에 넣을 위치 */
int out = 0;   /* 다음에 꺼낼 위치 */

/* 생산자 */
while (true) {
    /* next_produced 생성 */
    while (((in + 1) % BUFFER_SIZE) == out)
        ;   /* 가득 참: 대기 */
    buffer[in] = next_produced;
    in = (in + 1) % BUFFER_SIZE;
}

/* 소비자 */
while (true) {
    while (in == out)
        ;   /* 비어 있음: 대기 */
    next_consumed = buffer[out];
    out = (out + 1) % BUFFER_SIZE;
    /* next_consumed 사용 */
}
```
- `in == out`이면 비어 있음, `(in + 1) % BUFFER_SIZE == out`이면 가득 참
- 둘을 구분하려고 한 칸을 항상 비워두므로 실제 저장 가능 개수는 **BUFFER_SIZE − 1**
- 빈 while로 기다리는 건 **바쁜 대기(busy waiting)** → 비효율적, 세마포어·모니터로 개선 (동기화 장)
