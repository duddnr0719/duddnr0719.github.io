> 장치마다 제각각인 하드웨어를 디바이스 드라이버가 감싸고, 커널 I/O 서브시스템이 스케줄링·버퍼링·캐싱·스풀링·오류 처리를 맡는다. CPU와 장치가 대화하는 방식은 폴링 → 인터럽트 → DMA 순으로 CPU 부담이 줄어든다.
### 개요
- I/O 관리는 OS 설계의 핵심. 장치 종류도 제어 방식도 매우 다양함
- 장치는 포트·버스·장치 컨트롤러로 연결
- **디바이스 드라이버**: 장치 세부사항을 캡슐화해 I/O 서브시스템에 **균일한 인터페이스** 제공
- 새 장치가 계속 나오니 성능 관리가 갈수록 중요
### I/O 하드웨어
- 포트: 장치가 연결되는 지점
- 버스: 데이지 체인이나 공유 직접 접근으로 연결된 선 묶음
  - PCI(요즘은 PCIe): PC·서버의 주 버스 / 확장 버스: 느린 장치(키보드, 직렬·병렬 포트)
  - 예: 프로세서 → 캐시 → 브리지·메모리 컨트롤러 → 메모리, 그리고 PCI 버스 → 그래픽·IDE·SCSI 컨트롤러, 확장 버스 인터페이스
- 컨트롤러(호스트 어댑터): 포트·버스·장치를 작동시키는 전자 회로. 장치에 붙어 있거나 별도 카드, 자체 프로세서·마이크로코드·메모리를 가지기도
- 컨트롤러의 레지스터 (보통 1~4바이트 또는 FIFO): **데이터 입력, 데이터 출력, 상태, 제어**
- 드라이버가 레지스터에 명령·주소·데이터를 넣어 장치를 제어. 접근 방식은
  - 전용 **I/O 명령어** (x86 in/out, I/O 포트 주소)
  - **메모리 맵 I/O**: 레지스터를 메모리 주소 공간에 매핑 → 일반 load/store로 접근 (그래픽처럼 큰 공간이 필요할 때 효율적)
- PC I/O 포트 예: 000–00F DMA 컨트롤러, 020–021 인터럽트 컨트롤러, 040–043 타이머, 320–32F 하드디스크 컨트롤러, 378–37F 병렬 포트, 3D0–3DF 그래픽, 3F8–3FF 직렬 포트(주)
### 폴링 (Polling)
- 바이트마다 상태 레지스터의 **busy** 비트가 0이 될 때까지 반복해서 읽음
1. 호스트가 busy가 꺼질 때까지 읽음
1. 쓰기/읽기 비트 설정, 쓰기면 데이터를 데이터 출력 레지스터에
1. command-ready 비트 설정
1. 컨트롤러가 이를 보고 busy를 켜고 전송 수행
1. 끝나면 컨트롤러가 command-ready, error, busy를 끔
- 바쁜 대기: 장치가 빠르면 괜찮지만 느리면 낭비. CPU가 다른 일 하느라 확인을 놓치면 장치 버퍼가 넘쳐 데이터 손실 가능
- 한 번 확인에 명령 3개(상태 읽기 → 비트 추출 → 분기) → 대부분 준비 안 된 상태면 손해
### 인터럽트
- 장치가 CPU의 **인터럽트 요청 라인**을 올리고, CPU는 명령어 하나 끝날 때마다 확인
- 들어오면 상태를 저장하고 **인터럽트 핸들러(ISR)** 로 점프 → 처리 후 복귀
- **인터럽트 벡터**: 번호 → 핸들러 주소 테이블. 장치가 더 많으면 같은 번호에 핸들러 리스트를 다는 **인터럽트 체이닝**
- 우선순위가 있고, 일부는 늦추거나 무시(maskable) 가능, 일부는 막을 수 없음(non-maskable, 심각한 오류용)
- 인터럽트 기반 I/O 순서
  1. 드라이버가 I/O 시작 (CPU)
  1. 컨트롤러가 I/O 수행
  1. 입력 준비·출력 완료·오류 시 인터럽트 발생
  1. CPU가 받아서 핸들러로
  1. 핸들러가 데이터 처리 후 복귀
  1. CPU가 하던 일 재개
- Intel Pentium 이벤트 벡터: 0 나눗셈 오류, 3 브레이크포인트, 6 잘못된 opcode, 8 double fault, 13 general protection, **14 page fault**, 16 부동소수점 오류 … 0~31은 예외(마스크 불가), 32~255는 마스크 가능 인터럽트
- 인터럽트는 장치 I/O 말고도
  - 예외: 0 나누기·보호 위반 → 프로세스 종료, 페이지 폴트 → 페이지 적재
  - 시스템 호출: **트랩**(소프트웨어 인터럽트)으로 커널 진입. I/O는 특권 명령이라 반드시 시스템 호출을 통해서만
  - 멀티 CPU는 인터럽트를 동시에 처리하도록 설계 가능
### DMA (Direct Memory Access)
- 대량 전송에 바이트마다 CPU가 레지스터를 들락거리는 **프로그램 I/O(PIO)** 를 피함 → CPU를 거치지 않고 장치 ↔ 메모리 직접 전송
- OS가 메모리에 DMA 명령 블록(원본·목적지 주소, 읽기/쓰기 모드, 바이트 수)을 쓰고 그 위치를 DMA 컨트롤러에 알림 → 컨트롤러가 **버스 마스터**가 되어 전송
- 전송 중 CPU의 버스 사용을 잠깐씩 뺏지만(사이클 스틸링) 훨씬 효율적. 끝나면 인터럽트 한 번
- DVMA: 가상 주소를 직접 이해하는 DMA
- 6단계
  1. 드라이버가 "디스크 데이터를 주소 X 버퍼로" 요청을 받음
  1. 드라이버가 디스크 컨트롤러에 "C바이트를 X로" 지시
  1. 디스크 컨트롤러가 DMA 전송 시작
  1. 디스크 컨트롤러가 바이트를 DMA 컨트롤러로 보냄
  1. DMA 컨트롤러가 X에 쓰면서 주소는 증가, C는 감소
  1. C = 0이 되면 CPU에 인터럽트로 완료 알림
### 응용 프로그램 I/O 인터페이스
- 시스템 호출이 장치들을 **몇 가지 일반 클래스**로 묶어 감싸고, 드라이버 계층이 컨트롤러 차이를 커널로부터 숨김
  - 기존 프로토콜을 쓰는 새 장치는 드라이버만 있으면 OS 수정 없이 사용
  - 단, 드라이버 프레임워크는 OS마다 다름
- 계층: 커널 → 커널 I/O 서브시스템 → (소프트웨어) SCSI·키보드·마우스·PCI 버스·ATAPI 드라이버 → (하드웨어) 각 컨트롤러 → 장치
| 측면 | 종류 | 예 |
|---|---|---|
| 전송 단위 | 문자 / 블록 | 터미널 / 디스크 |
| 접근 방식 | 순차 / 임의 | 모뎀 / CD-ROM |
| 전송 시점 | 동기 / 비동기 | 테이프 / 키보드 |
| 공유 | 전용 / 공유 | 테이프 / 키보드 |
| 속도 | 지연, 탐색 시간, 전송률, 연산 간 지연 | |
| 방향 | 읽기 전용 / 쓰기 전용 / 읽기·쓰기 | CD-ROM / 그래픽 컨트롤러 / 디스크 |
- 규격에 안 맞는 장치 고유 기능은 뒷문(escape)으로: UNIX `ioctl(fd, command, data)` → 드라이버에 임의 명령 전달
### 장치 클래스
- **블록 장치**(디스크): `read`, `write`, `seek`
  - 파일 시스템을 통해 쓰거나, raw I/O·direct I/O로 블록에 직접 접근 (DB가 자체 버퍼링할 때)
  - **메모리 맵 파일**: 파일을 가상 메모리에 매핑하고 요구 페이징으로 읽음
- **문자 장치**(키보드, 마우스, 직렬 포트): `get()`, `put()` 한 문자씩. 줄 단위 편집은 상위 라이브러리가 제공
- **네트워크 장치**: 블록·문자와 성격이 달라 **소켓** 인터페이스 (Linux, UNIX, Windows). 프로토콜과 네트워크 동작을 분리, `select()`로 여러 소켓 중 준비된 것 확인. 그 밖에 파이프, FIFO, 스트림, 큐, 메일박스
- **시계와 타이머**: 현재 시각, 경과 시간, 타이머 설정. 일반 해상도 약 1/60초, 더 정밀한 것도 있음. 프로그래머블 인터벌 타이머로 주기적 인터럽트(스케줄러 타임 슬라이스 등)
### 블로킹, 논블로킹, 비동기 I/O
- **블로킹**: I/O가 끝날 때까지 프로세스를 대기 큐로. 쓰기·이해하기 쉽지만 부족할 때가 있음
- **논블로킹**: 있는 만큼만 즉시 반환 (읽은·쓴 바이트 수). UI, 버퍼 I/O에 유용. 멀티스레드로도 구현 가능. `select()`로 준비 확인 후 `read()`/`write()`
- **비동기**: 요청만 걸어두고 프로세스는 계속 실행, 끝나면 I/O 서브시스템이 신호·콜백으로 알림. 쓰기 어려움
- 동기: 요청 → 드라이버·핸들러·하드웨어 전송이 끝날 때까지 대기 → 재개 / 비동기: 요청 후 바로 계속, 전송은 뒤에서
### 커널 I/O 서브시스템
- **스케줄링**: 장치별 요청 큐에서 순서 조정 (디스크 스케줄링 등), 공정성이나 QoS. 장치 상태 테이블에 장치별 상태(busy 등)와 요청 목록(파일, 연산, 주소, 길이)을 둠
- **버퍼링**: 전송 중 데이터를 메모리에 잠시 보관
  - 속도 차이 흡수 (모뎀 → 디스크), 전송 크기 차이 흡수 (네트워크 패킷 조각 ↔ 메시지)
  - **복사 의미론**: `write()` 후 앱이 버퍼를 바꿔도 디스크엔 호출 시점 내용이 써지도록 커널 버퍼로 복사 (COW로 최적화하기도)
  - **이중 버퍼링**: 하나를 채우는 동안 다른 하나를 비움
- **캐싱**: 빠른 곳에 데이터 사본. 버퍼는 유일한 사본일 수 있고 캐시는 말 그대로 사본. 둘을 합쳐 쓰기도
- **스풀링**: 한 번에 하나만 처리할 수 있는 장치(프린터)의 출력을 디스크에 모아두고 순서대로 보냄
- **장치 예약**: 장치를 독점 할당/해제하는 시스템 호출 → 교착 주의
- **오류 처리**: 일시적 오류(디스크 읽기 실패, 장치 일시 불가)는 재시도. Solaris FMA, AIX처럼 오류 빈도를 추적해 재시도 오류가 늘어나는 장치는 사용 중지. 실패하면 오류 코드 반환, 시스템 로그에 기록
- **커널 자료구조**: 열린 파일 테이블, 네트워크 연결, 문자 장치 상태, 버퍼, 더티 블록 등. Windows는 I/O 요청을 **메시지(IRP)** 로 만들어 커널 → 드라이버 → 다시 사용자로 전달하며 수정 (유연하지만 오버헤드)
### STREAMS
- UNIX System V의 사용자 프로세스 ↔ 장치 간 **전이중** 통신 채널
- 구성: **스트림 헤드**(사용자 쪽) + 0개 이상의 **모듈** + **드라이버 엔드**(장치 쪽). 각각 읽기 큐·쓰기 큐 보유
- 큐끼리 메시지로 통신, 흐름 제어 지원. 내부는 비동기, 스트림 헤드와 사용자 프로세스 사이는 동기
- 모듈을 끼워 넣어 프로토콜 처리를 조립식으로
### 성능
- I/O는 CPU에 큰 부담: 드라이버 코드, 컨텍스트 스위치, 인터럽트 처리, 데이터 복사
- 개선
  - 컨텍스트 스위치 줄이기, 데이터 복사 줄이기
  - 인터럽트 줄이기: 큰 단위 전송, 똑똑한 컨트롤러, (busy가 짧을 땐) 폴링
  - DMA 활용, 기능을 하드웨어(컨트롤러)로 내리기
  - CPU·메모리·버스·I/O 성능의 균형 (하나라도 병목이면 전체가 놂)
  - 사용자 모드 프로세스·데몬을 커널 스레드로 옮기는 것 검토
- 기능을 어디에 둘지: 앱 코드 → 커널 → 드라이버 → 컨트롤러 → 장치 하드웨어로 내려갈수록 효율·성능↑, 대신 개발 비용·추상화 수준·유연성↓
