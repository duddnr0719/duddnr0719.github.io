### SDN 제어 평면의 등장 배경과 중앙 집중형 제어의 이점
- **전통적 인터넷 네트워크 계층의 구조와 한계**
  - 분산 · **라우터 당(distributed, per-router)** 방식으로 구현되어 왔음
  - 단일 라우터 안에 스위칭 하드웨어와 독점 라우터 OS(예: `Cisco IOS`)를 두고, 인터넷 표준 프로토콜(`IP` · `RIP` · `IS-IS` · `OSPF` · `BGP`)을 독점 형태로 구현함
  - 네트워크 계층마다 방화벽 · 부하 균형기(load balancer) · NAT 박스 등 별개의 **미들박스(middlebox, 네트워크 장비)**를 두는 구조임
  - **2005년** 무렵 네트워크 환경 변화 → 새로운 제어 평면 방식의 필요성이 제기됨
- **제어 평면 구조 복습**
  - **라우터 당 제어 평면(Per-Router Control Plane)** = 모든 라우터 내부의 개별 라우팅 알고리즘이 제어 평면에서 서로 통신하며 동작하는 방식
  - **논리적 중앙 집중형 제어 평면** = 논리적인 원격 중앙 제어기가 **로컬 제어 에이전트(local control agent, CA)**와 상호 작용하는 방식
- **논리적 중앙 집중형 제어 평면의 이점**
  - **네트워크 관리 용이** : **일반화된 포워딩(Generalized forwarding)**을 바탕으로 라우터의 잘못된 설정 오류를 막고 관리를 수월하게 함
  - **트래픽 흐름 제어의 유연성** : 테이블 기반 포워딩(`OpenFlow API`)으로 라우터를 "프로그래밍"할 수 있어 트래픽 흐름을 유연하게 다룸
  - **중앙 집중형 "프로그래밍"과 동적 분산** : 중앙에서 테이블을 계산해 라우터로 내려주므로 동적인 패키지 분산이 가능함
    - 반대로 모든 라우터에 분산 알고리즘(프로토콜)을 두어 테이블을 계산하는 분산 "프로그래밍"은 복잡해 구현과 관리가 어려움
  - **개방형 제어 평면 구현** : 특정 기업이 독점하던 제어 평면을 개방형 구조로 전환함
- **산업 구조 변화 비교(메인프레임 → PC 전개)**
  - **기존(수직적 통합)** : 폐쇄적 · 독점적 구조 → 발전 속도가 느리고 산업 영역이 좁음
  - **개방형(수평적 구조)** : 오픈 인터페이스 기반 → 발전 속도가 빠르고 산업 영역이 넓음
- **기존 라우팅의 3가지 한계와 SDN의 해결**
  - **특정 경로 지정** (`u` → `z`를 `uvwz`, `x` → `z`를 `xwyz` 경로로 보내려는 경우) : 링크 가중치를 정의해 조절하거나 새로운 라우팅 알고리즘이 필요함 → 링크 가중치는 이웃 노드로의 전달만 조절하므로 전체 트래픽 경로 설정은 불가능함
  - **트래픽 분할 · 부하 균형(load balancing)** (`u` → `z` 트래픽을 `uvwz`과 `uxyz`로 분리하려는 경우) : 기존 라우팅 알고리즘으로는 분리할 수 없으며 새로운 라우팅 알고리즘이 필요함
  - **트래픽 유형별 차별 라우팅** (빨강 · 파랑 트래픽을 각각 다르게 라우팅하려는 경우) : 목적지 기반 포워딩과 LS · DV 라우팅 알고리즘으로는 트래픽을 구분해 다르게 처리할 수 없음
  - → **일반적인 포워딩**과 **SDN**을 활용하면 원하는 라우팅 경로를 자유롭게 설정할 수 있음

### SDN 아키텍처: 데이터 평면 스위치, SDN 제어기, 네트워크 제어 응용
- **데이터 평면 스위치(Data Plane Switch)**
  - 일반화된 데이터 평면 포워딩을 하드웨어로 처리하는 빠르고 단순한 스위치
  - 제어기가 계산해 설치해 둔 **스위치 플로우 테이블**을 보유함
  - 테이블 기반 스위치 제어용 **API**(예: `OpenFlow`)를 통해 제어할 수 있는 대상과 없는 대상을 구분함
  - 제어기와의 통신 프로토콜(예: `OpenFlow`)로 상호 연동함
- **SDN 제어기(네트워크 OS)**
  - 네트워크 상태 정보를 유지 · 관리하는 계층
  - **노스바운드 API(Northbound API)** = 상위 계층 네트워크 제어 응용과 통신하는 인터페이스
  - **사우스바운드 API(Southbound API)** = 하위 계층 네트워크 스위치와 통신하는 인터페이스
  - 성능 · 확장성(scalability) · 고장 감내(fault-tolerance) · 강건성(robustness)을 확보하기 위해 분산 시스템으로 구현됨(예: `OpenFlow`)
- **네트워크 제어 응용**
  - **제어의 사령탑** : SDN 제어기가 제공하는 하위 계층 서비스와 API를 바탕으로 실제 제어 기능을 구현함
  - **분리 개발** : SDN이나 라우팅 전문 기업이 아닌 **제3자**도 독립적으로 개발해 공급할 수 있음

### OpenFlow 프로토콜과 SDN 제어기 구현체
- **OpenFlow 프로토콜 개요**
  - 제어기와 스위치 사이에서 동작하며 **TCP**로 메시지를 교환함(암호화는 옵션)
  - **OpenFlow 메시지 3가지 클래스** : 제어기에서 스위치 · 비동기(스위치에서 제어기) · 대칭(기타)
- **제어기 → 스위치 주요 메시지**
  - **특성(feature)** = 제어기가 스위치 특성을 질의하면 스위치가 응답하는 메시지
  - **설정(configure)** = 제어기가 스위치 설정을 조회하거나 지정하는 메시지
  - **상태 변경(modify-state)** = OpenFlow 테이블의 플로우 엔트리를 추가 · 삭제 · 변경하는 메시지
  - **패킷 내보내기(packet-out)** = 컨트롤러가 만든 제어용 패킷을 지정한 스위치 포트로 전송하는 메시지
- **스위치 → 제어기 주요 메시지**
  - **패킷 받기(packet-in)** = 스위치가 처리 방안을 묻기 위해 패킷을 제어기로 올려보내는 메시지
  - **플로우 삭제(flow-removed)** = 스위치에서 플로우 테이블 엔트리가 제거되었음을 알리는 메시지
  - **포트 상태(port status)** = 포트 상태 변경을 제어기에 통지하는 메시지
- **상위 수준 추상화 활용** : 네트워크 운영자는 OpenFlow 메시지를 직접 다루어 스위치를 프로그래밍하지 않고 제어기가 제공하는 **상위 수준의 추상화**를 활용함
- **SDN 제어/데이터 상호작용 단계(링크 장애 대응 예)**
  1. 스위치 `s1`이 링크 연결 실패를 OpenFlow **포트 상태** 메시지로 제어기에 통지
  2. SDN 제어기가 OpenFlow 메시지를 수신해 링크 상태 정보를 업데이트
  3. 링크 변경 시 동작하는 **Dijkstra 라우팅 알고리즘** 호출
  4. Dijkstra 알고리즘이 제어기의 네트워크 그래프 및 링크 상태 정보에 접근해 새 경로 산출
  5. 라우팅 알고리즘이 SDN 제어기의 **플로우 테이블 계산 컴포넌트**와 연동해 필요 시 새 플로우 테이블 생성
  6. 제어기가 OpenFlow를 통해 갱신 대상 스위치에 새 테이블 설치
- **오픈소스 SDN 제어기 구현체**
  - **OpenDaylight(ODL) 제어기** (`www.opendaylight.org`)
    - 네트워크 응용을 SDN 제어기 내부 또는 외부에 배치할 수 있는 구조
    - **서비스 추상화 계층(Service Abstraction Layer)** = 내부 · 외부 응용과 서비스를 상호 연결하는 계층
  - **ONOS(Open Network Operating System) 제어기** (`wiki.onosproject.org`)
    - 네트워크 응용을 제어기와 분리해 구성함
    - **인텐트 프레임워크(intent framework)** = '어떻게(how)'보다 **'무엇(what)'**을 원하는지만 선언하는 상위 수준 서비스 사양 제공
    - **분산 코어**에 중점을 두어 서비스 신뢰도와 확장에 따른 성능을 확보함
- **오픈소스 SDN의 현황과 한계**
  - 소프트웨어를 하드웨어로부터 분리해 운용하는 개념으로 아직 널리 보급되지는 않았으나 대형 데이터센터(대형 ISP · 구글 등)에서 사용 중
  - **Inter-AS** 구간에서는 여전히 **BGP**가 쓰임
  - **단일 장애점(Single point of Failure)** 위험이 있으며, 노력하고 있으나 하드웨어 및 구형 기술 대비 속도가 느림

### ICMP(Internet Control Message Protocol)와 Traceroute
- **ICMP 개요 및 메시지 구조**
  - 호스트와 라우터 사이에서 **네트워크 계층 정보**를 주고받는 프로토콜
  - **주요 기능**
    - **오류 보고(error reporting)** : '목적지 네트워크에 도달하지 못함' 같은 전송 오류 통지
    - **반향(echo) 요청/응답** : `ping` 프로그램에서 사용
  - **계층과 포맷**
    - **IP 상위 계층**에 해당하며, ICMP 메시지는 **IP 데이터그램의 페이로드**로 전송됨
    - **타입(type)** · **코드(code)** 필드와 **에러가 발생한 IP 데이터그램의 첫 8바이트**로 구성됨
- **Traceroute 진단 프로그램과 ICMP 동작**
  - **역할** : 지정된 목적지 경로를 따라 출발지부터 목적지 사이 라우터의 이름 · IP 주소를 추적하고 지연을 측정함
  - **지연 측정 및 패킷 송신**
    - 경로 상 모든 라우터 `i`에 대해 `3`개의 패킷을 보내고, 라우터 `i`가 패킷을 되돌려주면 송신과 응답 사이 시간을 재어 지연을 측정함
    - 출발지는 목적지를 향해 **UDP 포트 번호가 없는** 일련의 **UDP 세그먼트**를 송신함
    - 첫 번째 데이터그램은 `TTL=1`, 두 번째는 `TTL=2` 순으로 `TTL`을 `1`씩 높이며, 표준 Traceroute 프로그램은 같은 `TTL` 값을 가진 패킷을 **3번** 보냄
    - `n`번째 데이터그램이 `n`번째 라우터에 도달 → 라우터가 데이터그램 폐기 → 출발지로 **ICMP 메시지(`타입 11, 코드 0`, TTL expired)** 전송
    - 해당 ICMP 메시지에 라우터 이름과 IP 주소가 포함되며, 출발지는 응답 수신 시점에 **RTT**를 계산함
  - **중단 조건(stopping criterion)**
    - UDP 세그먼트가 최종 목적지 호스트에 도착하면 포트 번호가 없으므로 목적지가 오류를 반환함
    - 목적지가 **ICMP `"port unreachable"` 패킷(`타입 3, 코드 3`)**을 돌려보내면, 출발지가 이를 수신한 뒤 추적을 중단함

### 네트워크 관리와 설정: SNMP/MIB, NETCONF/YANG
- **네트워크 관리(Network Management)의 정의와 필요성**
  - 네트워크는 수천 개의 하드웨어/소프트웨어 요소가 상호 작용하는 자율 시스템으로, 비행기 · 핵 발전소처럼 감시 · 관리 · 제어가 필요한 복잡계임
  - **네트워크 관리** = 적정 비용으로 실시간 · 운용성능 · 서비스 품질 요구를 맞추기 위해 하드웨어 · 소프트웨어 · 인간 요소를 배치해 통합 · 조정함으로써 네트워크와 구성요소 자원을 감시 · 테스트 · 폴링 · 설정 · 분석 · 평가 · 제어하는 활동
- **네트워크 관리 시스템의 3가지 핵심 요소**
  - **관리 서버(managing server/controller)** = 네트워크 관리자가 운용하는 응용으로, 프로토콜을 통해 장치를 질의 · 설정 · 관리함
  - **피관리 장치(managed device)** = 설정해야 하는 하드웨어 · 소프트웨어 컴포넌트를 갖는 관리 대상 장치
    - 내부에 **에이전트(agent)**와 **데이터(data)**(장치 상태 · 설정 데이터 · 운용 데이터 · 장치 사용 통계)를 보유함
  - **네트워크 관리 프로토콜** = 관리 서버가 장치에 질의 · 설정 · 관리를 수행하고, 피관리 장치가 관리 서버에 데이터 · 이벤트를 알리는 데 사용됨
- **네트워크 관리 방식 비교**
  - **CLI(Command Line Interface)** = 운영자가 `ssh` 등으로 각 장치에 직접 접속해 명령을 입력하는 방식
  - **SNMP/MIB(Simple Network Management Protocol / Management Information Base)** = 운영자가 SNMP 프로토콜로 디바이스 데이터(`MIB`)를 질의 · 설정하는 방식
  - **NETCONF/YANG** = 데이터 모델링 언어 **YANG**으로 데이터를 정의하고, **NETCONF**로 원격 장치 간 YANG 호환 액션 · 데이터를 통신하는 방식
- **SNMP(Simple Network-Management Protocol)**
  - **MIB 정보를 전달하는 2가지 방법**
    - **요청/응답(request/response) 모드** = 관리 서버/제어기가 `request`를 보내면 피관리 장치가 `response`로 데이터를 회신함
    - **트랩(trap) 모드** = 피관리 장치가 데이터 · 이벤트를 알리기 위해 관리 서버/제어기로 `trap message`를 보냄
  - **메시지 형식** : SNMP 프로토콜의 메시지 단위를 **PDU(Protocol Data Unit)**라고 부름
- **NETCONF와 YANG**
  - **NETCONF** = **RPC(Remote Procedure Call)** 패러다임으로 관리 서버와 피관리 장치 간에 동작하며, 메시지는 **XML**로 작성됨
    - **동작 흐름** : 세션 초기화 및 기능 교환(`<hello>`) → 요청 · 응답(`<rpc>` · `<rpc-reply>`) 및 알림(`<notification>`) → 세션 종료(`<close-session>`)
  - **YANG** = NETCONF 네트워크 관리 데이터의 구조 · 문법 · 의미를 표현하는 **데이터 모델링 언어**로, 이를 이용해 장치와 동작을 기술한 **XML 문서**를 생성함
- **5장(제어 평면) 전체 요약**
  - **네트워크 제어 평면 접근 방식** : 전통적 **라우터 당 제어(per-router control)** vs **논리적 중앙 집중형 제어(SDN)**
  - **전통적 라우팅 알고리즘과 인터넷 구현** : **OSPF** · **BGP**
  - **SDN 제어기 실제 구현** : **ODL** · **ONOS**
  - **제어 메시지 및 운영 관리** : **ICMP** · **네트워크 관리**(`CLI` · `SNMP/MIB` · `NETCONF/YANG`)
