> 연구실 정본 NAS의 무방비 상태와 네트워크 단선을 계기로 Btrfs 예약 스냅샷과 정기 SMART 검사를 확립하고, 비표준 웹훅 규격을 해결하는 전용 중계 데몬을 개발하여 Slack 채널 실시간 알림 파이프라인을 구축함.

# 배경 — 왜 하게 됐나 ?
- 연구실 인프라 점검 중 데이터 정본 역할을 맡은 NAS가 무방비 상태임을 확인함.
- 스냅샷 패키지는 설치되어 있었으나 공유폴더 스냅샷이 0개였고, SMART 정기 검사와 장애 알림 설정도 전무했음.
- 여기에 11/2 오전 외부망 랜 포트의 물리 단선으로 가상머신 이미지 6대, 공유폴더, 홈 아카이브 등 백업 3종이 이틀 연속 실패하는 장애가 겹침.
- 관리 호스트만 실패 알림을 보내고 나머지 백업 실패는 아무도 알지 못했음.
- 목표 :
  - 실수나 랜섬웨어 발생 시 즉각 복구할 수 있는 Btrfs 스냅샷 체계 구축 (공유폴더 4개 대상, 매일 자동 생성, 최근 14개 보존).
  - 디스크 고장을 조기에 감지하기 위한 SMART 정기 검사 예약 (빠른 검사 주간, 확장 검사 월간).
  - 경고 및 장애 발생 시 연구실 공유 채널로 실시간 전달하는 웹훅 알림 파이프라인 완성.

# 환경
- 스토리지 : 연구실 NAS (Btrfs, DSM 7.2)
- 가상화 및 백업 호스트 : Debian 기반 가상화 호스트
- 연산 및 관리 환경 : 연구실 GPU 연산 노드 및 관리 노드
- 네트워크 : 2.5G 외부망 물리 링크 및 연구실 내부망
- 형상관리 : 연구실 인프라 레포지토리 (PR #19)

# 진행 흐름

## 1. 물리 링크 단선 확인과 근본 복구
- 11/2 10:22경부터 NAS 외부망 2.5G 포트가 물리 단선(NO-CARRIER) 상태에 빠진 것을 확인.
- 가상화 호스트 백업 저장소가 오프라인으로 전환되고, 연산 노드들의 원본 데이터 마운트가 응답 없이 멈춤.
- 임시 대안 검토 :
  - 통신 가능한 내부망으로 대상을 돌리는 우회로를 검토함.
  - 하지만 가상화 호스트 저장소, 연산 노드 마운트, 백업 가상머신 설정을 모두 고쳐야 해 변경 범위가 과도했음.
  - 설정 우회 대신 서버실 현장 점검으로 근본 조치를 결정함.
- 현장 점검으로 빠져 있던 랜 케이블을 재연결하여 2.5G 링크 복구 완료.
- 밀려 있던 백업 3종을 즉시 수동 실행하여 검증함 :
  - 홈 아카이브 백업 : 3분 24초 만에 종료 코드 0으로 완료.
  - 가상머신 6대 백업 : 11:09 ~ 11:15 수동 실행으로 파일 6개 생성 완료 (가장 큰 웹 서버 21GB).
  - 공유폴더 백업 : 바뀐 파일 4개 (34MB) 동기화 완료.
→ 물리 네트워크를 복구한 뒤, 본격적인 데이터 정본 보호 설정에 착수함.

## 2. Btrfs 예약 스냅샷 및 SMART 검사 예약
- 파일 손실을 방지하기 위해 Btrfs 스냅샷 스케줄을 수립함.
- 공유폴더 4개를 대상으로 매일 06:00에 스냅샷을 자동 생성하고, 최신 14개(최근 2주치)를 보존하도록 설정.
- 디스크 2장에 대해 SMART 정기 검사를 설정함 :
  - 빠른 검사 : 매주 토요일 00:00 예약.
  - 확장 검사 : 매월 22:00 예약 (첫 검사일 11/7).
→ 설정 완료 직후 마운트 경로에서 부작용을 발견함.

## 3. 스냅샷 디렉터리 노출 차단과 캐시 해제 검증
- NFS 마운트 최상위 경로에 스냅샷 디렉터리가 그대로 노출되어 있음을 발견.
- 노출 시 `du`, `find`, `rsync` 실행 과정에서 4.7 TB 공유 데이터가 중복 순회되어 백업 용량이 폭증함.
- 관리 화면 고급 설정에서 스냅샷 보이게 만들기 옵션을 즉시 비활성화함.
- 옵션을 끈 직후 디렉터리를 조회했으나 여전히 스냅샷 디렉터리가 표시되는 현상 발생 :
  - NFS 디렉터리 캐시(최대 60초)와 하위 마운트 유휴 유지 시간(500초)이 원인이었음.
  - 30초 간격으로 약 13분 동안 백그라운드 모니터링을 수행함.
  - 목록에서 스냅샷 디렉터리가 완전히 사라지고 하위 마운트가 자동 해제됨을 실측 검증.
→ 스냅샷과 디스크 검사는 설정되었으나, 이상 발생 시 알림을 보낼 채널 구축으로 넘어감.

## 4. Slack 직접 연동 실패와 프로토콜 규격 분석
- NAS 관리 화면의 웹훅 알림 기능으로 Slack Webhook 주소에 직접 테스트 알림을 발송함.
- 하지만 관리 화면에서 테스트 전송 실패가 발생함.
- 원인 규명을 위한 단계별 점검 :
  - NAS 콘솔에서 외부 Slack 서버 통신이 정상임을 확인하여 네트워크 단절 가설 기각.
  - 수동 페이로드로 curl 테스트 시 Slack에서 정상 수신됨을 확인하여 수신 문제 가설 기각.
- 가상화 호스트에 임시 웹 요청 수신기를 띄워 NAS가 전송하는 실제 패킷을 캡처함 :
  - DSM은 `Content-Type: application/json` 헤더를 붙이면서도 실제 본문은 URL 인코딩된 `payload` 형식으로 전송하고 있었음.
  - Slack의 표준 성공 응답인 `ok`를 실패로 간주하고 오직 `{"success":true}` JSON 응답만을 요구하고 있었음.
→ NAS 펌웨어를 수정할 수 없으므로 가상화 호스트에 전용 변환 중계 데몬을 개발하기로 결정.

## 5. 전용 중계 데몬(dsm-slack-relay) 개발과 토큰 전환
- 가상화 호스트에 전용 포트로 대기하는 중계 데몬을 구현함 :
  - NAS의 내부 요청만 수신하도록 제한.
  - URL 인코딩된 본문을 파싱하여 표준 JSON으로 Slack API에 전달.
  - Slack 성공 응답 확인 시 DSM에 `{"success":true}` 반환.
- 초기 배포 시 웹훅 URL을 셸에서 수동 입력받도록 했으나 빈 파일이 생성되어 서비스 기동에 실패함.
- 수동 입력을 없애고 가상화 호스트의 Slack 봇 토큰을 systemd credential로 재사용하도록 구조를 개선함.
- 데몬 스크립트와 systemd 유닛을 배포하여 서비스 활성화에 성공하고 관리자 DM으로 테스트 메시지를 수신함.
→ 개인 DM이 아닌 연구실 공유 채널로 알림 수신처를 전환하기로 결정.

## 6. 공유 채널 전환과 봇 권한 오류 해결
- 수신처를 관리자 개인 DM에서 연구실 공유 채널로 변경함.
- 변경 직후 테스트 전송 시 Slack API에서 `not_in_channel` 에러 발생 (14:25:14).
- 알림 봇이 해당 공유 채널의 멤버가 아니어서 발생한 오류임을 확인하고 채널에 봇을 초대함.
- 봇 초대 직후 재전송된 테스트 메시지가 채널로 즉시 정상 수신됨 (14:25:31).
- Warning 등급 이상의 이상 징후에만 채널 알림이 발송되도록 필터링 규칙 확정.
→ 일회성 작업으로 끝나지 않도록 인프라 레포지토리에 반영하기로 결정.

## 7. 인프라 레포지토리 반영 및 CI 검증 병합
- 인프라 형상관리 레포지토리에 중계 스크립트, systemd 유닛, 문서를 추가하고 PR #19 생성.
- CI 검사 2건 통과 확인 및 서버 파일과의 diff 0 검증 완료.
- main 브랜치(커밋 938fcb4)에 병합 완료.

# 트러블슈팅

## 1. 외부망 랜선 단선으로 인한 백업 파이프라인 전면 중단
- 현상 : 백업 3종이 이틀 연속 실패하고 저장소가 오프라인으로 표시됨.
- 원인 : NAS 외부망 랜 포트의 물리 링크 단선(NO-CARRIER) 상태.
- 해결 : 설정 우회 대신 서버실 현장에서 빠져 있던 랜 케이블을 물리적으로 재연결함.
- 결과 : 2.5G 물리 링크가 복구되고, 밀렸던 백업 3종을 수동 실행하여 모두 종료 코드 0으로 정상 완료함.

## 2. Btrfs 스냅샷 디렉터리 노출과 순회 부하
- 현상 : 스냅샷 설정 직후 NFS 마운트 경로 최상위에 스냅샷 디렉터리가 노출됨.
- 원인 : 관리 화면의 보이게 만들기 옵션이 켜져 있어 파일시스템 최상위에 매핑됨. `du`, `find`, `rsync` 실행 시 4.7 TB 데이터가 스냅샷 개수만큼 중복 순회되는 위험 발생.
- 해결 : 고급 설정에서 스냅샷 보이게 만들기 옵션을 비활성화함.
- 결과 : NFS 클라이언트 디렉터리 캐시(최대 60초)와 하위 마운트 유휴 시간(500초) 경과 후 디렉터리 목록에서 사라지고 하위 마운트가 자동 해제됨을 실측 확인.

## 3. DSM 웹훅과 Slack API 규격 불일치
- 현상 : NAS 관리 화면에서 Slack Webhook 주소로 보낸 테스트 알림이 실패함.
- 원인 : DSM은 본문을 URL 인코딩된 `payload` 형식으로 전송하고, Slack의 `ok` 응답을 오류로 보고 `{"success":true}` JSON 응답만을 요구함.
- 해결 : 가상화 호스트에 비표준 웹훅을 변환하는 전용 중계 데몬(`dsm-slack-relay`)을 개발하여 배포함.
- 결과 : DSM 요청을 정상 파싱하여 표준 JSON으로 Slack에 전달하고, DSM에는 요구 규격에 맞는 성공 응답을 반환하여 통신을 정상화함.

## 4. 수동 웹훅 URL 입력 오류와 데몬 기동 실패
- 현상 : 중계 데몬 배포 후 서비스가 시작되지 않고 아무런 반응이 없음.
- 원인 : 셸 입력 과정에서 웹훅 URL 파일이 빈 상태로 생성되어 서비스 사전 조건 검사에서 차단됨.
- 해결 : 수동 파일 입력을 폐기하고, 가상화 호스트의 Slack 봇 토큰을 systemd credential을 통해 재사용하도록 수정함.
- 결과 : 파일 누락 위험 없이 데몬이 정상 활성화되고 관리자 DM으로 테스트 메시지가 성공적으로 전달됨.

## 5. 공유 채널 전환 시 봇 권한 누락(not_in_channel) 오류
- 현상 : 알림 수신처를 관리자 개인 DM에서 연구실 공유 채널로 바꾸자 알림 전송이 실패함.
- 원인 : 데몬 로그 분석 결과 Slack API에서 `not_in_channel` 에러 반환. 알림 봇이 목적 채널에 초대되어 있지 않았음.
- 해결 : 공유 채널에 알림 봇을 초대하여 메시지 작성 권한을 부여함.
- 결과 : 초대 직후 전송된 테스트 알림이 채널로 즉시 정상 수신됨 (14:25:31 확인).

# 배운 점
- 물리 계층의 네트워크 단선은 복잡한 설정 우회로 땜질하려 하지 말고, 현장에서 케이블을 정상화하는 근본 조치가 인프라 전체의 복잡도를 낮추는 가장 빠른 길임.
- 외부 시스템과의 웹훅 연동 시 문서나 표준 규격을 맹신하지 말고, 실제 오가는 패킷을 직접 캡처하여 규격을 눈으로 검증해야 시간 낭비를 막을 수 있음.
- 배포 과정에서 텍스트 수동 입력을 배제하고, 기존 호스트에 검증된 자격증명 자산을 안전하게 재사용하는 구조가 시스템의 신뢰성을 크게 높임.
