> 신규 H200 GPU 서버의 유휴 낭비와 무단 점유를 막기 위해 Slurm 예약 기반 스케줄러와 웹 관리 포털을 구축하고, 실측 벤치마크를 통해 64코어 전체를 활용하도록 최적화함.

# 배경 — 왜 하게 됐나 ?
- 연구실에 H200 GPU 4장을 탑재한 고성능 서버가 신규 도입됨.
- 고가 자원 특성상 특정 사용자의 무단 독점이나 장시간 방치되는 유휴 문제를 사전에 막아야 했음.
- 목표 :
  - GPU 4장을 2장씩 두 쌍으로 묶어 1장 · 2장 · 4장 단위 예약 지원.
  - 연구자가 브라우저에서 예약 현황을 보고 사용 신청을 할 수 있는 웹 포털 구축.
  - Slurm 예약을 발급받은 사용자만 지정 기간에 GPU를 쓸 수 있도록 강제 격리.
  - 6시간 평균 사용률 10% 미만 방치 시 관리자에게 알리고 회수할 수 있는 체계 마련.
  - 탑재된 CPU 64코어를 병목 없이 온전히 활용할 수 있는 작업 환경 제공.

# 환경
- 장비 : H200 GPU 서버 (GPU 4장 · VRAM 141GB · AMD EPYC 9355 32코어 2소켓 · 총 64코어 128스레드 · NUMA 2개)
- 운영체제 · 커널 : Ubuntu Linux, 커널 6.8.0-138, NVIDIA 드라이버 595.91.07
- 소프트웨어 : Slurm 25.11.8 · MariaDB · cgroup v2 · FastAPI · SQLite · nginx

# 진행 흐름
1. OS 사양 · 토폴로지 실측과 초기 계획 수정
	- 초기에는 설계서에 적힌 64코어 1소켓 CPU와 드라이버 570, 커널 5.15를 전제로 함.
	- 실서버 하드웨어를 직접 확인해보니 AMD EPYC 9355 32코어 2소켓(NUMA 2개) 구조였음.
	- GPU 4장은 전부 소켓 0에 직결되어 있어, 소켓 0 코어만 쓰면 GPU당 8코어로 제한됨.
	- 드라이버는 595.91.07이고 커널은 6.8.0-138이었음.
	- 장치 식별 번호 확인 중 첫 번째 · 두 번째 카드가 2번 · 3번 디바이스 노드에 매핑되고, 세 번째 · 네 번째 카드가 0번 · 1번 디바이스 노드에 매핑되어 번호가 완전히 뒤집힌 것을 발견함.
	→ Slurm 25.11.8 소스 빌드를 진행하고, `gres.conf`에 역전된 디바이스 번호를 명시 매핑하여 올바른 카드가 묶이도록 초기 구성을 잡음.

2. Slurm 기본 수용 기준 시험과 구조적 결함 대응
	- Slurm 25.11.8을 올린 뒤 예약 기반 격리 동작 검증을 위해 7개 항목 시험을 수행하여 통과함.
	- 그러나 실제 운영 시 치명적인 구조적 결함 3가지를 실측함.
	  - 예약의 `cpu=N` 옵션은 코어 단위로 인식되며 소켓 0(32코어)에서만 코어를 탐색하여 GPU당 8코어가 한계였음.
	  - 4장 전체 예약 신청 시 기존 1~2장 부분 예약이 있어도 Slurm이 충돌을 거부하지 않고 덮어써 기존 잡을 막아버림 (1차 시험 37분 정체 원인).
	  - 잡 제출 제어 스크립트가 예약 플래그보다 먼저 평가되어 예약 인자를 적지 않은 잡이 즉시 튕김.
	→ 자원 겹침 검사를 Slurm에 위임하지 않고 상위 웹 백엔드와 관리 도구에서 선제적으로 차단하도록 구조를 변경함.

3. 웹 서비스 접근 경로 전환 (SSH 터널링 → 교내 전용 개방)
	- 초기에는 SSH 터널링을 통해 웹 화면에 접속하도록 안내함.
	- 터널 설정 미숙으로 접속 실패가 잦아 사용자 접근성이 크게 떨어짐.
	- 외부 노출을 막기 위해 방화벽 규칙을 정비하여 학내망에서만 접속하도록 제한함.
	- SSH 터널 방식을 버리고 웹 포트를 개방해 학내망에서는 브라우저로 직접 접속할 수 있게 설정함.
	→ 연구실과 교내망 환경에서 누구나 주소창 입력만으로 포털에 접근할 수 있게 됨.

4. 서비스형 웹 포털 전환과 관리 체계 구축
	- 웹 페이지 기반 정적 목업을 걷어내고 FastAPI 백엔드와 SQLite 데이터베이스를 결합한 웹 시스템을 구축함.
	- 관리자 승인 콘솔을 6개 탭으로 구성하고, 예약 강제 취소나 계정 비활성화 동작에 2단계 확인 절차를 적용함.
	- 가입 → 관리자 승인 → 예약 신청 → 승인(Slurm 예약 생성) → 잡 실행 → 반납 전체 흐름을 완성함.
	→ 목업을 내리고 실제 서비스 데몬을 등록하여 실서버 운영 체제로 진입함.

5. GPU 분할(MIG) 보류와 통째 카드 서빙 유지
	- 메모리 격리가 안 되는 Shard나 MPS는 OOM 시 타 사용자 잡까지 영향을 주므로 배제함.
	- 하드웨어 격리를 제공하는 MIG(71GB · 35GB 분할)를 검토했으나, 동적 분할 시 카드 전체가 완전히 비어 있어야 하는 제약이 있었음.
	- 이미 서버에서 선행 연구 작업이 돌고 있어 카드를 비울 수 없었음.
	→ 카드 분할을 무리하게 적용하지 않고, 1장 · 2장 · 4장 통째 카드 서빙 방식을 유지함.

6. SSH 세션의 GPU 직접 연산 차단
	- 웹 예약을 거치지 않고 SSH로 들어와 터미널에서 GPU 연산을 독점하는 행위를 막아야 했음.
	- PAM이나 sshd 설정은 원격 접속 단절 위험이 커 건드리지 않음.
	- systemd 로그인 세션 수준에서 GPU 연산 디바이스 접근을 닫아 CUDA 초기화 에러(`cuInit` 999)를 유도함 (`nvidia-smi` 조회는 허용).
	- 백그라운드 스케줄러 등을 통한 우회 실행 경로를 점검하여 일반 사용자의 무단 실행을 원천 차단함.
	→ Slurm 예약 잡 밖에서는 GPU 직접 연산이 불가능하도록 통제함.

7. 기능 확장 배포와 환경 의존적 결함 보완
	- 미사용 감지 알림, 6자리 이메일 인증, 작업 폴더 정리 도구, 사용자 전용 CLI 명령어를 배포함.
	- 실서버 배포 후 버그 2종이 발견됨.
	  - Slurm이 예약 정보를 조회할 때 GPU 타입명을 소문자(`paira`)로 반환하여 잡 제출이 거부됨.
	  - 사용자 홈 폴더 내 읽기 권한이 없는 디렉터리가 포함되어 있으면 용량 확인이 502 에러로 뻗음.
	- GPU 타입을 원래 대소문자 표기(`pairA`)로 자동 변환하도록 정규화 로직을 추가함.
	- 용량 측정 시 권한 에러를 예외 처리하고 접근 가능한 범위만 합산하도록 수정함.
	→ 실제 사용자 환경에서 발생하는 예외 상황을 처리함.

8. 웹 리버스 프록시 접속 경로 재구성
	- 데몬이 정상 작동 중임에도 외부 사용자가 포트 없이 접속 시 연결이 거부되는 현상이 보고됨.
	- 리버스 프록시가 특정 내부 포트 하나만 수신하고 있어 브라우저 기본 웹 접속 요청을 수신하지 못한 것이 원인이었음.
	- 일반 비암호화 웹 요청은 보안 암호화 서비스로 301 리다이렉트되도록 구성하고, 암호화 서비스를 정식 창구로 지정함.
	- 기존 웹 포트도 병행 수신하도록 구성하고 모든 경로에 학내망 접속 규칙을 적용함.
	→ 주소창에 포트 번호를 붙이지 않아도 웹 포털로 자동 연결되도록 개선함.

9. 유휴 GPU 회수 정책 변경과 연동 결함 5종 수정
	- 6시간 유휴 지속 시 24시간 뒤 자동 강제 취소하는 방식은 연구자의 연산 데이터를 날릴 위험이 컸음.
	- 자동 회수를 없애고 유휴 감지 시(6시간 평균 10% 미만) 신청자에게 반납을 권유하고 관리자에게 알림을 보내는 방식으로 바꿈.
	- 관리자가 승인 콘솔에서 상황을 확인한 뒤 수동으로 취소하도록 정책을 변경함.
	- 실서버 연동 시험 587건 중 발견된 결함 5종을 수정함.
	  - 다른 잡 실행 중 예약 종료일 변경 실패(502) → scontrol 호출에 `Flags=IGNORE_JOBS` 옵션 추가.
	  - ID와 이메일 끝 줄바꿈(`\n`) 포함 시 통과 버그 → 정규식 엄격 매칭.
	  - GPU 수량 필드 비정수형 통과 버그 → 정수(1, 2, 4) 검증.
	  - slurmctld 재시작 직후 약 4초간 승인 502 에러 → 3초 간격 재시도 로직 도입.
	  - 점검 예약을 일반 사용자가 취소 시 404 발생 → 403 권한 거부 처리.
	- 결함 수정 후 재시험에서 95건 전수 통과를 달성함.
	→ 웹과 스케줄러 간 데이터 불일치 위험을 해소함.

10. CPU 코어 배정 상한 논쟁과 벤치마크 실측
	- 소켓 0에만 붙어 있는 물리 구조 때문에 GPU당 8코어(총 32코어)만 쓰자는 의견과, 비어 있는 32코어를 낭비하지 말고 16코어씩 총 64코어를 다 쓰자는 의견이 대립함.
	- 반대편 소켓 코어를 쓰면 NUMA 거리 차이로 메모리 병목이 발생할 것이라는 가설이 있었음.
	- 4장 동시 부하 상황에서 3회 평균 벤치마크를 수행함.
	  - CPU 전처리 병목 작업 : 8코어 21508 img/s → 16코어 31006 img/s (+44% 향상)
	  - GPU 학습 병목 작업 (ResNet-50) : 8코어 15932 img/s → 16코어 16154 img/s (+1.4% 향상)
	- 실측 결과 16코어에서 성능 저하는 전혀 없었음.
	- 가설을 폐기하고 GPU당 16코어까지 지원하되 기본값은 8코어로 제출되는 정책을 확정함.
	- `gres.conf`에서 쌍 B 카드에 소켓 1 코어를 배정하도록 설정을 반영함 (검증 148건 통과, 5건 실패).
	→ 서버 하드웨어의 모든 CPU 코어를 남김없이 활용할 수 있게 최적화함.

11. 전체 라이프사이클 실서버 전수 검증
	- 계정 가입부터 승인, 코어 선택 잡 제출, 분할 예약 공존, 연장 및 반납까지 전 시나리오를 브라우저 클릭과 실서버 로그로 대조 검증함.
	- 총 260건 검증 항목에서 0건 실패로 전수 통과를 확인함 (참고 32건).
	→ 실무에 즉시 투입 가능한 안정성을 확보함.

# 트러블슈팅
## 1. GPU 디바이스 파일 번호 역전 현상
- 현상 : nvidia-smi 0번과 1번 카드가 2번과 3번 디바이스 노드에 매핑되고 2번과 3번 카드가 0번과 1번 디바이스 노드에 매핑되어 카드 순서가 뒤집힘.
- 원인 : 커널 모듈이 초기화될 때 드라이버 디바이스 노드를 부여하는 순서와 메인보드 PCI 슬롯 인덱스가 일치하지 않음.
- 해결 : `gres.conf` 설정 파일에 디바이스 번호를 역전된 순서 그대로 명시 등록함.
- 결과 : Slurm 예약 잡에서 요청한 물리 카드가 의도한 쌍(pairA, pairB)에 정확히 매핑됨.

## 2. 노드 전체(4장) 예약 생성 시 부분 예약 덮어쓰기 결함
- 현상 : 기존에 1장이나 2장 예약이 잡혀 있는 시간대에 4장 전체 예약을 신청하면 거부 없이 생성되어 기존 사용자 잡을 중단시킴 (1차 시험 37분 정체 원인).
- 원인 : Slurm 자체 예약 로직이 노드 단위 전체 자원 요청 시 기존 부분 예약과의 자원 충돌을 거부하지 않고 덮어쓰는 구조적 한계.
- 해결 : 예약 겹침 여부를 Slurm에 위임하지 않고 상위 웹 백엔드 및 제어 스크립트에서 선제적으로 전수 대조하여 거부하도록 로직 구현.
- 결과 : 겹치는 시간대의 예약 신청이 웹 승인 단계에서 확실하게 차단됨.

## 3. SSH 세션 직접 실행을 통한 GPU 무단 점유
- 현상 : 승인받지 않은 사용자가 SSH로 들어와 터미널에서 CUDA 프로세스를 직접 띄워 카드를 독점할 수 있었음.
- 원인 : Slurm은 잡 스케줄러일 뿐이라 리눅스 일반 세션의 디바이스 파일 접근 권한까지 통제하지는 못함.
- 해결 : 로그인 세션 환경에서 GPU 연산 디바이스 접근을 차단하여 CUDA 초기화 시 에러(`cuInit` 999)가 발생하도록 가드를 구축하고, 백그라운드 우회 실행 경로도 함께 차단함.
- 결과 : 예약 밖에서의 직접 연산이 차단되고, Slurm 예약 잡 안에서만 정상 연산이 가능해짐.

## 4. 리버스 프록시 접속 경로 미수신으로 인한 웹 접속 실패
- 현상 : 웹 서비스 데몬이 켜져 있음에도 외부 사용자가 브라우저 주소창에 포트 없이 입력하면 사이트가 열리지 않음.
- 원인 : 리버스 프록시가 특정 내부 포트만 수신하고 있어 브라우저 기본 웹 접속 요청을 거부함.
- 해결 : 일반 웹 요청은 보안 암호화 서비스로 301 리다이렉트하고, 암호화 접속을 정식 서비스로 올리며, 기존 웹 포트도 병행 수신하도록 구성함. 방화벽 규칙도 모든 경로에 동일하게 적용함.
- 결과 : 주소창 입력 방식과 무관하게 학내망에서 웹 포털로 매끄럽게 연결됨.

## 5. 다른 잡 실행 중 예약 종료일 수정 실패 (502 에러)
- 현상 : 다른 사용자의 잡이 실행 중일 때 특정 예약의 종료일을 연장하거나 조기 반납하려 하면 웹에서 502 에러가 터짐.
- 원인 : Slurm `scontrol update` 명령이 노드에서 잡이 실행되고 있을 때 예약 시간 수정을 기본적으로 거부함.
- 해결 : 예약 갱신 명령어 호출 시 `Flags=IGNORE_JOBS` 플래그를 추가하여 잡 실행 여부와 무관하게 예약 시간을 수정할 수 있도록 조치함.
- 결과 : 다중 예약 환경에서도 연장 승인과 조기 반납이 에러 없이 즉시 처리됨.
