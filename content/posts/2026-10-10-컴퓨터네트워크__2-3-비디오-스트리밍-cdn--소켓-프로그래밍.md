> 스트리밍 비디오 = 압축 + DASH + 재생 버퍼링. 이걸 전 세계에 뿌리는 게 CDN이고, 애플리케이션은 결국 소켓으로 TCP/UDP를 쓴다.
### 비디오 스트리밍의 도전 과제
- Netflix·YouTube가 가정용 ISP 다운스트림의 80%(2020). 
- 확장성: 수억 명에게 서버 하나로는 불가 / 이질성: 유선·무선, 고·저대역폭 사용자 혼재
- 해결: 분산된 응용 수준 인프라(CDN)
### 비디오와 압축
- 비디오 = 일정 속도(예: 24장/초)로 출력되는 이미지 배열, 이미지 = 픽셀 배열
- 압축은 중복 제거
  - 공간적 중복: 한 이미지 안. 같은 색 픽셀 N개 → (색상 값, N) 두 개만 전송
  - 시간적 중복: 연속 프레임 사이. 프레임 i+1 전체 대신 i와의 차이만 전송
- CBR(고정 비트율) vs VBR(움직임에 따라 비트율 가변)
- 예: MPEG1(CD-ROM) 1.5Mbps, MPEG2(DVD) 3~6Mbps, MPEG4(인터넷) 64Kbps~12Mbps
### 저장 비디오 스트리밍
- 스트리밍: 앞부분 재생하는 동안 뒷부분을 계속 받음
- 대역폭이 혼잡에 따라 계속 변하고, 손실·지연이 생기면 재생이 끊김
- 연속 재생: 한번 재생 시작하면 원래 타이밍대로 가야 함 → 지연 변동(지터) 때문에 **클라이언트 버퍼 + 재생 지연**으로 보상
- 상호작용성(정지, 되감기, 빨리감기, 인덱싱), 손실 패킷 재전송도 고려
### DASH (Dynamic Adaptive Streaming over HTTP)
- 서버: 비디오를 청크로 쪼개고, 청크마다 여러 비트율(144p, 360p, 720p …)로 인코딩해 따로 저장. manifest 파일에 비트율별 URL 제공.
- 클라이언트: 주기적으로 대역폭 측정 → manifest 보고 지금 대역폭으로 버틸 수 있는 최대 비트율 청크를 하나씩 요청
- 지능은 클라이언트에: 버퍼가 비거나 넘치지 않게 요청 시점 결정, 비트율 결정, 가깝거나 대역폭 높은 서버 선택
### CDN
- 옵션1 거대 데이터센터 1개: 단일 장애점, 혼잡 지점, 먼 클라이언트는 긴 경로, 인기 영상이 같은 링크로 반복 전송 → 확장 불가
- 옵션2 분산 서버에 복사본 저장(CDN)
  - Enter deep: ISP 접속 네트워크 깊숙이 서버 배치, 사용자와 최대한 가깝게 (Akamai, 120개국 24만 서버, 2015)
  - Bring home: 접속 네트워크 근처 POP에 적은 수의 대형 클러스터 (Limelight)
- 동작: 가까운 노드로 유도, 경로가 혼잡하면 다른 복사본 노드 선택
### CDN 접근 과정 (DNS 리다이렉션)
1. Bob이 netcinema.com 페이지에서 `http://netcinema.com/6Y7B23V` 얻음
1. 로컬 DNS로 질의
1. netcinema 책임 DNS가 IP 대신 `http://KingCDN.com/NetC6y&B23V` 반환
1. 로컬 DNS가 KingCDN 책임 DNS에 질의
1. KingCDN이 적절한 CDN 서버 IP 반환
1. Bob이 그 서버에서 HTTP(DASH)로 스트리밍
### OTT와 Netflix
- OTT: 인터넷으로 영화·TV를 제공하는 서비스. 과제: 가장자리 혼잡, 어떤 노드에 무엇을 둘지, 어느 노드에서 받을지, 비트율
- Netflix: 등록·과금 서버만 자체 운영, 나머지는 제3자 인프라
  - 스튜디오 마스터를 Amazon 클라우드에 업로드 → 여러 비트율·포맷 생성 → CDN으로 업로드
  - CDN은 Akamai, Limelight, Level-3 혼용
  - 흐름: 계정/로그인(Netflix 서버) → 브라우징(Amazon) → manifest 반환(CDN 순위 + 버전별 URL) → DASH 스트리밍
### 소켓 프로그래밍
- 소켓 = 애플리케이션 프로세스와 종단 간 트랜스포트 프로토콜 사이 인터페이스. 위는 개발자, 아래는 OS가 제어.
- UDP: 비연결·비신뢰 / TCP: 연결형·신뢰
- 예제 앱: 클라이언트가 한 줄 입력 → 서버가 대문자로 바꿔 돌려줌 → 클라이언트 출력
### UDP 소켓
- 핸드셰이크 없음. 보낼 때마다 목적지 IP·포트를 붙여야 하고, 서버는 받은 패킷에서 송신자 주소를 꺼내 답장.
- 순서 바뀜·손실 가능. 앱 입장에선 '데이터그램' 단위 전송.
```python
# UDPClient.py
from socket import *
serverName = 'localhost'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_DGRAM)          # UDP 소켓
message = input('Input lowercase sentence:')
clientSocket.sendto(message.encode(), (serverName, serverPort))  # 매번 주소 지정
modifiedMessage, serverAddress = clientSocket.recvfrom(2048)
print(modifiedMessage.decode())
clientSocket.close()
```
```python
# UDPServer.py
from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_DGRAM)
serverSocket.bind(('', serverPort))
print('The server is ready to receive')
while True:
    message, clientAddress = serverSocket.recvfrom(2048)  # 송신자 주소도 같이 받음
    serverSocket.sendto(message.decode().upper().encode(), clientAddress)
```
### TCP 소켓
- 서버 프로세스가 먼저 떠 있어야 하고, 접속만 받는 환영 소켓(welcoming socket)을 가짐
- 클라이언트가 서버 IP·포트로 소켓 생성 → 3-way handshake로 연결
- 서버는 `accept()` 때 그 클라이언트 전용 **연결 소켓**을 새로 만듦 → 여러 클라이언트 동시 처리(소스 포트로 구분)
- 앱 입장에선 바이트 스트림 '파이프'. 연결 후엔 주소를 붙이지 않음.
```python
# TCPClient.py
from socket import *
serverName = 'localhost'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_STREAM)         # TCP 소켓
clientSocket.connect((serverName, serverPort))      # 연결 설정
sentence = input('Input lowercase sentence:')
clientSocket.send(sentence.encode())
modifiedSentence = clientSocket.recv(1024)
print('From Server:', modifiedSentence.decode())
clientSocket.close()
```
```python
# TCPServer.py
from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_STREAM)         # 환영 소켓
serverSocket.bind(('', serverPort))
serverSocket.listen(1)
print('The server is ready to receive')
while True:
    connectionSocket, addr = serverSocket.accept()  # 클라이언트별 연결 소켓
    sentence = connectionSocket.recv(1024).decode()
    connectionSocket.send(sentence.upper().encode())
    connectionSocket.close()                        # 환영 소켓은 계속 대기
```
- 실행: 서버 먼저 `python3 TCPServer.py` → 다른 터미널에서 `python3 TCPClient.py`
### 2장 정리
- 구조: 클라이언트/서버, P2P / 요구사항: 신뢰성, 처리율, 지연
- 트랜스포트: TCP(연결·신뢰), UDP(비신뢰·데이터그램)
- 프로토콜: HTTP, SMTP·POP·IMAP, DNS, BitTorrent·DHT, DASH·CDN, 소켓
- 프로토콜 공통 패턴: 요청/응답 교환, 메시지 = 헤더(데이터에 대한 정보) + 데이터
- 설계 이슈: 중앙집중 vs 분산, stateless vs stateful, 신뢰 vs 비신뢰 전송, "복잡성은 네트워크 가장자리에"
