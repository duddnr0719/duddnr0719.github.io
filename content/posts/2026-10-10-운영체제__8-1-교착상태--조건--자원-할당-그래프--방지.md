> 교착상태는 상호 배제·보유와 대기·비선점·순환 대기 4조건이 **동시에** 성립할 때만 생긴다. 자원 할당 그래프에 사이클이 없으면 안전, 있으면 (인스턴스가 하나씩일 땐) 교착. 처리 방법은 방지·회피·탐지+복구·무시.
### 교착상태란
- 집합 안의 모든 프로세스가, 그 집합 안의 다른 프로세스만 일으킬 수 있는 사건을 기다리는 상황
- 요청한 자원을 다른 대기 중인 스레드가 쥐고 있어서 스스로는 상태를 바꿀 수 없음
### 시스템 모델
- 유한한 자원 유형 R₁…Rₘ, 각 유형마다 인스턴스 여러 개 (예: CPU 4, 메모리 2, I/O 3)
- 자원 사용 순서: **요청**(open, wait, lock) → **사용** → **해제**(close, signal, unlock)
- mutex 두 개로 만드는 교착
```c
pthread_mutex_t first_mutex, second_mutex;

void *do_work_one(void *param) {
    pthread_mutex_lock(&first_mutex);
    pthread_mutex_lock(&second_mutex);
    /* 작업 */
    pthread_mutex_unlock(&second_mutex);
    pthread_mutex_unlock(&first_mutex);
    pthread_exit(0);
}
void *do_work_two(void *param) {
    pthread_mutex_lock(&second_mutex);   /* 순서가 반대 */
    pthread_mutex_lock(&first_mutex);
    /* 작업 */
    pthread_mutex_unlock(&first_mutex);
    pthread_mutex_unlock(&second_mutex);
    pthread_exit(0);
}
```
- T1이 first를, T2가 second를 잡은 순간 서로를 영원히 기다림. 다만 타이밍이 맞아야만 생겨서 재현·테스트가 어려움
- 해결: 잠금 순서를 모두 first → second로 통일
### 필요조건 4가지 (모두 동시에 성립해야 함)
1. **상호 배제**: 자원을 한 번에 하나만 사용
1. **보유와 대기**: 자원을 하나 이상 쥔 채 다른 자원을 기다림
1. **비선점**: 쥔 쪽이 스스로 놓기 전엔 뺏을 수 없음
1. **순환 대기**: P₀ → P₁ → … → Pₙ → P₀ 처럼 서로가 쥔 자원을 고리 모양으로 기다림
### 자원 할당 그래프
- 방향 그래프 G = (V, E). V = 프로세스 집합 P ∪ 자원 유형 집합 R
  - 프로세스: 원 / 자원: 사각형, 안의 점 = 인스턴스 수
  - **요청 간선** Pᵢ → Rⱼ: 요청하고 기다리는 중
  - **할당 간선** Rⱼ → Pᵢ: 인스턴스가 할당됨
- 위 mutex 예: first_mutex → thread_one → second_mutex → thread_two → first_mutex (사이클)
- 예: T = {T₁, T₂, T₃}, R₁(1), R₂(2), R₃(1), R₄(3)
  - E = {T₁ → R₁, T₂ → R₃, R₁ → T₂, R₂ → T₂, R₂ → T₁, R₃ → T₃}
  - 사이클 없음 → 교착 아님 (T₃가 끝나면 R₃ 반환 → T₂ → T₁ 순으로 진행)
- 여기에 T₃ → R₂ 추가하면 사이클 2개
  - T₁ → R₁ → T₂ → R₃ → T₃ → R₂ → T₁
  - T₂ → R₃ → T₃ → R₂ → T₂
  - R₂의 인스턴스 2개가 모두 T₁, T₂에 있고 둘 다 대기 중 → **교착**
- 사이클이 있지만 교착이 아닌 예: P₁ → R₁ → P₃ → R₂ → P₁, 그런데 R₁, R₂에 인스턴스가 하나씩 더 있어 P₂, P₄가 쥐고 있음 → P₂나 P₄가 끝나며 반환하면 사이클이 풀림
- 정리
  - 사이클 없음 → 교착 **없음** (확실)
  - 사이클 있음 + 자원 유형마다 인스턴스 1개 → 교착 **확정**
  - 사이클 있음 + 인스턴스 여러 개 → 교착 **가능성**만 (사이클은 필요조건이지 충분조건이 아님)
### 처리 방법
| 방법 | 내용 | 오버헤드 |
|---|---|---|
| 방지 (prevention) | 4조건 중 하나 이상을 구조적으로 불가능하게 | 높음 |
| 회피 (avoidance) | 사전 정보(최대 요구량)로 항상 안전 상태만 유지 | 높음 |
| 탐지 + 복구 | 생기도록 두고 주기적으로 찾아서 복구 | 낮음 |
| 무시 (타조 알고리즘) | 드물게 생기니 신경 안 씀 | 없음 |
- Linux, Windows 등 대부분의 OS는 **무시**를 택하고, 교착을 피하는 건 응용 개발자의 몫
### 방지: 조건별 전략
- **상호 배제 제거**: 읽기 전용 파일처럼 공유 가능한 자원은 잠글 필요 없음. 하지만 mutex처럼 본질적으로 독점인 자원이 있어 일반적으로 불가능
- **보유와 대기 제거**: 시작할 때 필요한 자원을 한꺼번에 요청·할당받거나, 아무것도 안 쥐었을 때만 요청 허용 → 자원 이용률↓, 인기 자원 여러 개가 필요한 프로세스는 기아
- **비선점 제거**: 요청이 바로 안 되면 쥔 자원을 모두 내놓게 함(선점) → 레지스터·메모리처럼 상태를 저장·복원하기 쉬운 자원에만 적용 가능, mutex·세마포엔 부적합
- **순환 대기 제거**: 모든 자원 유형에 순서 F: R → ℕ를 매기고 **오름차순으로만 요청** → 가장 현실적
  - F(first_mutex) = 1, F(second_mutex) = 5면 모든 스레드가 first → second 순으로만 잠금
  - 순서를 정하는 것 자체가 개발자의 규율에 달림
### 잠금 순서를 정해도 생기는 교착: 계좌 이체
```c
void transaction(Account from, Account to, double amount) {
    mutex lock1 = get_lock(from);
    mutex lock2 = get_lock(to);
    acquire(lock1);
    acquire(lock2);
    withdraw(from, amount);
    deposit(to, amount);
    release(lock2);
    release(lock1);
}
```
- 코드상 순서는 항상 from → to지만, T1이 `transaction(A, B, 25)`, T2가 `transaction(B, A, 50)`을 동시에 실행하면 T1은 A → B, T2는 B → A 순으로 잠금 → 교착
- 해결: 계좌 번호처럼 **전역적으로 정해진 기준**으로 잠금 순서를 정함 (항상 번호가 작은 계좌부터)
- 모든 계좌를 하나의 큰 잠금으로 묶으면 교착은 없지만 병렬성을 잃음
### 회피와 안전 상태
- 회피: 자원을 줄 때마다 "이걸 주고 나도 안전한가?"를 검사해서 할당 여부 결정
- 필요한 사전 정보: 각 프로세스의 **최대 요구량**, 현재 할당량, 가용 자원 수
- **안전 상태**: 모든 프로세스를 끝낼 수 있는 **안전 순서** <P₁, …, Pₙ>가 존재
  - 각 Pᵢ가 앞으로 더 필요한 자원 ≤ 현재 가용 + 앞선 Pⱼ(j < i)들이 끝나며 돌려줄 자원
- 안전 → 교착 없음 보장 / 불안전 → 교착 **가능** / 교착 상태 ⊂ 불안전 상태
- 원칙: 시스템이 항상 안전 상태에 머물도록만 자원을 내줌 (요청이 와도 불안전해지면 기다리게 함)
- 구체적 알고리즘(자원 할당 그래프 알고리즘, 은행원 알고리즘)과 탐지·복구는 다음 강
