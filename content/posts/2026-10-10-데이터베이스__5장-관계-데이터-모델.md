> 데이터 모델 = 구조 + 연산 + 제약조건. 5장은 구조(릴레이션, 키)와 제약조건(개체·참조·도메인 무결성)을 다룬다. 연산은 6장.
### DBMS 역사와 인물
- 1963 찰스 바크만: GE에서 최초 상용 DBMS **IDS**, 네트워크 모델, CODASYL DBTG 표준의 기반
- 1968 IMS/DB: 최초의 계층형 DB
- 1970 **E. F. 코드**: 논문 〈A Relational Model of Data for Large Shared Data Banks〉 → 관계형 모델, 코드의 12규칙, SQL의 토대
- 1973 IBM System R / 1974 Ingres 프로젝트
- 1977 밥 마이너: 오라클 공동 창립, Oracle V1·V2 → 관계형 모델의 상업적 성공
- 1995 MySQL, 1996 PostgreSQL / 2007~ NoSQL(MongoDB, Cassandra, Couchbase)
- IBM: System/360(1964, 최초 메인프레임급), ISAM·VSAM 인덱스 파일 시스템, 관계형 DBMS 출시 등 데이터 처리 표준화 선도
- 계보: System R → SQL/DS·DB2 / Ingres → Sybase → SQL Server, Postgres → PostgreSQL(→ Redshift, Greenplum 등) / MySQL → MariaDB, Aurora
### 논리적 설계
- 개념 설계에서 만든 ER 스키마를 DBMS가 처리할 수 있는 구조로 변환. 대부분 관계 모델을 씀.
- 계층형 DB의 문제: 복잡한 관계 표현 어려움, 중복 데이터 문제 → 데이터 독립성 확보가 힘듦
- 관계 모델에서의 논리 설계 = ER의 개체·관계를 릴레이션으로 변환
  - ER 요소: 강한/약한 개체, 단일값·다중값·복합 속성, 1:1·1:N·N:M·다항 관계
  - → 릴레이션 스키마 요소: 릴레이션, 기본키, 외래키, 무결성 제약조건
- 표기: 관계(Relationship)와 구분하려고 Relation은 '릴레이션'으로 씀
### 코드의 12규칙
- 진짜 RDBMS라 부르려면 지켜야 할 기준
| 규칙 | 내용 | 현대 RDBMS |
|---|---|---|
| 0 기본 | 관계형 모델을 따르는 DBMS | 적용 |
| 1 정보 | 모든 데이터는 테이블의 행·열로 | 적용 |
| 2 보장된 접근 | 테이블 이름 + 기본키 값 + 속성 이름만으로 접근 | 대부분 적용 |
| 3 널 처리 | 누락/모르는 값은 일관되게 NULL | 부분 (DBMS마다 다름) |
| 4 동적 카탈로그 | 메타데이터도 테이블처럼 접근 | 적용 (Oracle 데이터 딕셔너리, information_schema) |
| 5 종합 서브언어 | 한 언어가 정의·질의·갱신·보안·제약 모두 지원 | 적용 (SQL) |
| 6 뷰 갱신 | 이론상 갱신 가능한 뷰는 실제로도 가능 | 부분 (조인/집계 뷰는 불가) |
| 7 고급 삽입·갱신·삭제 | 집합 단위 연산 지원 | 적용 |
| 8 물리적 독립성 | 저장 방식이 바뀌어도 응용 영향 없음 | 거의 적용 |
| 9 논리적 독립성 | 테이블 구조가 바뀌어도 응용 수정 최소 | 부분 |
| 10 무결성 독립성 | 무결성 제약은 앱이 아니라 DBMS가 관리 | 적용 (PK, FK, CHECK, UNIQUE) |
| 11 분산 독립성 | 분산 저장돼도 하나의 DB처럼 | 부분 (특히 MySQL) |
| 12 비전복 | 다른 인터페이스로 접근해도 보안·무결성 동일 | 부분 (트리거·저수준 API로 우회 가능) |
- 요약: 표현은 오직 테이블로, 접근은 일관·단순하게, 독립성과 무결성 보장
### 기본 용어
- 하나의 개체에 대한 데이터를 하나의 릴레이션(테이블)에 저장. 관계, 메타데이터도 전부 릴레이션으로.
| 용어 | 의미 | 파일 시스템 대응 |
|---|---|---|
| 릴레이션 | 개체 데이터를 담은 2차원 테이블 | 파일 |
| 속성 | 열 | 필드 |
| 투플 | 행 (n개 요소의 순서쌍) | 레코드 |
- 도메인: 한 속성이 가질 수 있는 모든 값의 집합 (CHAR(20), INT…). 입력·수정 시 적합성 판단 기준 → 도메인 무결성
- 널: 아직 모르거나 해당 값이 없음. 허용 여부를 명시해야 함
- **차수(degree) = 속성 개수**, **카디널리티(cardinality) = 투플 개수**
### 릴레이션과 DB의 구성
- 릴레이션 스키마(내포, intension): 릴레이션 이름 + 속성 이름들. 정적. 예) 고객(고객아이디, 고객이름, 나이, 등급, 직업, 적립금)
- 릴레이션 인스턴스(외연, extension): 어느 한 시점의 투플 집합. 동적.
- DB 스키마 = 릴레이션 스키마 모음 + 릴레이션 간 제약조건 / DB 인스턴스 = 릴레이션 인스턴스 모음
### 릴레이션의 특성
1. 투플의 유일성: 같은 투플이 두 개 있을 수 없음
1. 투플의 무순서: 행 순서는 의미 없음
1. 속성의 무순서: 열 순서도 의미 없음
1. 속성의 원자성: 원자 값만. 직업에 '회사원, 학생'처럼 다중 값이 들어가면 위반
### 키
- 투플을 유일하게 구별하는 속성(들)
- 특성: **유일성**(모든 투플이 서로 다른 키 값) / **최소성**(꼭 필요한 속성만으로 구성)
| 키 | 정의 | 고객 릴레이션 예 |
|---|---|---|
| 슈퍼키 | 유일성만 만족 | 고객아이디, (고객아이디, 고객이름), (고객이름, 주소) |
| 후보키 | 유일성 + 최소성 | 고객아이디, (고객이름, 주소) |
| 기본키 | 후보키 중 선택한 것 | 고객아이디 |
| 대체키 | 선택 안 된 후보키 | (고객이름, 주소) |
| 외래키 | 다른 릴레이션의 기본키를 참조 | 주문.주문고객 → 고객.고객아이디 |
- 포함 관계: 슈퍼키 ⊃ 후보키 ⊃ {기본키, 대체키}
### 외래키
- 릴레이션 간 지켜야 할 제약을 표현. 외래키를 가진 쪽 = 참조하는 릴레이션, 기본키를 가진 쪽 = 참조되는 릴레이션
- 외래키와 참조하는 기본키는 **이름은 달라도 되지만 도메인은 같아야** 함
- 한 릴레이션에 외래키가 여러 개일 수 있고, 외래키가 기본키가 될 수도 있음
  - 상담(학번, 담당교사, 상담일자, 내용): 학번 → 학생, 담당교사 → 교사. 둘을 합쳐 기본키
- 자기 릴레이션의 기본키를 참조할 수도 있음: 고객.추천고객 → 고객.고객아이디
- 외래키는 널을 가질 수 있음 (추천인 없는 고객)
### 무결성 제약조건
- 무결성 = 데이터를 결함 없이 정확·유효하게 유지하는 것. 이를 위한 규칙이 무결성 제약조건.
- **개체 무결성**: 기본키를 이루는 속성은 널 불가 + 중복 불가 (고객아이디가 NULL이거나 'apple'이 두 번이면 위반)
- **참조 무결성**: 외래키는 참조할 수 없는 값을 가질 수 없음 (주문고객 'cherry'인데 고객에 cherry가 없으면 위반). **외래키가 널인 건 위반 아님.**
- **도메인 무결성**: 모든 속성 값은 도메인에 속해야 함. 기본은 자료형, 나머지는 CHECK로 (등급 ∈ {vip, gold, silver}, 성적 < 100)
### 제약조건 구현
```sql
-- 컬럼 레벨
CREATE TABLE EMP (
  EMPNO    NUMBER(4) PRIMARY KEY,                       -- 개체 무결성
  ENAME    VARCHAR2(10),
  JOB      VARCHAR2(9),
  MGR      NUMBER(4),
  HIREDATE DATE,
  SAL      NUMBER(7,2),
  COMM     NUMBER(7,2),
  DEPTNO   NUMBER(2) NOT NULL REFERENCES DEPT(DEPTNO)   -- 참조 무결성
);
```
```sql
-- 테이블 레벨: 제약조건 이름을 명시하자
CREATE TABLE EMP (
  EMPNO    NUMBER(4),
  ENAME    VARCHAR2(10),
  JOB      VARCHAR2(9),
  MGR      NUMBER(4),
  HIREDATE DATE,
  SAL      NUMBER(7,2),
  COMM     NUMBER(7,2),
  DEPTNO   NUMBER(2) NOT NULL,
  CONSTRAINT EMP_PK      PRIMARY KEY (EMPNO),                          -- 개체
  CONSTRAINT EMP_DEPT_FK FOREIGN KEY (DEPTNO) REFERENCES DEPT(DEPTNO), -- 참조
  CONSTRAINT EMP_CK      CHECK (SAL < 10000)                           -- 도메인
);
```
- 이름을 붙여두면 위반 오류 메시지에서 어떤 제약인지 바로 보이고, 나중에 `ALTER TABLE ... DROP CONSTRAINT EMP_CK`처럼 관리하기 쉬움
