> 프로그램 전체가 메모리에 있을 필요는 없다. 필요한 페이지만 그때그때 올리는 요구 페이징으로 논리 공간을 물리 공간보다 크게 쓴다. 대가는 페이지 폴트(디스크 I/O)라서 폴트율을 수십만 분의 1 수준으로 낮춰야 하고, fork는 Copy-on-Write로 싸게 만든다.
### 왜 가상 메모리인가
- 오류 처리 코드, 잘 안 쓰는 기능, 크게 잡아둔 자료구조처럼 실제로는 거의 안 쓰이는 부분이 많음 → 일부만 메모리에 있어도 실행 가능
- 효과
  - 물리 메모리 크기의 제약에서 벗어남 (논리 주소 공간 ≫ 물리 메모리 가능)
  - 프로세스마다 메모리를 덜 쓰니 더 많이 동시에 실행 → CPU 이용률·처리량↑
  - 적재·스왑에 드는 I/O가 줆
  - 여러 프로세스가 주소 공간을 공유하기 쉬움, 프로세스 생성이 빨라짐
- 가상 메모리 = **논리 메모리와 물리 메모리의 분리**. 구현은 요구 페이징이 주류 (요구 세그멘테이션은 거의 안 씀)
### 가상 주소 공간
- 프로세스가 보는 메모리: 주소 0부터 끝까지 연속. 실제로는 MMU가 페이지 단위로 흩어진 물리 프레임(또는 디스크)에 매핑
- 스택은 최대 주소에서 아래로, 힙은 아래에서 위로 자람. 사이의 큰 **구멍**엔 물리 메모리를 주지 않고, 실제로 커질 때 비로소 할당
- 공유 라이브러리: 각 프로세스의 가상 주소 공간에 매핑되지만 물리 프레임은 하나 → 공유
- 페이지를 읽기·쓰기로 공유 매핑하면 공유 메모리, `fork()`도 페이지 공유로 빠르게
### 요구 페이징 (Demand Paging)
- 프로세스를 통째로 올리지 않고 **실제로 참조되는 페이지만** 그때 적재
- 이점: I/O 감소, 메모리 절약, 응답 빨라짐, 더 많은 사용자
- 페이지 단위로 가져오는 스와퍼 = **페이저(pager)**
- 페이지 테이블의 **유효-무효 비트**
  - v: 메모리에 있음 / i: 메모리에 없음(또는 불법 주소). 처음엔 전부 i
  - 프로그램 코드는 바꿀 필요 없이 OS와 MMU가 자동으로 처리
  - 수정 여부를 표시하는 dirty bit도 함께 씀 (교체 시 디스크에 다시 써야 하는지 판단)
### 페이지 폴트 처리
1. 페이지 참조
1. 유효 비트가 i → MMU가 **트랩** → OS
1. OS가 내부 테이블로 확인: 불법 참조면 프로세스 종료, 단지 메모리에 없는 거면 디스크 위치 확인
1. 빈 프레임을 확보하고 디스크에서 그 페이지를 읽어옴
1. 페이지 테이블 갱신 (프레임 번호 기록, v로)
1. 폴트를 일으킨 **명령어를 처음부터 다시 실행**
- **순수 요구 페이징**: 시작 시 페이지가 하나도 없음 → 첫 명령어부터 폴트, 이후 모든 페이지가 처음 쓰일 때 폴트
- 명령어 하나가 여러 페이지(명령어, 피연산자 여러 개)를 건드리면 폴트가 여러 번 날 수 있지만, **참조 지역성** 덕분에 실제론 그리 심하지 않음
- 하드웨어 요구: 유효-무효 비트가 있는 페이지 테이블, 스왑 공간이 있는 보조 저장장치(HDD, SSD, NVM)
- 하드디스크가 윙윙 도는 건 스왑 중이라는 신호, SSD로 바꾸면 체감 속도가 확 빨라지는 이유도 페이지 인/아웃이 빨라서
### 참조 지역성 예제
- 페이지 = 128워드, `int data[128][128]`이 행 단위로 저장 → 한 행 = 한 페이지
```c
int i, j;
int data[128][128];

/* 열 우선: 매 접근마다 다른 행(페이지)을 건드림 → 최악 128 × 128 = 16,384번 폴트 */
for (j = 0; j < 128; j++)
    for (i = 0; i < 128; i++)
        data[i][j] = 0;

/* 행 우선: 한 페이지를 다 쓰고 다음 페이지로 → 128번 폴트 */
for (i = 0; i < 128; i++)
    for (j = 0; j < 128; j++)
        data[i][j] = 0;
```
- (프로세스에 프레임이 128개보다 적게 주어졌다고 가정할 때) 같은 일을 하는 코드라도 접근 순서에 따라 폴트 수가 100배 넘게 차이남
### 명령어 재시작
- 폴트가 나면 프로세스는 대기 큐로, 페이지가 올라오면 준비 큐로 → 다시 CPU를 받았을 때 **폴트 직전과 똑같은 상태**에서 이어가야 함
- `C = ADD A, B`: A 가져오기 → B 가져오기 → 더하기 → C에 저장. C 저장에서 폴트가 나면 A, B를 다시 가져와 처음부터 재실행
- 까다로운 경우: 블록 이동처럼 한 명령어가 여러 위치를 바꾸고 원본·대상이 겹칠 때 → 시작 전에 모든 관련 페이지를 확인하거나, 덮어쓴 값을 임시 레지스터에 보관해 되돌릴 수 있게
### 빈 프레임 리스트
- 폴트 때 페이지를 넣을 빈 프레임들의 풀 (연결 리스트: head → 7 → 97 → 15 → 126 → … → 75)
- 내주기 전에 0으로 채움(zero-fill-on-demand) → 이전 내용 노출 방지
### 요구 페이징의 성능
- 폴트 처리 최악의 경우: 트랩 → 레지스터·상태 저장 → 폴트인지 판별 → 유효성·디스크 위치 확인 → 디스크 읽기(큐 대기, 탐색·회전 지연, 전송) → 그동안 CPU는 다른 프로세스에 → I/O 완료 인터럽트 → 다른 프로세스 상태 저장 → 인터럽트 원인 확인 → 페이지 테이블 갱신 → CPU 재할당 대기 → 상태 복원 후 명령어 재실행
- 주요 비용 세 가지: 인터럽트 처리(수백 명령어), **페이지 읽기(대부분)**, 재시작(짧음)
- 폴트율 p (0 ≤ p ≤ 1)
  - **EAT = (1 − p) × 메모리 접근 시간 + p × 페이지 폴트 서비스 시간**
- 예: 메모리 200ns, 폴트 서비스 8ms (= 8,000,000ns)
  - EAT = (1 − p) × 200 + p × 8,000,000 = **200 + 7,999,800p** (ns)
  - 1,000번에 1번 폴트(p = 0.001) → 약 8,199.8ns ≈ **8.2μs → 약 40배 느려짐**
  - 성능 저하를 10% 이내로(EAT < 220ns): 20 > 7,999,800p → **p < 0.0000025** (약 40만 번에 1번 미만)
### 스왑 공간 활용
- 같은 디스크라도 스왑 공간 I/O가 파일 시스템 I/O보다 빠름 (큰 덩어리로 할당, 파일 탐색·간접 할당이 없음)
- 방식 1(옛 BSD): 시작할 때 실행 이미지를 통째로 스왑 공간에 복사하고 이후 스왑에서 페이징
- 방식 2(Solaris, 현대 BSD): 코드 같은 페이지는 처음엔 실행 파일에서 바로 읽고, 교체할 땐 그냥 버림(다시 파일에서 읽으면 되니까)
  - 파일과 연결되지 않은 **익명 메모리**(스택, 힙)나 수정된 페이지는 스왑 공간에 써야 함
- 모바일: 스와핑 대신 파일 시스템에서 페이지를 가져오고, 부족하면 읽기 전용 페이지(코드)를 회수
- Windows는 `C:\pagefile.sys`/`swapfile.sys`로 보통 RAM 크기 정도 잡음
### Copy-on-Write
- `fork()` 직후 부모와 자식이 **같은 페이지를 공유**하다가, 누군가 그 페이지에 **쓰려는 순간** 그 페이지만 복사
  - 프로세스 1이 페이지 C를 수정 → C의 복사본이 생기고 프로세스 1의 페이지 테이블만 복사본을 가리킴, A·B는 계속 공유
  - 읽기만 한다면 복사할 이유가 없음 → fork가 훨씬 빠르고 메모리 절약 (fork 직후 exec하면 거의 복사가 없음)
- 복사할 새 프레임은 미리 0으로 채워둔 **영 페이지 풀**에서 (이전 프로세스 데이터가 새 프로세스에 보이면 안 되므로)
- `vfork()`: 부모를 멈추고 자식이 부모의 주소 공간을 COW 없이 그대로 씀 → 자식이 곧바로 `exec()`할 때만 안전하고 가장 빠름 (자식이 메모리를 바꾸면 부모에게 보임)
### 빈 프레임이 없으면?
- 프로세스 페이지들이 모든 프레임을 차지하고 있고, 커널·I/O 버퍼도 메모리가 필요
- **페이지 교체**: 지금 잘 안 쓰는 페이지(희생자)를 골라 내보내고 그 자리에 새 페이지
- 목표는 **폴트 수를 최소화**하는 희생자 선택 알고리즘 → 다음 강
