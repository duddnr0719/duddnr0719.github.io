> 체크섬 → ACK/NAK → 순서 번호 → 타이머 순으로 하나씩 붙이면 rdt 3.0이 되고, stop-and-wait의 낮은 이용률은 파이프라이닝(GBN, SR)으로 푼다.
### rdt 기본 설정
- 목표: 비신뢰 채널 위에서 상위 계층에 신뢰 채널처럼 보이게 하기. 복잡도는 채널 특성(오염, 손실, 순서 뒤바뀜)에 좌우.
- 송신자·수신자는 서로의 상태를 모름 → 메시지로 주고받아야 앎. 그래서 프로토콜이 필요.
- 인터페이스
  - `rdt_send()`: 상위 계층이 호출해 데이터 전송 요청
  - `udt_send()`: rdt가 비신뢰 채널로 패킷 전송
  - `rdt_rcv()`: 패킷이 수신 측에 도착하면 호출
  - `deliver_data()`: rdt가 상위로 데이터 전달
- 단방향 데이터 전송만 고려(제어 패킷은 양방향), 동작은 FSM으로 표현: `이벤트 / 행동`
### rdt 1.0: 완전 신뢰 채널
- 비트 오류·손실 없음 → 송신자는 그냥 보내고(`make_pkt` → `udt_send`), 수신자는 그냥 받음(`extract` → `deliver_data`). 피드백 불필요.
### rdt 2.0: 비트 오류 채널
- 체크섬으로 오류 검출 + 수신자 피드백(ACK = 정상, NAK = 오류) + NAK면 재전송
- stop-and-wait: 보내고 응답 올 때까지 대기
- 송신자 FSM: `Wait for call from above` → 전송 → `Wait for ACK or NAK` (NAK면 재전송, ACK면 복귀)
- 수신자 FSM: corrupt면 `NAK`, 아니면 `extract` → `deliver_data` → `ACK`
- 치명적 결함: ACK/NAK 자체가 깨질 수 있음 → 송신자는 상황을 모르고, 그냥 재전송하면 **중복 패킷**
- 해결: ACK/NAK에도 체크섬, 깨지면 현재 패킷 재전송, 패킷에 **순서 번호** 추가, 수신자는 중복이면 버림
### rdt 2.1: ACK/NAK 오류 대응
- stop-and-wait이라 순서 번호는 0, 1이면 충분
- 상태 수가 2.0의 2배: 송신자는 "지금 보내는 게 0인지 1인지", 수신자는 "기다리는 게 0인지 1인지" 기억
- 송신자: ACK/NAK가 깨졌거나 NAK면 재전송
- 수신자: 정상이고 기다리던 번호면 전달 + ACK, 깨졌으면 NAK, 정상인데 이전 번호(중복)면 버리고 ACK만 다시 보냄
- 수신자는 자기가 보낸 ACK/NAK가 제대로 갔는지 모름
### rdt 2.2: NAK 없는 버전
- NAK 대신 "마지막으로 제대로 받은 패킷의 ACK"를 보냄 → ACK에 순서 번호 명시 (`ACK0`, `ACK1`)
- 송신자는 **중복 ACK**를 받으면 NAK처럼 현재 패킷 재전송
- 신뢰성은 2.1과 동일, 신호가 하나라 단순
### rdt 3.0: 오류 + 손실 채널
- 데이터나 ACK가 아예 사라질 수 있음 → 체크섬·순서 번호·재전송만으론 부족
- 해결: **카운트다운 타이머**. 보낼 때 `start_timer`, 정상 ACK 오면 `stop_timer`, 시간 안에 ACK 없으면 재전송
- 손실이 아니라 지연된 거라면 중복이 생기지만 순서 번호로 처리
- 깨진 ACK나 엉뚱한 번호의 ACK는 무시하고 타임아웃까지 대기
- 시나리오
  - (a) 손실 없음
  - (b) 패킷 손실 → 타임아웃 → 재전송
  - (c) ACK 손실 → 타임아웃 → 재전송 → 수신자가 중복 감지, ACK 재전송
  - (d) 조기 타임아웃/지연된 ACK → 중복 재전송 → 수신자는 버리고 ACK, 늦게 온 중복 ACK는 송신자가 무시
### rdt 3.0 성능
- 예: R = 1Gbps, RTT = 30ms, L = 8000비트(1KB)
  - 전송 시간 L/R = 8μs = 0.008ms
  - 수신자 도착 t = RTT/2 + L/R = 15.008ms
  - 송신자 ACK 도착 t = RTT + L/R = 30.008ms
- **U_sender = (L/R) / (RTT + L/R) = 0.008 / 30.008 ≈ 0.00027**
- 30ms 동안 1KB만 보냄 → 1Gbps 링크에서 처리율 약 267kbps. 프로토콜이 물리 자원을 못 씀.
### 파이프라이닝
- ACK를 안 기다리고 여러 패킷을 연속 전송
- 필요: 순서 번호 범위 확대(전송 중 패킷마다 고유 번호), 송수신 버퍼
- 3개 파이프라이닝: U = 3(L/R) / (RTT + L/R) = 0.024 / 30.008 ≈ 0.00081 → 3배
- 대표 두 가지: GBN, SR
### Go-Back-N
- 송신자
  - k비트 순서 번호, 크기 N 윈도우(ACK 안 받은 패킷 최대 N개), 슬라이딩 윈도우
  - `ACK(n)` = **누적 ACK** (n까지 전부 받음)
  - 타이머는 가장 오래된 미확인 패킷 하나만
  - `timeout(n)`: n 이후 윈도우 안의 패킷 **전부** 재전송
- 수신자
  - 순서대로 받은 것 중 가장 큰 번호로 ACK (중복 ACK 생길 수 있음), `rcv_base`만 기억
  - 순서 어긋난 패킷은 **버퍼링 없이 버리고** 마지막 순차 ACK 재전송
- 예(N=4): pkt2 손실 → pkt3, 4, 5는 버려지고 ack1 반복 → pkt2 타임아웃 → pkt2~5 전부 재전송
### Selective Repeat
- 수신자: 정상 수신한 패킷마다 **개별 ACK**, 순서 어긋난 건 **버퍼링** 후 빈 칸이 채워지면 한 번에 상위 전달
- 송신자: 미확인 패킷마다 **개별 타이머**, 만료된 패킷만 재전송
- 송신자 이벤트
  - 상위에서 데이터: 윈도우에 다음 번호 자리가 있으면 전송
  - `timeout(n)`: n만 재전송, 타이머 재시작
  - `ACK(n)` ∈ [sendbase, sendbase+N-1]: n을 받은 것으로 표시, n이 가장 작은 번호면 윈도우를 다음 미확인 번호로 이동
- 수신자 이벤트
  - pkt n ∈ [rcvbase, rcvbase+N-1]: ACK(n). 비순차면 버퍼, 순차면 버퍼에 쌓인 것까지 함께 전달하고 윈도우 이동
  - pkt n ∈ [rcvbase-N, rcvbase-1]: 이미 받은 거라도 ACK(n) 다시 보냄
  - 그 외: 무시
- 예(N=4): pkt2 손실 → pkt3, 4, 5 버퍼링 + ack3, 4, 5 → pkt2만 재전송 → 2~5 한 번에 전달
### SR 딜레마
- 순서 번호 0~3, 윈도우 3일 때
  - (a) ACK 정상 → 수신 윈도우가 3, 0, 1로 이동 → 새 pkt0 수락 (정상)
  - (b) ACK 전부 손실 → 송신자는 옛 pkt0 재전송 → 수신자는 이걸 새 pkt0으로 착각해 수락
  - 수신자 입장에선 (a)와 (b)가 구분 안 됨
- 조건: **윈도우 크기 ≤ 순서 번호 공간 / 2**
### rdt 버전 정리
| 버전 | 채널 가정 | 피드백 | 순서 번호 | 재전송 트리거 | 핵심 |
|---|---|---|---|---|---|
| 1.0 | 완전 신뢰 | 없음 | X | 없음 | 가장 단순 |
| 2.0 | 비트 오류 | ACK/NAK | X | NAK | ACK/NAK 오염 시 모호, 중복 |
| 2.1 | 비트 오류 | ACK/NAK | 0/1 | NAK·깨진 피드백 | 순서 번호로 중복 제거, 상태 2배 |
| 2.2 | 비트 오류 | ACK만 | 0/1 | 중복 ACK | NAK 제거 |
| 3.0 | 오류 + 손실 | ACK | 0/1 | 타임아웃 | 타이머 도입, 이용률 매우 낮음 |
