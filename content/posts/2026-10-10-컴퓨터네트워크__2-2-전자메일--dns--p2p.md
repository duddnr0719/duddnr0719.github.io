> SMTP는 메일을 서버까지 '밀어넣고', DNS는 계층형 분산 DB로 이름을 IP로 바꾸며, P2P는 피어가 업로드를 나눠 맡아 N이 커져도 분배 시간이 잘 안 늘어난다.
### 전자메일 구성
- 3요소: 사용자 에이전트(UA, 메일 리더: Outlook, Thunderbird), 메일 서버, SMTP
- 메일 서버: 받은 메일을 담는 메일박스 + 보낼 메일을 담는 메시지 큐. 서버 간 SMTP에서 보내는 쪽이 클라이언트, 받는 쪽이 서버.
### SMTP (RFC 5321)
- TCP 25번 포트로 보내는 서버 → 받는 서버에 **직접** 전송
- 3단계: 핸드셰이킹 → 메시지 전송 → 종료. HTTP처럼 명령(ASCII)/응답(상태 코드 + 문장)
- 앨리스 → 밥 흐름
  1. 앨리스 UA로 작성 → 앨리스 메일 서버의 메시지 큐
  1. 앨리스 서버(SMTP 클라이언트)가 밥 서버로 TCP 연결 → 메시지 전송
  1. 밥 서버가 밥 메일박스에 저장 → 밥 UA가 읽음
- 상호동작 예
```
S: 220 hamburger.edu
C: HELO crepes.fr
S: 250 Hello crepes.fr, pleased to meet you
C: MAIL FROM: <alice@crepes.fr>
S: 250 alice@crepes.fr... Sender ok
C: RCPT TO: <bob@hamburger.edu>
S: 250 bob@hamburger.edu ... Recipient ok
C: DATA
S: 354 Enter mail, end with "." on a line by itself
C: Do you like ketchup?
C: How about pickles?
C: .
S: 250 Message accepted for delivery
C: QUIT
S: 221 hamburger.edu closing connection
```
- 특징: 지속 연결, 헤더·바디 모두 7비트 ASCII, 메시지 끝 = `CRLF.CRLF`
- HTTP vs SMTP: HTTP는 pull, SMTP는 push. 둘 다 ASCII 명령/응답 + 상태 코드. HTTP는 객체마다 응답 메시지, SMTP는 모든 객체를 한 메시지로.
- 메시지 포맷(RFC 2822): 헤더(`To:`, `From:`, `Subject:`) + 빈 줄 + 바디. 헤더는 SMTP 명령(`MAIL FROM`, `RCPT TO`)과 다른 것.
### 메일 접속 프로토콜
- SMTP는 수신자 서버까지만 → 서버에서 꺼내오는 프로토콜이 따로 필요
- IMAP(RFC 3501): 서버에 둔 메시지 조회·삭제·폴더 관리
- HTTP: SMTP(송신)·IMAP(수신) 위에 웹 인터페이스 제공 (Gmail, Hotmail 등)
### DNS 개요
- 호스트 식별자: IP 주소(32비트, 라우팅용) vs 호스트 네임(`www.sch.ac.kr`, 사람용)
- DNS = 호스트 네임 → IP 변환 디렉터리 서비스. 계층 구조 DNS 서버들로 만든 분산 DB이자, 그걸 질의하는 애플리케이션 계층 프로토콜.
- 서비스
  - 이름 → IP 변환
  - 호스트 에일리어싱: 간단한 별칭(`enterprise.com`) → 정식 이름(`relay1.west-coast.enterprise.com`)
  - 메일 서버 에일리어싱
  - 부하 분산: 정식 이름 하나에 IP 여러 개(복제 웹 서버)
- 중앙 집중으로 안 하는 이유: 단일 장애점, 트래픽 양, 먼 거리 지연, 유지관리, 확장성 X (Comcast 하루 6000억, Akamai 2.2조 질의)
- 특성: 수십억 레코드, 하루 수 조 질의, 읽기 위주, ms 단위 성능, 수백만 기관이 나눠 관리, 신뢰성·보안 중요
### DNS 계층
- 루트 → TLD(.com, .org, .edu, .kr …) → 책임(authoritative) 서버
- `www.amazon.com` 조회: 루트에 .com 서버 위치 → .com TLD에 amazon.com 서버 위치 → amazon.com 책임 서버에 IP 질의
- 루트 네임 서버: 아무도 못 푼 이름의 마지막 접촉점. 없으면 인터넷이 동작 안 함. 논리적으로 13개, 각각 다수 복제. ICANN이 관리, DNSSEC으로 인증·무결성 제공.
- TLD 서버: 일반 TLD + 국가 TLD 담당 (Network Solutions가 .com/.net, Educause가 .edu)
- 책임 DNS 서버: 기관의 웹·메일 서버 이름 ↔ IP 매핑. 기관이나 서비스 제공자가 운영.
- 로컬 DNS 서버: 호스트 질의가 가장 먼저 가는 곳. 캐시에 있으면 바로 응답(최신 아닐 수 있음), 없으면 계층에 전달. ISP마다 운영하며 엄밀히는 DNS 계층에 속하지 않음. (`ip addr`, `ifconfig`, `ipconfig`로 확인)
### 반복적 vs 재귀적 질의
- 예: `engineering.nyu.edu`가 `gaia.cs.umass.edu` 조회
- 반복적(iterated): 로컬 서버가 루트 → TLD → 책임 서버에 차례로 묻고, 각 서버는 "나는 모르니 이 서버에 물어봐"라고 다음 주소만 알려줌 (총 8단계)
- 재귀적(recursive): 질의받은 서버가 대신 다음 서버에 물어 끝까지 해결 → 상위 계층 서버에 부담이 큼
### DNS 캐싱
- 응답을 받은 네임 서버는 저장해두고 바로 응답 → 응답 시간 개선. TTL이 지나면 삭제.
- 보통 로컬 서버에 TLD 주소가 캐시되어 루트는 자주 안 감.
- IP가 바뀌면 캐시가 낡을 수 있음 → best-effort 변환.
### DNS 레코드와 메시지
- RR 형식: `(name, value, type, ttl)`
  - A: name=호스트 이름, value=IP
  - NS: name=도메인(foo.com), value=그 도메인 책임 서버의 호스트 이름
  - CNAME: name=별칭(`www.ibm.com`), value=정식 이름(`servereast.backup2.ibm.com`)
  - MX: name=별칭, value=그 메일 서버의 정식 이름
- 메시지: 질의·응답 같은 포맷
  - 헤더: 16비트 식별자(응답도 같은 값), 플래그(질의/응답, 재귀 요청, 재귀 가능, 책임 서버 응답)
  - 개수 필드: questions / answer RRs / authority RRs / additional RRs
  - 본문: questions(이름·타입), answers(응답 RR), authority(책임 서버 레코드), additional info
- 레코드 등록 예(networkutopia.com)
  1. 등록기관(Network Solutions)에 주/부 책임 서버 이름·IP 제공 → .com TLD에 `(networkutopia.com, dns1.networkutopia.com, NS)`, `(dns1.networkutopia.com, 212.212.212.1, A)` 삽입
  1. 자기 책임 서버에 `www` → A 레코드, `mail` → MX 레코드 등록
### P2P 파일 분배
- 상시 서버 없음, 피어가 요청과 제공을 동시에 → 자율 확장성. 대신 간헐적 접속·IP 변경으로 관리 복잡. (BitTorrent, KanKan, Skype)
- 문제: 크기 F 파일을 서버 1대가 N개 피어에 분배. us=서버 업로드, ui=피어 업로드, di=피어 다운로드, dmin=최저 다운로드 속도
- 클라이언트-서버: 서버가 N개 복사본을 직접 보냄
  - **D_cs ≥ max{ NF/us, F/dmin }** → N에 비례해 선형 증가
- P2P: 서버는 1개만 보내면 되고, 전체 업로드 용량 = us + Σui
  - **D_p2p ≥ max{ F/us, F/dmin, NF/(us + Σui) }** → N이 늘면 업로드 용량도 같이 늘어남
- 예: F/u = 1시간, us = 10u, dmin ≥ us일 때 N이 커지면 C-S는 직선으로 증가, P2P는 1시간 근처에서 완만
### BitTorrent
- 파일을 256KB 청크로 분할. 트래커 = 참여 피어 목록 관리, 토렌트 = 청크를 주고받는 피어 집합.
- 가입: 처음엔 청크 0 → 트래커에서 목록 받아 일부와 연결(이웃 피어) → 받으면서 동시에 업로드 → 완성 후 떠나거나(이기적) 남거나(이타적)
- 청크 가져오기: 이웃에게 주기적으로 청크 목록 요청 → 가장 희귀한 것부터(rarest first)
- 청크 보내기(tit-for-tat): 나에게 가장 빨리 보내주는 상위 4명에게 전송(10초마다 재선정) + 30초마다 무작위 1명 추가(optimistically unchoke) → 새 피어도 상위 4명에 들 기회
- 결과: 업로드를 빨리 해줄수록 좋은 파트너를 얻고 다운로드도 빨라짐
