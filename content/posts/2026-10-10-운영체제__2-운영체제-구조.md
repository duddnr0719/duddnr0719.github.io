> 프로그램은 API(라이브러리)를 통해 시스템 호출로 커널 서비스를 쓴다. OS를 어떻게 쪼개느냐에 따라 단순·모놀리식·계층·마이크로커널·모듈 구조가 있고, 실제 OS는 대부분 하이브리드.
### 운영체제 서비스
- OS = 프로그램 실행 환경, 컴퓨터를 '쓸 수 있게' 해주는 모든 것
- 사용자를 위한 기능
  - 사용자 인터페이스: CLI, GUI, 터치
  - 프로그램 실행: 메모리에 올리고 실행하고 끝나면 정리
  - I/O 처리: 파일 읽기·쓰기, 프린터 출력 등을 OS가 중간에서 처리
  - 파일 시스템 조작: 생성·삭제·검색·권한 (탐색기, ls, cp, rm)
  - 통신: 프로세스 간 데이터 교환 (공유 메모리 / 메시지 패싱)
  - 오류 감지: CPU·메모리·I/O·사용자 프로그램 어디서든 → 감지하고 적절히 대응, 디버깅 도구 지원
- 시스템 효율을 위한 기능
  - 자원 할당: CPU 사이클, 메모리, 저장소, I/O 장치 배분
  - 사용 기록(accounting): 사용자별 자원 사용량 추적 (과금, 통계)
  - 보호(모든 자원 접근 통제)와 보안(사용자 인증, 외부 침입 방어)
- 계층: 사용자·시스템 프로그램 → UI(GUI, batch, CLI) → **시스템 호출** → 서비스 → 하드웨어
### 사용자 인터페이스
- 자동차의 핸들·브레이크·계기판처럼, 사용자가 커널을 조작하는 접점
- CLI: 명령어를 타이핑. 커널에 있거나 별도 시스템 프로그램(셸: bash, zsh, fish, PowerShell)
  - 셸 내장 명령(cd, echo) vs 외부 프로그램(/bin/ls). 외부 프로그램 방식이면 실행 파일만 추가해서 셸 수정 없이 명령 확장 가능
- GUI: 데스크톱 메타포(바탕화면, 폴더, 휴지통), 마우스·키보드·모니터
### 시스템 호출
- OS·커널이 제공하는 서비스의 프로그래밍 인터페이스. 주로 C/C++로 작성
- 직접 호출보다 **API**로 사용: Win32 API, POSIX API(UNIX, Linux, macOS), Java API
- 파일 복사 같은 간단한 프로그램도 시스템 호출 수십 번: 파일명 입력받기(화면 출력, 입력) → 입력 파일 열기(없으면 중단) → 출력 파일 생성(있으면 중단) → 읽기/쓰기 반복 → 닫기 → 완료 메시지 → 정상 종료
- API 예: `ssize_t read(int fd, void *buf, size_t count)` (`<unistd.h>`) — 읽은 바이트 수 반환, EOF면 0, 오류면 −1
- `printf("Greetings")` → 표준 C 라이브러리 → 커널 모드에서 `write()` 시스템 호출. fread 내부를 몰라도 쓰듯이, 호출자는 API 규칙만 알면 됨
- 구현: 시스템 호출마다 **번호**가 있고, 커널은 번호로 인덱싱된 테이블에서 해당 함수를 찾아 실행 후 결과 반환. 컴파일러의 런타임 라이브러리가 중간을 관리
- 매개변수 전달 3가지 (예: `fopen("text.txt", "r")` → 번호 하나로는 정보가 부족)
  1. 레지스터: 가장 빠르지만 레지스터 개수보다 많으면 불가
  1. 메모리 블록(테이블): 매개변수를 메모리에 두고 그 주소를 레지스터로 전달
  1. 스택: 프로그램이 push, OS가 pop
  - 블록·스택 방식은 개수·길이 제한이 없음
### 시스템 호출의 유형
| 유형 | 내용 | Windows | UNIX |
|---|---|---|---|
| 프로세스 제어 | 생성/종료, end/abort, load/execute, 속성, 대기·시그널, 메모리 할당/해제, 덤프·디버거, 잠금 | CreateProcess, ExitProcess, WaitForSingleObject | fork, exit, wait |
| 파일 관리 | create/delete, open/close, read/write/seek, 속성 | CreateFile, ReadFile, WriteFile, CloseHandle | open, read, write, close |
| 장치 관리 | request/release, read/write/seek, 속성, attach/detach | SetConsoleMode, ReadConsole, WriteConsole | ioctl, read, write |
| 정보 유지 | 시간·날짜, 시스템 데이터, 속성 조회·설정 | GetCurrentProcessID, SetTimer, Sleep | getpid, alarm, sleep |
| 통신 | 연결 생성·삭제, 메시지 송수신, 공유 메모리, 원격 장치 | CreatePipe, CreateFileMapping, MapViewOfFile | pipe, shmget, mmap |
| 보호 | 접근 제어, 권한 조회·설정 | SetFileSecurity, InitializeSecurityDescriptor | chmod, umask, chown |
### 프로그램 실행 모델
- MS-DOS(싱글태스킹): 부팅하면 셸(command.com). 별도 프로세스 개념 없이 프로그램이 커널 빼고 메모리를 덮어씀 → 끝나면 셸을 다시 로드
- FreeBSD(멀티태스킹): 로그인 → 셸 실행 → `fork()`로 새 프로세스 생성 → `exec()`으로 프로그램 로드 → 셸은 대기하거나 백그라운드(`&`) 실행 → 종료 시 `exit(0)` 정상, `exit(N)` 오류 코드 N
- Arduino: OS·CLI 없이 부트로더가 스케치를 바로 불러와 실행
### 시스템 프로그램
- 개발·실행을 편하게 해주는 프로그램들. 사용자가 보는 'OS'의 모습은 사실 커널이 아니라 이것
  - 파일 관리(탐색기, ls, cp), 상태 정보(작업 관리자, 로깅, Windows 레지스트리)
  - 파일 편집(vim, nano, grep, sed, find), 언어 지원(컴파일러, 어셈블러, 디버거, 인터프리터)
  - 로딩·실행(로더, 링커), 통신(웹, 메일, 원격 로그인, 파일 전송)
  - 백그라운드 서비스: 부팅 시 자동 시작, 사용자 공간에서 실행 (Windows = 서비스, Linux = **데몬**). 디스크 검사, 스케줄링, 로깅, 인쇄
- 응용 프로그램(크롬, 한글, 게임)은 보통 OS의 일부로 보지 않음
### 설계와 구현
- 정답은 없고 목표·사양부터
  - 사용자 목표: 편리, 배우기 쉬움, 신뢰, 안전, 빠름
  - 시스템 목표: 설계·구현·유지보수 쉬움, 유연, 신뢰, 오류 없음, 효율적
- **정책(policy)과 메커니즘(mechanism)의 분리**
  - 메커니즘 = 어떻게 (타이머 인터럽트), 정책 = 무엇을 (CPU 시간을 얼마씩 배분할지)
  - 분리하면 메커니즘은 그대로 두고 정책만 바꿔 동작을 바꿀 수 있음 (if문 하나 고치기 vs 구조 바꾸기)
- 언어: 어셈블리 → Algol, PL/1 → C/C++. 실제로는 혼합 (부팅·인터럽트는 어셈블리, 커널 본체는 C, 유틸리티는 C++·Python·셸). 고급 언어는 포팅이 쉽고, 속도 손해는 컴파일러 최적화로 거의 해결
### 운영체제 구조
| 구조 | 특징 | 장점 | 단점 |
|---|---|---|---|
| 단순 (MS-DOS) | 최소 메모리에 최대 기능, 모듈·레벨 구분 없음 | 작음 | 구조라 부르기 어려움, 보호 없음 |
| 모놀리식 (전통 UNIX) | 시스템 호출 인터페이스~하드웨어 사이 전부(파일시스템, 스케줄링, 메모리)를 커널 한 덩어리에 | 내부 호출이라 빠름 | 하나 고장나면 전체 영향, 유지보수 어려움 |
| 계층 | 계층 0 = 하드웨어 … 계층 N = UI, 바로 아래 계층만 사용 | 디버깅·검증 쉬움 | 계층 나누기 어렵고, 여러 계층을 거쳐 느림 |
| 마이크로커널 (Mach) | 최소 기능(IPC, 기본 메모리 관리, 스케줄링)만 커널에, 파일시스템·드라이버는 사용자 공간. 메시지 패싱으로 통신 | 확장·포팅 쉬움, 안정성·보안 | 사용자↔커널 메시지 전달 오버헤드 |
| 모듈 (LKM) | 핵심 구성요소가 독립 모듈, 필요할 때 동적 로드 (USB 꽂으면 드라이버 로드) | 계층보다 유연 (모듈끼리 직접 호출) | — |
- Solaris: 코어 커널 + 스케줄링 클래스, 파일시스템, 로더블 시스템 호출, 실행 형식, STREAMS, 장치·버스 드라이버 모듈
- **하이브리드**: 현실 OS는 섞어 씀
  - Linux: 모놀리식 + 동적 모듈
  - Windows: 모놀리식 기반 + 마이크로커널 요소 (서브시스템 personality)
  - macOS: Aqua GUI, Cocoa 등 위에 커널 환경 = Mach + BSD UNIX + I/O Kit + 커널 확장(kext)
  - iOS: macOS 기반, ARM. Cocoa Touch → Media Services → Core Services → Core OS
  - Android: 수정된 Linux 커널(프로세스, 메모리, 드라이버, 전력) → 라이브러리(SQLite, OpenGL, WebKit, libc) + Android Runtime(Core Libraries, Dalvik → ART) → Application Framework → Apps. Java/Kotlin → 바이트코드 → Dalvik/ART 실행 파일
### 디버깅과 성능 튜닝
- 오류 정보를 로그 파일에 기록
  - 앱 크래시 → **코어 덤프** (프로세스 메모리 스냅샷, 세그폴트 때 core 파일)
  - OS 크래시 → **크래시 덤프** (커널 메모리, 블루스크린 후 MEMORY.DMP)
- 추적(strace, dtrace), 프로파일링(perf, gprof)
- Kernighan의 법칙: 디버깅은 코딩보다 2배 어렵다 → 최대한 똑똑하게 짠 코드는 디버깅할 수 없다 → **단순하게 짜라**
- 성능 튜닝 = 병목 찾아 제거. top, htop, nvtop, 작업 관리자
- DTrace: 실행 중인 시스템에서도 쓰는 추적 도구. 코드 지점에 프로브를 걸어 데이터 수집
```d
sched:::on-cpu
uid == 101
{
    self->ts = timestamp;
}

sched:::off-cpu
self->ts
{
    @time[execname] = sum(timestamp - self->ts);
    self->ts = 0;
}
```
- UID 101 사용자의 프로세스별 CPU 실행 시간(ns)을 몇 줄로 집계
### 생성과 부팅
- SYSGEN: 하드웨어 정보를 모아 그 시스템에 맞는 커널 생성 (Linux `make menuconfig` → `make`)
- 부팅
  1. 전원 ON → CPU가 정해진 주소의 펌웨어(ROM/EEPROM) 코드 실행
  1. 1단계: ROM 코드가 디스크의 **부트 블록** 로드
  1. 2단계: 부트 블록이 부트로더(GRUB 등) 로드. GRUB은 여러 OS·커널 선택 화면(듀얼 부팅)
  1. 부트로더가 커널을 메모리에 로드 → OS 실행 시작
