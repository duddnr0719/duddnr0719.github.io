> TCP는 손실을 혼잡 신호로 보고 AIMD(슬로 스타트 → 혼잡 회피 → 손실 시 감소)로 cwnd를 조절한다. 요즘은 CUBIC, 지연 기반(BBR), ECN, 그리고 UDP 위의 QUIC까지 나왔다.
### 혼잡이란
- 너무 많은 출발지가 너무 많은 데이터를 너무 빨리 보내 네트워크가 감당 못 하는 상태
- 흐름 제어(송신자 1이 수신자 1에게 너무 빠름)와 다름. 혼잡 제어는 송신자들 전체를 억제하는 것.
- 결과: 패킷 손실(라우터 버퍼 오버플로), 긴 지연(버퍼 큐잉)
### 혼잡의 원인과 비용
- 시나리오 1: 송수신 2쌍, 라우터 버퍼 무한, 재전송 없음
  - 연결당 최대 처리량 R/2, λin이 R/2에 가까워질수록 지연이 급증
- 시나리오 2: 버퍼 유한, 재전송 있음. λin = 원래 데이터, λ'in = 원래 + 재전송 데이터
  - 2.1 버퍼가 빌 때만 보낸다면(이상적): 손실 없음, λ'in = λin
  - 2.2 손실된 것만 재전송: R/2로 보낼 때 일부가 재전송이라 실제 처리량은 R/2 미만 → 재전송으로 용량 낭비
  - 2.3 현실: 너무 일찍 타임아웃되어 손실 안 된 패킷까지 복사본 전송
  - 비용: 손실 재전송, 큰 지연으로 인한 불필요한 재전송, 라우터가 쓸데없는 복사본에 대역폭 사용
- 시나리오 3: 송신자 4개, 멀티홉 경로
  - λ'in이 커지면 한 흐름이 버퍼를 차지해 다른 흐름 패킷이 버려지고, 처리량이 결국 0으로 감
  - 추가 비용: 중간에서 버려진 패킷을 거기까지 보내느라 쓴 상류 라우터의 전송 용량·버퍼가 낭비
- 정리: 처리량은 용량을 못 넘음, 한계에 다가갈수록 지연 증가, 손실·재전송·중복이 처리량을 깎음, 하류 손실이 상류 자원을 낭비
### 혼잡 제어 접근법
- 종단 간: 네트워크의 명시적 피드백 없이 손실·지연으로 혼잡 추정 → **TCP 방식**
- 네트워크 지원: 라우터가 혼잡 수준이나 명시적 송신률을 알려줌 (TCP ECN, ATM, DECbit)
### AIMD
- 손실 날 때까지 올리고, 손실 나면 내림 → 톱니 모양으로 대역폭 탐색
- 가법적 증가: 매 RTT마다 cwnd를 1 MSS씩
- 승법적 감소
  - 중복 ACK 3개: 반으로 (TCP Reno)
  - 타임아웃: 1 MSS로 (TCP Tahoe)
- 분산·비동기 알고리즘이면서 안정적으로 동작
### cwnd
- 미확인 데이터 양을 제한: **LastByteSent − LastByteAcked ≤ cwnd**
- 전송률 ≈ **cwnd / RTT** (bytes/sec). cwnd는 감지한 혼잡에 따라 동적으로 바뀜.
### 슬로 스타트
- 연결 시작 시 cwnd = 1 MSS, 첫 손실까지 **지수적** 증가
- ACK 하나마다 +1 MSS → 결과적으로 매 RTT마다 2배 (1 → 2 → 4 → 8)
- 시작은 느리지만 금방 빨라짐
### 손실 감지와 반응
- 타임아웃: 심한 혼잡으로 보고 cwnd = 1 MSS → 임계치(ssthresh)까지 지수 증가 → 이후 혼잡 회피(선형 증가)
- 중복 ACK 3개(Reno): 일부 세그먼트는 전달되고 있다는 뜻 → cwnd를 반으로 줄이고 선형 증가
- 혼잡 회피 선형 증가: ACK마다 **MSS × (MSS / cwnd)**. cwnd = 10 MSS면 ACK마다 1/10 MSS, 10개 다 받아야 1 MSS
- Tahoe는 둘을 구분 안 하고 항상 cwnd = 1 MSS
### 슬로 스타트 → 혼잡 회피 전환
- cwnd가 ssthresh에 도달하면 지수 → 선형
- 손실이 나면 ssthresh = 손실 직전 cwnd / 2
- 예: 초기 ssthresh = 8 MSS → cwnd 8에서 선형 전환 → cwnd 12에서 중복 ACK 3개 → ssthresh = 6. Tahoe는 1부터, Reno는 ssthresh + 3 = 9에서 선형 증가
### TCP 혼잡 제어 FSM
| 상태 | 새 ACK | 중복 ACK 3개 | 타임아웃 |
|---|---|---|---|
| 슬로 스타트 (초기 cwnd=1 MSS, ssthresh=64KB) | cwnd += MSS, cwnd ≥ ssthresh면 혼잡 회피로 | ssthresh = cwnd/2, cwnd = ssthresh + 3, 재전송 → 빠른 회복 | ssthresh = cwnd/2, cwnd = 1 MSS, 재전송 |
| 혼잡 회피 | cwnd += MSS·(MSS/cwnd) | 위와 동일 → 빠른 회복 | 위와 동일 → 슬로 스타트 |
| 빠른 회복 | cwnd = ssthresh → 혼잡 회피 | (중복 ACK마다 cwnd += MSS) | 위와 동일 → 슬로 스타트 |
### TCP CUBIC
- 병목 링크 상태는 크게 안 변한다고 가정. Wmax = 손실이 났던 윈도 크기.
- 손실 시 반으로 줄인 뒤, 처음엔 Wmax 쪽으로 빠르게, 가까워지면 천천히, 넘어서면 다시 빠르게 탐색
- **W(t) = C(t − K)³ + Wmax** (K = Wmax에 다시 도달하는 시점). K에서 멀수록 크게, 가까울수록 작게 증가.
- 리눅스 기본값, 많은 웹 서버가 사용
### 지연 기반 혼잡 제어
- 기존 TCP(classic, CUBIC)는 병목 링크에서 손실 날 때까지 속도를 올림. 하지만 병목이 꽉 차면 더 보내도 처리량은 안 늘고 RTT(큐잉)만 늘어남.
- 목표: 파이프를 "딱 꽉 차게, 그 이상은 아니게"
- RTTmin = 혼잡 없을 때 RTT, 기대 처리량 = cwnd / RTTmin
  - 측정 처리량 ≈ 기대 처리량 → 안 막힘 → cwnd 선형 증가
  - 측정 처리량 ≪ 기대 처리량 → 막힘 → cwnd 선형 감소
- Google BBR: 손실 없이 지연은 낮추고 처리량은 최대화. 구글 백본에 적용 후 YouTube 처리량 평균 4%, 일부 국가 14% 이상 향상. Ubuntu 22.04에서도 켤 수 있음.
### ECN
- 네트워크 지원 방식. 라우터가 IP 헤더(ToS 필드) 2비트로 혼잡 표시 → 목적지까지 전달
- 수신자가 ACK의 TCP 헤더에 **ECE** 비트 세팅 → 송신자가 cwnd 줄이고 **CWR** 비트로 응답
### TCP 공평성
- K개 연결이 R bps 병목을 공유할 때 각자 평균 R/K에 가까우면 공평
- 두 연결 그래프로 보면: 가법적 증가는 기울기 1로 같이 오르고, 손실 시 둘 다 반으로 줄어듦 → 반복하면 "동등 공유선"과 "전체 이용선"의 교차점 근처로 수렴
- 조건: 연결 수가 고정, RTT가 비슷할 때
- UDP: 멀티미디어는 혼잡 제어를 피하려고 UDP로 일정 속도 전송 → TCP 흐름을 압박
- 병렬 연결: 링크 R에 기존 연결 9개일 때 새 앱이 1개 쓰면 R/10, 11개 쓰면 R/2 이상 차지 → 불공평
### 트랜스포트 기능 확장과 QUIC
- 40년간 TCP/UDP를 썼지만 새로운 환경이 생김: 긴 대용량 파이프(전송 중 패킷이 많아 손실 시 파이프라인 멈춤), 무선(손실을 혼잡으로 오인), 고지연 링크, 지연에 민감한 데이터센터, 저우선순위 배경 트래픽
- 해결: 트랜스포트 기능을 UDP 위 애플리케이션 계층으로 옮김 → HTTP/3의 QUIC
- QUIC: UDP 위 애플리케이션 계층 프로토콜, 구글 서버·크롬·모바일 YouTube에 적용
  - TCP처럼 연결 설정, 오류·혼잡 제어 + 보안 포함
  - 한 연결 안에 여러 스트림 → 하나가 손실돼도 다른 스트림은 진행 → HOL 블로킹 제거
  - 연결 설정: TCP + TLS는 핸드셰이크 2번을 차례로 해야 하지만, QUIC은 신뢰성·혼잡 제어·인증·암호화를 핸드셰이크 1번으로
- 계층 비교
  - HTTP/2: HTTP → TLS → TCP → IP
  - HTTP/3: HTTP/3 → QUIC(RDT + 혼잡 제어 + 암호화) → UDP → IP
### 3장 정리
- 트랜스포트 서비스: 다중화·역다중화, 신뢰적 전송, 흐름 제어, 혼잡 제어
- 인터넷 구현: UDP, TCP, QUIC
- 네트워크 가장자리(애플리케이션, 트랜스포트) 끝 → 다음은 코어(네트워크 계층)
