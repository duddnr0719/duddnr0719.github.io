> 파일 시스템의 중복성·종속성 문제를 풀려고 나온 소프트웨어가 DBMS. 정의·조작·제어 기능을 가지며, 네트워크/계층 → 관계 → 객체 → NoSQL/NewSQL로 발전했다.
### 파일 시스템의 문제
- 응용 프로그램마다 자기 데이터 파일을 따로 관리
- **데이터 중복성**: 같은 데이터가 여러 파일에 → 공간 낭비 + 일관성·무결성 유지 어려움
  - 예: 고객 관리 파일(고객아이디, 고객명, 연락처, 주소, 등급, 비밀번호)과 주문 관리 파일(주문번호, 고객아이디, 고객명, 연락처, 주소, 제품명, 수량)에 고객 정보가 중복
- **데이터 종속성**: 응용 프로그램이 파일 구조에 종속
- 동시 공유·보안·회복 기능 부족, 응용 프로그램 개발이 어려움
- 장점은 저비용 하나
### 해결: 통합
- 중복 데이터를 한곳에 통합해 저장하고 모든 응용이 공유
- 관계 모델로 보면: 고객 릴레이션(PK 고객아이디)과 주문 릴레이션으로 나누고, 주문의 `주문고객`이 고객아이디를 참조하는 **외래키**가 됨 → 고객 정보는 한 번만 저장
### DBMS 정의와 기능
- DBMS(DataBase Management System): 파일 시스템 문제를 해결하려고 나온 소프트웨어. 조직에 필요한 데이터를 DB에 통합 저장·관리.
- 사용자(응용 프로그램 또는 직접 접근) ↔ DBMS ↔ DB(공유 데이터 + 개별 데이터)
| 기능 | 내용 | 언어 |
|---|---|---|
| 정의 | DB 구조를 정의·수정 | DDL |
| 조작 | 삽입·삭제·수정·검색 | DML |
| 제어 | 데이터를 항상 정확하고 안전하게 유지 | DCL |
- 이 셋을 모두 담은 표준 언어가 SQL(Structured Query Language)
### 장단점
- 장점: 중복 통제, 데이터 독립성 확보, 동시 공유, 보안 향상, 무결성 유지, 표준화, 장애 회복, 응용 개발 비용 감소
- 단점
  - 비용이 큼 (DBMS 구매 비용)
  - 백업·회복이 복잡 (동시 공유 때문에 불가피)
  - 중앙 집중 관리의 취약점 (장애 하나가 전체 업무 중단)
### 발전 과정
- 1960년대 파일 시스템 →
- **1세대**
  - 네트워크 DBMS: 그래프 형태 (IDS)
  - 계층 DBMS: 트리 형태 (IMS)
- **2세대 관계 DBMS**: 테이블 형태
| DBMS | 제작사 | 비고 |
|---|---|---|
| Oracle | Oracle | 상용 점유율 1위 |
| MySQL | Oracle | 오픈 소스 + 상용 |
| MariaDB | MariaDB | MySQL 초기 개발자들이 독립해서 만든 오픈 소스 |
| PostgreSQL | PostgreSQL | 오픈 소스 |
| SQL Server | Microsoft | 중·대형 시장 |
| DB2 | IBM | 메인프레임 점유율 1위 |
| Access | Microsoft | PC용 |
| SQLite | SQLite | 모바일(Android, iOS) 전용, 오픈 소스 |
  - 그 밖에 Informix, Sybase
- **3세대**
  - 객체지향 DBMS: 객체로 DB 구성 (O2, ONTOS, GemStone)
  - 객체관계 DBMS: 객체 + 관계
- **4세대**: 빅데이터 등장
  - 비정형 데이터 위주, 안정성·일관성을 위한 복잡한 기능 포기, 스키마를 미리 정하지 않는 유연성, 분산 처리(Hadoop)
  - NoSQL: 대부분 오픈 소스, 비정형(웹 문서, SNS)에 적합, 일관성·무결성보다 **가용성·확장성** 중시 (HBase, Cassandra, MongoDB, CouchDB)
  - NewSQL: 관계 DBMS의 장점 + NoSQL의 확장성·유연성, 정형/비정형 모두 안정적·빠르게 (Google Spanner, VoltDB, NuoDB)
- 전망: NewSQL은 아직 진입 단계. RDBMS나 NoSQL을 대체하기보다는 공존할 것 → 데이터 형태와 업무 성격에 맞춰 선택
