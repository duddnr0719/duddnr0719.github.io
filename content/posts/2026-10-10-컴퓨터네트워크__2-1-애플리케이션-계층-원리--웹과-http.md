> 애플리케이션은 소켓을 통해 트랜스포트 서비스를 '고르고', HTTP는 그 위에서 TCP로 객체를 주고받는 비상태 프로토콜이다.
### 네트워크 애플리케이션 원리
- 애플리케이션은 종단 시스템에서만 실행. 코어(라우터·스위치)는 사용자 앱을 실행하지 않음 → 코어용 SW 개발 불필요, 빠른 개발·배포 가능.
- 클라이언트/서버 구조
  - 서버: 항상 켜짐, 고정 IP, 데이터 센터로 확장
  - 클라이언트: 서버에만 요청, 클라이언트끼리 직접 통신 X, 유동 IP 가능, 간헐적 연결
  - 예: HTTP, IMAP, FTP
- P2P 구조: 상시 서버 없음, 피어끼리 직접 통신. 새 피어가 서비스 요청과 동시에 제공 → 자기 확장성(self-scalability). 대신 피어가 간헐적 연결·IP 변경 → 관리 어려움.
### 프로세스와 소켓
- 프로세스 = 호스트에서 실행 중인 프로그램. 같은 호스트는 OS의 IPC, 다른 호스트는 메시지 교환.
- 클라이언트 프로세스 = 통신 세션을 시작하는 쪽, 서버 프로세스 = 접속을 기다리는 쪽. P2P도 두 역할을 모두 가짐.
- 소켓: 애플리케이션 계층 ↔ 트랜스포트 계층 사이 인터페이스(API). 프로세스가 집이면 소켓은 문.
  - 소켓 위쪽은 개발자가, 아래쪽(트랜스포트 이하)은 OS가 통제 → 반반의 통제권
- 프로세스 주소 = IP 주소(호스트 식별, 32비트) + 포트 번호(소켓 식별). IP만으로는 호스트 안 여러 프로세스를 구분 못 함.
  - well-known 포트: HTTP 80, SMTP 25 (목록은 IANA)
  - 예: gaia.cs.umass.edu → 128.119.245.12:80
### 애플리케이션 계층 프로토콜이 정하는 것
- 메시지 타입(요청/응답), 문법(필드 구성), 의미(필드 정보의 뜻), 언제·어떻게 송신/응답하는지의 규칙
- 오픈 프로토콜: RFC로 공개, 상호운용성 보장(HTTP, SMTP) / 독점 프로토콜: Skype, Zoom
### 앱이 트랜스포트에 요구하는 것
- 데이터 무결성(파일·웹은 손실 0 필요, 오디오는 일부 손실 OK), 처리율(멀티미디어는 최소 보장 필요, 이메일은 탄력적), 시간(인터넷 전화·게임은 저지연), 보안
| 앱 | 손실 | 대역폭 | 시간 민감 |
|---|---|---|---|
| 파일 전송/메일/웹 | 비손실 | 가변적 | X |
| 실시간 A/V | 허용 | 오디오 5kbps~1Mbps, 비디오 10kbps~5Mbps | 수십 ms |
| 저장 A/V | 허용 | 위와 동일 | 수 초 |
| 상호작용 게임 | 허용 | Kbps+ | 수십 ms |
| 메신저 | 비손실 | 가변적 | 경우에 따라 |
### TCP vs UDP
- TCP: 신뢰적 전송(손실 X, 순서 보장), 흐름 제어, 혼잡 제어, 연결지향(핸드셰이크), full-duplex. 시간·최소 처리율·보안은 미제공.
- UDP: 비신뢰, 비연결형, 위 서비스 전부 없음. 혼잡 제어·오버헤드를 피하려는 실시간 앱이 사용(DNS, LoL 등).
  - 방화벽이 UDP를 막는 경우가 많아 멀티미디어도 점점 TCP 위(DASH 등)로 이동.
- 매핑: SMTP·HTTP 1.1·FTP·DASH → TCP / 게임·인터넷 전화(SIP, RTP, Skype) → TCP 또는 UDP
- TLS: TCP/UDP는 평문 전송 → TLS가 암호화된 TCP 연결, 무결성, 종단 인증 제공. 애플리케이션 계층에서 라이브러리로 구현(앱이 TLS 라이브러리에 평문을 넘기면 암호화되어 소켓으로 나감).
### 웹과 HTTP 개요
- 웹 페이지 = 기본 HTML 파일 + 참조 객체들(이미지, 오디오 등). 각 객체는 URL(호스트 이름 + 경로 이름)로 지정.
  - `http://www.someschool.edu/someDept/pic.gif` → 호스트 `www.someschool.edu`, 경로 `/someDept/pic.gif`
- 클라이언트(브라우저)가 요청·표시, 서버(웹 서버)가 객체 전송. TCP 80번 포트 사용.
- 비상태(stateless): 서버는 과거 요청을 기억하지 않음. 상태 유지 프로토콜은 한쪽이 죽으면 상태 불일치 조정이 복잡하기 때문.
### 비지속 vs 지속 연결
- 비지속: TCP 연결 하나에 객체 하나. 예) HTML 1개 + JPEG 10개면 연결 11번.
  1. 클라이언트가 서버 80번 포트로 TCP 연결 → 서버 수락
  1. 요청 메시지 전송 → 서버가 응답 전송 후 연결 종료
  1. 클라이언트가 HTML 파싱 → JPEG 10개 각각 위 과정 반복
- RTT: 작은 패킷이 서버에 갔다 돌아오는 시간
- 응답 시간 = **2 RTT + 파일 전송 시간** (TCP 연결 1 RTT + 요청~첫 바이트 1 RTT)
- 비지속 단점: 객체마다 2 RTT, 연결마다 OS 오버헤드, 그래서 브라우저가 병렬 연결을 여러 개 엶.
- 지속(HTTP/1.1 기본): 응답 후에도 연결 유지, 참조 객체는 객체당 1 RTT 수준.
### HTTP 메시지
- 요청: ASCII. 요청 라인(`method URL version`) + 헤더 라인(`이름: 값`) + 빈 줄(`\r\n`) + 바디
```
GET /index.html HTTP/1.1
Host: www-net.cs.umass.edu
User-Agent: Mozilla/5.0 ...
Accept: text/html,application/xhtml+xml
Accept-Language: en-us,en;q=0.5
Accept-Encoding: gzip,deflate
Connection: keep-alive
```
- 메서드
  - GET: 사용자 입력을 URL의 `?` 뒤에 붙여 전송 (`/animalsearch?monkeys&banana`)
  - POST: 폼 입력을 바디에 담아 전송
  - HEAD: 바디 없이 헤더만 응답
  - PUT: 지정 URL에 파일 업로드(있으면 대체)
- 응답: 상태 라인(`HTTP/1.1 200 OK`) + 헤더(Date, Server, Last-Modified, ETag, Content-Length, Content-Type …) + 데이터
- 상태 코드: `200 OK`, `301 Moved Permanently`(새 위치는 `Location:`), `400 Bad Request`, `404 Not Found`, `505 HTTP Version Not Supported`
- 확인: `curl -v gaia.cs.umass.edu` (-v로 요청/응답 헤더 출력)
### 쿠키
- 비상태 HTTP에서 사용자 상태를 유지하는 방법. 구성 4요소: 응답의 `Set-Cookie:` 헤더, 요청의 `Cookie:` 헤더, 브라우저가 관리하는 쿠키 파일, 사이트의 백엔드 DB.
- 흐름: 첫 방문 → 서버가 ID(예: 1678) 생성 + DB 엔트리 → `Set-Cookie: 1678` → 브라우저 저장 → 재방문 시 `Cookie: 1678` → 서버가 DB 조회해 맞춤 동작
- 용도: 인증, 장바구니, 추천, 웹메일 세션. 프로토콜 종단이 아니라 메시지가 상태를 실어 나르는 구조.
- 계정 정보와 결합되면 사생활 노출 위험.
### 웹 캐시(프록시 서버)
- 기점 서버 대신 요청을 처리. 브라우저에겐 서버, 기점 서버에겐 클라이언트.
- 캐시에 있으면 바로 응답, 없으면 기점 서버에서 가져와 저장 후 전달. 서버는 `Cache-Control: max-age=<초>` / `no-cache`로 캐싱 허용 여부 지시.
- 이점: 응답 시간 단축, 기관 접속 회선 트래픽 감소, 느린 서버도 빠르게 콘텐츠 분배.
- 계산 예: 접속 링크 1.54Mbps, RTT 2초, 객체 100Kb, 15요청/초 → 1.5Mbps
  - 캐시 없음: 접속 링크 이용률 1.5/1.54 = 0.97 → 큐잉 지연 폭증, 종단 지연 = 2초 + 수 분 + μs
  - 옵션1 회선 154Mbps 증설: 이용률 0.0097 → 약 2초. 하지만 비쌈.
  - 옵션2 캐시 설치(히트율 0.4): 링크 트래픽 0.6×1.5 = 0.9Mbps, 이용률 0.58 → 평균 지연 ≈ 0.6×(2.01초) + 0.4×(ms) ≈ **1.2초**. 더 싸고 더 빠름.
### 조건부 GET
- 캐시가 `If-modified-since: <date>`로 복사본 시점을 보냄
- 안 바뀌었으면 `304 Not Modified`(객체 생략), 바뀌었으면 `200 OK` + 데이터
### HTTP/2, HTTP/3
- HTTP/1.1: 한 연결에서 파이프라인 GET 가능하지만 순서대로(FCFS) 응답 → 큰 객체 뒤의 작은 객체가 대기하는 **HOL 블로킹**, 손실 재전송 시 전부 stall.
- HTTP/2(RFC 7540, 2015): 메서드·상태 코드·헤더는 1.1과 동일. 클라이언트 지정 우선순위로 전송, 서버 푸시, 객체를 프레임으로 쪼개 섞어(인터리빙) 보내 HOL 완화.
  - 한계: 단일 TCP라 패킷 하나 손실되면 모든 객체 전송이 멈춤. 기본 TCP엔 암호화도 없음.
- HTTP/3(RFC 9114, 2022): 구글이 만든 QUIC(UDP 기반) 사용. 암호화가 프로토콜에 포함, 오류·혼잡 제어 제공, 사용자 IP가 바뀌어도 연결 유지(모바일 스트리밍에 유리).
