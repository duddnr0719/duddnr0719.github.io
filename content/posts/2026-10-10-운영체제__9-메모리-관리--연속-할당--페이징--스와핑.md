> CPU가 만드는 주소는 논리 주소고, MMU가 실행 시간에 물리 주소로 바꾼다. 연속 할당은 외부 단편화가 문제 → 페이징(고정 크기로 쪼개 아무 프레임에나)으로 해결. 페이지 테이블은 TLB로 빠르게, 너무 크면 계층·해시·역 페이지 테이블로.
### 배경
- 프로그램은 디스크 → 메모리에 적재되어 프로세스로 실행
- CPU가 직접 접근하는 저장소는 **레지스터와 메인 메모리뿐**. 메모리 유닛은 주소 + 읽기/쓰기 요청만 봄
- 레지스터는 1클럭, 메모리는 여러 클럭 → CPU가 멈춤(stall) → 사이에 **캐시**
- **베이스·리미트 레지스터**: 프로세스마다 접근 가능한 범위를 지정 (Base ≤ 주소 < Base + Limit)
  - 사용자 모드에서 나오는 모든 주소를 하드웨어가 검사, 벗어나면 트랩 (segmentation fault)
  - 두 레지스터를 바꾸는 명령은 특권 명령
### 주소 바인딩
- 소스의 기호 주소(`int a`) → 컴파일 후 재배치 가능 주소(모듈 시작 + 14) → 링커·로더 후 절대 주소
| 시점 | 결과 | 특징 |
|---|---|---|
| 컴파일 시간 | 절대 코드 | 적재 위치가 바뀌면 재컴파일 |
| 적재 시간 | 재배치 가능 코드 | 적재할 때 위치 결정 |
| 실행 시간 | — | 실행 중에도 이동 가능, 하드웨어(MMU) 필요 |
- 현대 OS는 대부분 **실행 시간 바인딩** (MMU로 동적 재배치)
### 논리 주소 vs 물리 주소
- 논리(가상) 주소: CPU가 생성하는 주소, 그 집합 = 논리 주소 공간
- 물리 주소: 메모리 유닛이 실제로 보는 주소
- 실행 시간 바인딩에선 둘이 다름
- **MMU**: 실행 중에 가상 → 물리로 바꾸는 하드웨어
  - 가장 단순한 형태: **재배치 레지스터** 값을 더함. 논리 346 + 재배치 14000 = 물리 **14346**
  - 사용자 프로그램은 물리 주소를 전혀 보지 않음
- 동적 적재: 루틴을 호출될 때 비로소 적재 (안 쓰는 코드는 메모리를 차지하지 않음), 루틴은 디스크에 재배치 가능 형식으로 보관
### 연속 메모리 할당
- 메모리를 두 파티션으로: 낮은 주소엔 OS(인터럽트 벡터 포함), 높은 주소엔 사용자 프로세스
- 각 프로세스는 **연속된 한 덩어리**를 통째로 받음
- 보호: 논리 주소 < 리미트인지 검사 → 맞으면 재배치 레지스터를 더해 물리 주소, 아니면 트랩
- 가변 파티션: 프로세스 크기에 맞게 할당. 프로세스가 생겼다 사라지면서 크기가 제각각인 빈 공간 **홀(hole)** 이 흩어짐
- 동적 메모리 할당 전략 (크기 n 요청)
  - **최초 적합**: 처음 만나는 충분히 큰 홀
  - **최적 적합**: 충분히 큰 것 중 가장 작은 홀 (전체 탐색, 가장 작은 자투리)
  - **최악 적합**: 가장 큰 홀 (전체 탐색, 가장 큰 자투리)
  - 속도·공간 효율 모두 최초·최적이 최악보다 나음
  - 예: 홀 18K, 30K, 50K에 16K 요청 → 최초·최적은 18K, 최악은 50K
- 연습문제: 파티션 100, 170, 40, 205, 300, 185MB에 프로세스 200, 15, 185, 75, 175, 80MB를 차례로 (남은 자투리도 다시 쓸 수 있다고 가정)
| 요청 | 최초 적합 | 최적 적합 | 최악 적합 |
|---|---|---|---|
| 200 | 205 | 205 | 300 |
| 15 | 100 | 40 | 205 |
| 185 | 300 | 185 | 205의 나머지 190 |
| 75 | 100의 나머지 85 | 100 | 185 |
| 175 | 185 | 300 | **할당 불가** (남은 최대 홀 170) |
| 80 | 170 | 300의 나머지 125 | 170 |
- 최초·최적은 모두 할당하지만 최악 적합은 큰 홀을 먼저 깎아 먹어서 175MB를 못 넣음
### 단편화
- **외부 단편화**: 빈 공간의 합은 충분한데 연속돼 있지 않아 할당 불가
- **내부 단편화**: 고정 단위로 나눠 주다 보니 할당된 공간이 요청보다 조금 커서 안쪽이 남는 것
- **50% 규칙**: 최초 적합을 분석하면 N개 블록 할당 시 0.5N개 블록이 단편화로 버려짐 → 메모리의 약 1/3을 못 씀
- **압축(compaction)**: 프로세스들을 한쪽으로 몰아 빈 공간을 하나로 합침
  - 재배치가 실행 시간에 동적으로 될 때만 가능, 비용 큼, I/O 진행 중이면 곤란 (커널 버퍼로만 I/O)
  - 근본 대안: 연속이 아니어도 되게 → 세그멘테이션, 페이징
### 세그멘테이션
- 프로그램을 의미 단위의 **가변 길이** 세그먼트 집합으로 봄 (코드, 함수, 전역 변수, 스택, 힙, 심볼 테이블, 배열 …)
- 세그먼트끼리는 물리적으로 떨어져 있어도 되고, 변환은 세그먼트 테이블이 담당
- 교재 10판에선 빠짐. 페이징이 워낙 강력해서 지금은 거의 안 씀 (개념만)
### 페이징
- 프로세스의 물리 주소 공간이 **연속일 필요 없음** → 외부 단편화 없음
- 물리 메모리를 고정 크기 **프레임**(2의 거듭제곱, 512B~16MB), 논리 메모리를 같은 크기의 **페이지**로 나눔
- OS는 빈 프레임 목록을 관리, n페이지 프로세스엔 빈 프레임 n개 (예: 빈 프레임 14, 13, 18, 20, 15 → 새 프로세스의 페이지 0~3에 14, 13, 18, 20 할당, 15만 남음)
- 논리 주소 = **페이지 번호 p | 오프셋 d**
  - 논리 주소 공간 2ᵐ, 페이지 크기 2ⁿ이면 상위 m − n비트가 p, 하위 n비트가 d
  - p로 페이지 테이블을 찾아 프레임 번호 f → 물리 주소 = f × 페이지 크기 + d
- 예: m = 4, n = 2 (16B 공간, 4B 페이지), 페이지 테이블 0→5, 1→6, 2→1, 3→2
  - 논리 주소 13 = 1101₂ → p = 3, d = 1 → 프레임 2 → 물리 2 × 4 + 1 = **9**
- 내부 단편화: 페이지 2,048B, 프로세스 72,766B → 35페이지 + 1,086B → 36페이지 필요, 마지막 페이지에서 2,048 − 1,086 = **962B** 낭비
  - 최악 1프레임 − 1B, 평균 반 페이지
  - 작은 페이지: 단편화↓, 대신 페이지 테이블↑·I/O 효율↓ → 요즘은 큰 페이지도 함께 지원 (Linux 4KB/2MB, Solaris 8KB/4MB)
### 페이지 테이블과 TLB
- 페이지 테이블은 메인 메모리에. **PTBR**(테이블 위치), **PTLR**(테이블 크기) 레지스터가 가리키고, 컨텍스트 스위치 때 이 값만 바꿈
- 문제: 데이터 하나 읽을 때 메모리 접근 **2번** (페이지 테이블 + 데이터)
- **TLB**: 최근 쓴 (페이지 → 프레임) 매핑을 담은 고속 연관 메모리 캐시. 모든 항목을 동시에 비교. 보통 32~1,024개
  - 히트: 바로 프레임 번호 / 미스: 페이지 테이블에서 찾고 TLB에 등록 (가득 차면 교체, 일부는 wired down으로 고정)
  - **ASID**: 항목마다 주소 공간 ID를 붙여 프로세스를 구분 → 없으면 컨텍스트 스위치마다 TLB 전체를 비워야 함
- **유효 접근 시간** (메모리 접근 t, TLB 적중률 α, TLB 검색 시간 무시)
  - EAT = α·t + (1 − α)·2t = **(2 − α)·t**
  - α = 0.8, t = 100ns → 0.8 × 100 + 0.2 × 200 = **120ns**
  - α = 0.99 → 0.99 × 100 + 0.01 × 200 = **101ns** (거의 1번 접근 수준)
  - 슬라이드 그림엔 `(1 + α)·t`로 적혀 있는데, 위 계산과 맞으려면 `(2 − α)·t`가 맞음
  - TLB 검색 시간 ε까지 넣고 메모리 접근을 1로 두면 EAT = (1 + ε)α + (2 + ε)(1 − α) = 2 + ε − α
### 메모리 보호와 공유
- 페이지 테이블 항목에 **보호 비트** (읽기 전용 / 읽기·쓰기 / 실행 전용)
- **유효-무효 비트**: v면 그 프로세스의 합법적 페이지, i면 접근 시 트랩
  - i가 되는 경우: 허락된 논리 주소 공간 밖, 프레임 정보가 없거나 범위를 벗어남, (가상 메모리에서) 아직 메모리에 안 올라온 페이지
- **공유 페이지**: 읽기 전용·재진입 가능 코드(에디터, 컴파일러, 윈도우 시스템, 공유 라이브러리)는 사본 하나를 여러 프로세스의 페이지 테이블이 같은 프레임으로 가리킴. 데이터는 프로세스마다 따로
### 페이지 테이블 구조
- 32비트 주소, 4KB 페이지 → 항목 2³² / 2¹² = 2²⁰ ≈ 100만 개 × 4B = 프로세스당 **4MB**를 연속으로 → 부담
- **계층적(다단계) 페이지 테이블**: 페이지 테이블 자체를 페이징
  - 32비트, 1KB 페이지: p(22) + d(10) → p를 다시 p₁(12) + p₂(10)으로
  - [p₁ 12 | p₂ 10 | d 10]: 바깥 테이블 → 안쪽 테이블 → 데이터 (메모리 접근 3번)
  - 안 쓰는 영역의 안쪽 테이블은 만들 필요 없음
  - 64비트(4KB 페이지)면 항목 2⁵²개, 2단계로 해도 바깥 테이블만 수 TB → 단계를 늘리면 접근 횟수가 4~5번으로
- **해시 페이지 테이블**: 가상 페이지 번호를 해시해서 버킷으로, 충돌은 체인 (가상 페이지 번호, 프레임 번호, 다음 포인터)
  - 클러스터형: 한 항목이 연속된 여러 페이지(예: 16개)를 담당 → 64비트·드문드문한 주소 공간에 적합
- **역 페이지 테이블**: 물리 프레임마다 항목 하나, 시스템 전체에 테이블 **하나** (PID, 가상 페이지 번호)
  - 메모리 사용량이 크게 줆
  - 대신 (PID, p)로 테이블을 검색해야 해서 느림 → 해시로 보완, 같은 프레임을 여러 가상 주소가 가리키는 공유 메모리가 어려움
### 스와핑
- 프로세스(또는 그 페이지)를 잠시 **백킹 스토어**(빠른 디스크)로 내렸다가 다시 올림 → 프로세스들의 메모리 합이 실제 메모리보다 커도 실행 가능
- 다시 올릴 위치: 컴파일·적재 시간 바인딩이면 원래 주소로, 실행 시간 바인딩이면 아무 곳에나
- 컨텍스트 스위치에 스와핑이 끼면 매우 느림: 100MB 프로세스, 50MB/s → 스왑 아웃 2초 + 스왑 인 2초 ≈ **4초**
- I/O 대기 중인 프로세스는 내리면 안 됨 (I/O가 엉뚱한 프로세스 메모리로 들어감) → 커널 버퍼로만 I/O(더블 버퍼링, 오버헤드 추가)
- 현대 OS(UNIX, Linux, Windows)는 프로세스 통째가 아니라 **페이지 단위** 스와핑, 메모리가 부족할 때만
- 모바일은 보통 스와핑 안 함: 플래시는 용량이 작고 쓰기 횟수 제한, CPU-플래시 처리량도 낮음
  - iOS: 앱에 메모리를 반납하라고 요청, 안 하면 종료
  - Android: 메모리가 부족하면 앱을 종료하되 상태를 플래시에 저장해 빠르게 재시작
