> 회피 = 요청을 들어줬다고 '가정'한 뒤 여전히 안전 순서가 있는지 검사. 인스턴스가 하나씩이면 자원 할당 그래프(클레임 간선 + 사이클 검사), 여러 개면 은행원 알고리즘. 탐지는 같은 계산을 Need 대신 Request로 돌려 남는 프로세스를 찾는 것.
### 왜 회피인가
- 방지는 효율이 나쁨: 쓸 수 있는 방법이 적고, 처리량이 떨어지고, 멀티스레딩으로 얻은 속도를 까먹음
- 회피: 위험한 상태로 가는 할당이면 "좀 기다려" → 이를 위해 사전 정보가 필요
  - 각 프로세스가 앞으로 요구할 **최대** 자원 수, 가용 자원 수, 이미 할당된 수
- **안전 상태**: 안전 순서 <P₁, …, Pₙ>가 존재 (각 Pᵢ가 더 필요한 양 ≤ 가용 + 앞선 프로세스들이 반납할 양)
  - 안전 → 교착 없음 / 불안전 → 교착 가능 / 교착 ⊂ 불안전 → **안전 상태에서만 놀자**
| 상황 | 알고리즘 | 판단 | 복잡도 |
|---|---|---|---|
| 자원마다 인스턴스 1개 | 자원 할당 그래프 | 사이클 여부 | O(n²) |
| 인스턴스 여러 개 | 은행원 알고리즘 | 안전 순서 존재 여부 | O(m × n²) |
### 자원 할당 그래프 알고리즘
- **클레임 간선** Pᵢ ⇢ Rⱼ (점선): 앞으로 Rⱼ를 요청할 수도 있음을 미리 표시
1. 요청이 오면 클레임 간선을 요청 간선으로
1. 들어줬다고 가정하고 할당 간선 Rⱼ → Pᵢ로 바꿔봄
1. 사이클이 없으면 허용, 생기면 거부(대기)
- 예: R₁ → P₁(할당), P₂ → R₁(요청), P₁ ⇢ R₂, P₂ ⇢ R₂(클레임). 지금 R₂를 P₂에게 주면 R₂ → P₂ → R₁ → P₁ ⇢ R₂ 사이클 → 불안전이므로 R₂가 비어 있어도 P₂는 기다려야 함
### 은행원 알고리즘: 자료구조
- n = 프로세스 수, m = 자원 유형 수
- `Available[m]`: Rⱼ의 가용 인스턴스 수
- `Max[n][m]`: Pᵢ가 Rⱼ를 최대 몇 개 요구할지
- `Allocation[n][m]`: Pᵢ가 지금 가진 Rⱼ 수
- `Need[n][m]` = **Max − Allocation**: 앞으로 더 요구할 수
### 안전 알고리즘
1. `Work = Available`, 모든 `Finish[i] = false`
1. `Finish[i] == false`이고 `Need[i] ≤ Work`인 i를 찾음. 없으면 4로
1. `Work += Allocation[i]`, `Finish[i] = true` (i가 끝나고 반납했다고 보고) → 2로
1. 모든 `Finish[i] == true`면 안전
### 예제
- 스레드 T₀~T₄, 자원 A(10), B(5), C(7)
| | Allocation | Max | Need |
|---|---|---|---|
| T₀ | 0 1 0 | 7 5 3 | 7 4 3 |
| T₁ | 2 0 0 | 3 2 2 | 1 2 2 |
| T₂ | 3 0 2 | 9 0 2 | 6 0 0 |
| T₃ | 2 1 1 | 2 2 2 | 0 1 1 |
| T₄ | 0 0 2 | 4 3 3 | 4 3 1 |
- Available = (3, 3, 2)
| 단계 | 선택 | 조건 | Work |
|---|---|---|---|
| 시작 | | | (3, 3, 2) |
| 1 | T₁ | (1, 2, 2) ≤ (3, 3, 2) | (5, 3, 2) |
| 2 | T₃ | (0, 1, 1) ≤ (5, 3, 2) | (7, 4, 3) |
| 3 | T₄ | (4, 3, 1) ≤ (7, 4, 3) | (7, 4, 5) |
| 4 | T₀ | (7, 4, 3) ≤ (7, 4, 5) | (7, 5, 5) |
| 5 | T₂ | (6, 0, 0) ≤ (7, 5, 5) | (10, 5, 7) |
- 안전 순서 <T₁, T₃, T₄, T₀, T₂> 존재 → **안전**. 순서는 하나만 있으면 되고 다른 순서도 가능
### 자원 요청 알고리즘 (Pᵢ가 Requestᵢ를 요청)
1. `Request ≤ Need[i]` 아니면 오류 (최대 요구량 초과)
1. `Request ≤ Available` 아니면 대기 (자원 부족)
1. 들어줬다고 **가정**: `Available −= Request`, `Allocation[i] += Request`, `Need[i] −= Request` → 안전 알고리즘 실행 → 안전하면 실제로 할당, 아니면 되돌리고 대기
- T₁이 (1, 0, 2) 요청
  - (1, 0, 2) ≤ Need₁ (1, 2, 2) ✓, ≤ Available (3, 3, 2) ✓
  - 가정: Allocation₁ = (3, 0, 2), Need₁ = (0, 2, 0), Available = (2, 3, 0)
  - 안전 순서 <T₁, T₃, T₄, T₀, T₂> 여전히 존재 → **승인**
- 그 상태에서 T₄가 (3, 3, 0) 요청 → (3, 3, 0) ≤ Need₄ (4, 3, 1) ✓, 하지만 > Available (2, 3, 0) → **대기**
- 그 상태에서 T₀가 (0, 2, 0) 요청 → 1·2단계는 통과, 가정하면 Available = (2, 1, 0)인데 어느 스레드의 Need도 만족 못 함 → 불안전 → **대기** (자원이 있어도 안 줌)
```python
import numpy as np

def is_safe(avail, alloc, need):
    work, finish, seq = avail.copy(), [False] * len(alloc), []
    changed = True
    while changed:
        changed = False
        for i in range(len(alloc)):
            if not finish[i] and all(need[i] <= work):
                work += alloc[i]; finish[i] = True; seq.append(f"T{i}"); changed = True
    return all(finish), seq

def request(i, req, avail, alloc, need):
    if any(req > need[i]):  return "error"
    if any(req > avail):    return "wait (부족)"
    a, al, n = avail - req, alloc.copy(), need.copy()
    al[i] += req; n[i] -= req
    ok, seq = is_safe(a, al, n)
    return ("grant", seq) if ok else "wait (불안전)"

alloc = np.array([[0,1,0],[2,0,0],[3,0,2],[2,1,1],[0,0,2]])
mx    = np.array([[7,5,3],[3,2,2],[9,0,2],[2,2,2],[4,3,3]])
avail = np.array([3,3,2])
print(is_safe(avail, alloc, mx - alloc))   # (True, ['T1', 'T3', 'T4', 'T0', 'T2'])
print(request(1, np.array([1,0,2]), avail, alloc, mx - alloc))   # grant
```
### 현실적 한계
- 방지·회피 모두 복잡하고, 자원을 보수적으로만 써서 성능이 떨어짐
- 요청마다 알고리즘을 돌려야 함 (프로세스가 수백 개면 부담 큼)
- 최대 요구량을 미리 알기 어려움 → 불안전 상태를 절대 허용하면 안 되는 특수한 경우에만 사용
### 교착상태 탐지
- 교착을 허용하고 주기적으로 찾아서 복구: 실행 → 탐지 → (교착이면) 복구 → 계속
- **인스턴스 1개씩: 대기 그래프(wait-for graph)**
  - 자원 할당 그래프에서 자원 노드를 없애고 Pᵢ → Pⱼ ("Pᵢ가 Pⱼ가 쥔 걸 기다림")만 남김
  - 사이클이 있으면 교착. O(n²)
- **인스턴스 여러 개: 행렬 기반** (Available, Allocation, Request)
  1. `Work = Available`. Allocation[i]가 0이 아니면 `Finish[i] = false`, 0이면 true (아무것도 안 쥔 프로세스는 교착에 낄 수 없음 ← 안전 알고리즘과 다른 점)
  1. `Finish[i] == false`이고 `Request[i] ≤ Work`인 i
  1. `Work += Allocation[i]`, `Finish[i] = true` → 2로
  1. `Finish[i] == false`로 남은 프로세스들이 교착 상태. O(m × n²)
  - 은행원과 같은 계산인데 Need 대신 **현재 요청(Request)** 을 씀 (낙관적으로 "지금 요청만 채워주면 끝난다"고 가정)
- 예: 자원 (7, 2, 6)이 전부 할당되어 Available = (0, 0, 0)
| | Allocation | Request |
|---|---|---|
| T₀ | 0 1 0 | 0 0 0 |
| T₁ | 2 0 0 | 2 0 2 |
| T₂ | 3 0 3 | 0 0 0 |
| T₃ | 2 1 1 | 1 0 0 |
| T₄ | 0 0 2 | 0 0 2 |
  - T₀ → (0, 1, 0), T₂ → (3, 1, 3), T₃ → (5, 2, 4), T₁ → (7, 2, 4), T₄ → (7, 2, 6) → 전부 끝남, **교착 없음**
  - T₂의 요청이 (0, 0, 1)로 바뀌면: T₀ 처리 후 Work = (0, 1, 0), 나머지 누구의 Request도 못 채움 → **T₁, T₂, T₃, T₄ 교착**
- 언제 돌릴까: 교착이 얼마나 자주 생기나, 얼마나 많은 프로세스가 영향받나
  - 요청이 즉시 안 될 때마다 돌리면 정확하지만 오버헤드 큼
  - 너무 드물면 원인 추적이 어려워짐 → 주기적으로(예: 하루~한 달, CPU 이용률이 떨어질 때)
### 복구
- **프로세스 종료**
  - 교착된 프로세스 전부 종료: 간단하지만 그동안의 작업 손실이 큼
  - 사이클이 풀릴 때까지 하나씩 종료: 매번 탐지를 다시 돌려야 해서 오버헤드
  - 누구부터? 우선순위, 지금까지 실행한 시간과 남은 시간, 쥔 자원의 종류·양, 더 필요한 자원 양 등 비용이 가장 적은 쪽
- **자원 선점**
  1. 희생자 선택: 비용이 최소가 되도록 누구의 어떤 자원을 뺏을지
  1. 롤백: 자원을 뺏긴 프로세스를 안전한 이전 상태로 되돌려 재시작 (가장 단순한 건 전부 재시작)
  1. 기아 방지: 같은 프로세스만 계속 희생되지 않게 롤백 횟수를 비용에 포함
