> 준비 큐에서 누구에게 CPU를 줄까. FCFS(단순, 호송 효과) → SJF/SRTF(평균 대기 최소, 버스트 예측 필요) → 우선순위(기아 → 노화) → RR(응답성, q 선택이 관건) → 다단계(피드백) 큐. 평가는 결정론적 모델링·큐잉 모델·시뮬레이션·실제 구현.
### 기본 개념
- 다중 프로그래밍의 핵심 = CPU 스케줄링 (CPU는 제한된 자원, 여러 프로세스가 경쟁)
- 프로세스 실행 = **CPU 버스트**와 **I/O 버스트**의 반복 (파일 읽기 → 처리 → 화면 출력 → …)
- CPU 버스트 히스토그램: 짧은 버스트(수 ms)가 압도적으로 많고 길수록 지수적으로 줄어듦
  - 대부분은 I/O 바운드(짧게 씀), 일부만 CPU 바운드(오래 씀)
  - CPU 바운드가 CPU를 안 놓으면 I/O 바운드는 I/O가 끝나도 한참 대기 → 스케줄링이 필요
### 스케줄러와 디스패처
- CPU 스케줄러: 준비 큐에서 하나를 골라 CPU 할당
- 스케줄링이 일어나는 시점
  1. running → waiting (I/O 요청, `wait()`)
  1. running → ready (타이머 인터럽트)
  1. waiting → ready (I/O 완료)
  1. 종료
  - 1, 4에서만 하면 **비선점**(자발적으로 놓을 때까지), 2, 3에서도 하면 **선점**
  - 선점의 주의점: 공유 데이터를 쓰던 중 뺏기면 경쟁 상태, 커널 작업 중 인터럽트 처리도 신중해야 함
- **디스패처**: 선택된 프로세스에 실제로 CPU를 넘기는 모듈
  - 컨텍스트 스위치(현재 상태 저장 → 새 상태 복원) → 사용자 모드 전환 → 재개 위치로 점프
  - **디스패치 지연**: 이 과정에 걸리는 시간, 보통 μs 단위, 최소화해야 함
### 평가 기준
| 기준 | 의미 | 목표 |
|---|---|---|
| CPU 이용률 | CPU가 일한 시간 비율 | 최대 |
| 처리량 | 단위 시간당 완료 프로세스 수 | 최대 |
| 반환 시간 | 제출 ~ 완료 (= 실행 + 대기) | 최소 |
| 대기 시간 | 준비 큐에서 기다린 시간의 합 (스케줄링이 직접 영향) | 최소 |
| 응답 시간 | 요청 ~ 첫 응답 (대화형에서 중요) | 최소 |
- 프로세스 전체 수명이 아니라 CPU 버스트 1건 기준으로 따짐
### FCFS (선착순)
- 먼저 온 순서대로, 비선점, FIFO 큐
- P1 = 24, P2 = 3, P3 = 3
  - 도착 P1, P2, P3: `P1 0–24 | P2 24–27 | P3 27–30` → 대기 0, 24, 27 → 평균 **17**
  - 도착 P2, P3, P1: `P2 0–3 | P3 3–6 | P1 6–30` → 대기 6, 0, 3 → 평균 **3**
- 도착 순서에 따라 성능이 크게 흔들림
- **호송 효과(convoy effect)**: 긴 CPU 바운드 하나 뒤에 짧은 I/O 바운드들이 줄줄이 대기 → CPU·장치 이용률 모두 하락
### SJF (최단 작업 우선)
- 다음 CPU 버스트가 가장 짧은 프로세스부터
- 주어진 프로세스 집합에서 **평균 대기 시간이 최소**임이 증명됨
- 예: 모두 시각 0 도착, P1 = 6, P2 = 8, P3 = 7, P4 = 3
  - `P4 0–3 | P1 3–9 | P3 9–16 | P2 16–24`
  - 대기 P1 3, P2 16, P3 9, P4 0 → 평균 **7**
  - 슬라이드 본문엔 도착 시각(0, 2, 4, 5)과 순서 'P1 → P4 → …'가 적혀 있지만, 간트 차트와 대기 시간은 모두 시각 0 도착 기준(P4 → P1 → P3 → P2)이라 그쪽으로 정리함
- 한계: 다음 버스트 길이를 미리 알 수 없음 → 과거로 예측
### 다음 버스트 예측: 지수 평균
- tₙ = n번째 실제 버스트, τₙ₊₁ = 다음 예측값, 0 ≤ α ≤ 1
- **τₙ₊₁ = α·tₙ + (1 − α)·τₙ**
  - α = 0: 최근 실측 무시, 예측값 유지
  - α = 1: 직전 실측값만 사용
- 펼치면 τₙ₊₁ = α·tₙ + (1−α)α·tₙ₋₁ + … + (1−α)ʲα·tₙ₋ⱼ + … + (1−α)ⁿ⁺¹·τ₀
  - (1 − α) < 1이라 오래된 버스트일수록 가중치가 지수적으로 줄어듦 → 최근 경향 위주로 적응
### SRTF (선점형 SJF)
- 새로 온 프로세스의 버스트가 현재 프로세스의 **남은** 시간보다 짧으면 선점
- 예 1: P1(도착 0, 8), P2(1, 4), P3(2, 9), P4(3, 5)
  - `P1 0–1 | P2 1–5 | P4 5–10 | P1 10–17 | P3 17–26`
  - t = 1: P2(4) < P1 남은 7 → 선점. t = 3: P4(5) > P2 남은 2 → 선점 안 됨
  - 대기 P1 9, P2 0, P3 15, P4 2 → 평균 **6.5**
  - 슬라이드엔 대기 10, 1, 17, 5 / 평균 8.25와 "P4 도착 시 재선점"으로 적혀 있는데, 직접 시뮬레이션하면 위 결과가 나옴 (교재 값도 6.5)
- 예 2: P1(0, 7), P2(2, 4), P3(4, 1), P4(5, 4)
  - 비선점 SJF: `P1 0–7 | P3 7–8 | P2 8–12 | P4 12–16` → 대기 0, 6, 3, 7 → 평균 4
  - SRTF: `P1 0–2 | P2 2–4 | P3 4–5 | P2 5–7 | P4 7–11 | P1 11–16` → 대기 9, 1, 0, 2 → 평균 **3**
### 우선순위 스케줄링
- 우선순위 정수가 작을수록 높음. 선점형/비선점형 모두 가능
- SJF = 우선순위가 '예측 버스트의 역수'인 특수 경우
- 예 (모두 시각 0): P1(10, 3), P2(1, 1), P3(2, 4), P4(1, 5), P5(5, 2)
  - `P2 0–1 | P5 1–6 | P1 6–16 | P3 16–18 | P4 18–19`
  - 대기 6, 0, 16, 18, 1 → 평균 **8.2**
- 문제: **기아(starvation)** — 높은 우선순위가 계속 오면 낮은 건 영원히 대기
- 해결: **노화(aging)** — 오래 기다릴수록 우선순위를 점점 올려줌
### Round Robin (RR)
- 시분할용 선점 방식. 각자 **시간 할당량 q**(보통 10~100ms)만큼만 실행, 다 쓰면 타이머 인터럽트 → 준비 큐 맨 뒤로
- n개 프로세스면 누구도 (n − 1)·q 이상 기다리지 않음
- 예 (q = 4): P1 = 24, P2 = 3, P3 = 3
  - `P1 0–4 | P2 4–7 | P3 7–10 | P1 10–14 | … | P1 26–30`
  - 대기 P1 6, P2 4, P3 7 → 평균 약 5.67
  - 평균 반환 시간은 SJF보다 길지만 **응답 시간**이 좋음
- q 크기
  - 너무 크면 FCFS와 같아짐
  - 너무 작으면 컨텍스트 스위치 오버헤드 (버스트 10짜리: q = 12 → 0회, q = 6 → 1회, q = 1 → 9회)
  - 컨텍스트 스위치는 보통 1μs 미만이니 q가 그보다 훨씬 커야 함
  - 경험칙: **CPU 버스트의 약 80%가 q보다 짧도록**
- q에 따른 평균 반환 시간은 단조롭지 않음 (P1 6, P2 3, P3 1, P4 7: q = 1 → 11, 2 → 11.5, 3 → 10.75, 4 → 11.5, 5 → 12.25, 6·7 → 10.5)
### 다단계 큐
- 대화형과 배치 작업은 요구가 다름 → 준비 큐를 여러 개로 분리
  - 전경(대화형): RR / 배경(배치): FCFS
- 계층 예: 시스템 → 대화형 → 대화형 편집 → 배치 → 학생 프로세스 (위가 높은 우선순위)
- 큐 사이 스케줄링
  - 고정 우선순위: 위 큐가 비어야 아래 큐 실행 → 기아 위험
  - 시간 분할: 전경 80%, 배경 20%처럼 CPU 시간을 나눠줌
### 다단계 피드백 큐
- 다단계 큐는 프로세스가 한 큐에 고정 → 피드백 큐는 **큐 사이 이동 허용**
  - CPU를 오래 쓰면 아래 큐로 강등, 오래 기다리면 위로 승격 (노화가 자연스럽게 구현)
- 정의 매개변수: 큐 개수, 각 큐의 알고리즘, 승격 기준, 강등 기준, 처음 들어갈 큐
- 예: Q0(RR, q = 8ms) → Q1(RR, q = 16ms) → Q2(FCFS)
  - 새 프로세스는 Q0. 8ms 안에 못 끝내면 Q1 뒤로, 거기서 16ms 안에 못 끝내면 Q2
  - 짧은 대화형 작업은 위에서 빨리 끝나고, 긴 CPU 작업은 아래로 내려가 남는 시간에 처리
### 스레드 스케줄링
- 현대 OS가 실제로 스케줄링하는 건 프로세스가 아니라 **커널 스레드**
- 경쟁 범위
  - PCS(Process Contention Scope): 다대일·다대다 모델에서 스레드 라이브러리가 사용자 스레드를 LWP에 배치할 때, 같은 프로세스 안에서 경쟁
  - SCS(System Contention Scope): 커널이 커널 스레드를 CPU에 배치할 때, 시스템 전체와 경쟁 (일대일 모델은 SCS만)
```c
pthread_attr_t attr;
int scope;
pthread_attr_init(&attr);
pthread_attr_getscope(&attr, &scope);              /* PTHREAD_SCOPE_PROCESS or _SYSTEM */
pthread_attr_setscope(&attr, PTHREAD_SCOPE_SYSTEM); /* SCS로 설정 */
for (i = 0; i < NUM_THREADS; i++)
    pthread_create(&tid[i], &attr, runner, NULL);
```
- Linux·macOS는 SCS만 지원 (PROCESS로 설정하면 실패)
### 다중 프로세서 스케줄링
- 비대칭: 마스터 CPU 하나만 커널 자료구조·I/O 담당 → 단순하지만 병목
- 대칭(SMP): CPU마다 스스로 스케줄링. 공통 준비 큐 하나 또는 CPU별 큐
- **프로세서 친화성**: 하던 CPU에서 계속 실행 → 캐시에 남은 데이터 재사용
  - 소프트: OS가 노력은 하지만 보장 안 함 / 하드: 시스템 호출로 특정 CPU 집합에 고정
- NUMA: CPU마다 가까운 메모리가 더 빠름 → 스케줄러와 메모리 할당기가 함께 고려
- **부하 균형**: 일부 CPU만 바쁘지 않게
  - 푸시 이주: 감시 태스크가 주기적으로 과부하 CPU에서 한가한 CPU로 밀어냄
  - 풀 이주: 한가한 CPU가 바쁜 CPU의 큐에서 가져옴
  - 친화성과 부하 균형은 서로 상충
- 멀티코어 + 하드웨어 스레드: Intel i7 4코어 × 2 = 8 하드웨어 스레드
  - 한 스레드가 **메모리 스톨**(M)에 걸리면 같은 코어의 다른 스레드가 계산(C) → 지연 숨김, 처리량↑
### 알고리즘 평가
- 기준을 정하고 → 그 기준으로 측정
- **결정론적 모델링**: 정해진 작업 부하에 각 알고리즘을 적용해 정확히 계산
  - P1 = 10, P2 = 29, P3 = 3, P4 = 7, P5 = 12 (모두 시각 0)
  - FCFS: 대기 0, 10, 39, 42, 49 → 평균 **28**
  - SJF: `P3 0–3 | P4 3–10 | P1 10–20 | P5 20–32 | P2 32–61` → 평균 **13**
  - RR(q = 10): `P1 0–10 | P2 10–20 | P3 20–23 | P4 23–30 | P5 30–40 | P2 40–50 | P5 50–52 | P2 52–61` → 대기 0, 32, 20, 23, 40 → 평균 **23**
  - 단순·정확하지만 그 입력에만 해당하는 결과
- **큐잉 모델**: 도착과 버스트를 확률 분포(보통 지수 분포)로 보고 이용률·대기 시간 계산. 시스템 = 큐를 가진 서버들의 네트워크
  - **Little의 법칙: n = λ × W** (평균 큐 길이 = 도착률 × 평균 대기 시간). 모든 알고리즘·분포에서 성립
  - 초당 7개 도착, 큐 길이 14 → W = 14 / 7 = **2초**
- **시뮬레이션**: 시스템을 프로그램으로 모델링, 시계 변수로 진행하며 통계 수집. 입력은 난수 또는 실제 시스템을 기록한 **트레이스 테이프**. 정확하지만 비쌈
- **실제 구현**: 커널에 넣어서 측정. 가장 정확하지만 비용·위험이 크고 환경마다 결과가 다름 → 현대 OS는 스케줄러를 모듈화하고 매개변수를 조정 가능하게 설계 (데이터센터, 스마트폰, IoT에 맞춤)
