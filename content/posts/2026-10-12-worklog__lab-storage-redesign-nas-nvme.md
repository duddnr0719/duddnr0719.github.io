> 단일 장애점인 RAID0에 놓여 있던 4.8TB 연구 원본 데이터를 2중 전수 무결성 검증을 거쳐 NAS로 이전하고, 고속 NVMe 스토리지의 기존 파일 경로 호환성을 유지하면서 4.7TB의 작업 공간을 확보함.

# 배경 — 왜 하게 됐나 ?
## 기존 작업 스토리지의 용량 고갈과 단일 장애점 위험
- 연구실 학습용 고속 스토리지는 가상화 호스트의 2TB NVMe SSD 4장을 묶은 RAID0(총 7.4TB) 환경이었음.
- 2026.10 초 실측 결과 7.4TB 중 6.6TB를 사용하여 사용률이 94%에 달했고, 여유 공간은 503GB에 불과했음.
- 디스크 4장 중 1장만 고장 나도 전체가 유실되는 구조인데 외부 백업이 0벌이었음.
- 재수급이 어려운 핵심 원본 데이터셋 4.8TB가 백업 없이 방치된 상태였음.

## 개편 목표
- 원천(raw) 데이터를 8베이 Synology NAS(12TB HDD 2장 RAID1)로 이전하여 영구 보존 정본을 구축함.
- 학습 속도 저하를 막기 위해 가상화 호스트의 고속 NVMe를 공용 작업 캐시 공간으로 전환함.
- 기존 연구자들의 학습 파이프라인과 코드 경로를 깨뜨리지 않고 무중단으로 투명하게 전환함.
- 100% 무결성을 보증하기 위해 이전 파일 전수 체크섬 대조를 완료한 뒤에만 원본을 정리함.

# 환경
- 가상화 호스트 서버 (고속 NVMe 7.4TB, RAID0 스트라이핑)
- 연구실 GPU 서버 2대 (1번 GPU 서버와 2번 GPU 서버, 각 10G 네트워크 연결)
- 제어 서버 (스케줄러 및 공용 환경 관리)
- 중앙 저장소 (8베이 Synology NAS, 12TB HDD 2장 RAID1, 2.5G 네트워크 연결)
- 파일시스템 및 프로토콜 : Btrfs, ext4, NFS, Samba

# 진행 흐름
## 1. 스토리지 계층 구조 설계와 I/O 성능 실측 (2026.10.07)
- 당초 구상은 모든 데이터를 NAS에 두고 각 GPU 서버가 학습 시작 시 로컬 디스크로 받아 캐싱하는 방식이었음.
- 그러나 실측 결과 두 가지 물리적 한계가 드러남.
  - I/O 대역폭 병목 : NAS의 NFS 순차 읽기는 2.5G 대역폭 한계로 263MB/s에 그쳤고, 평균 325KB 소용량 파일 읽기는 단일 27MB/s(초당 84개)와 8병렬 94MB/s(초당 282개)로 저조했음. 반면 가상화 호스트 NVMe 읽기는 GPU 서버에서 859MB/s(2번 GPU 서버 834MB/s)가 측정되어 NAS 직접 읽기보다 3배 이상 빨랐음.
  - GPU 서버 로컬 용량 부족 : 1번 GPU 서버의 로컬 여유 공간은 509GB에 불과하여 684GB 크기의 단일 프로젝트 데이터셋조차 담을 수 없었음.
- 중복 데이터 실측 : 1MB 이상 파일 51만 개를 해시 대조한 결과, 프로젝트 간 복사본 등 약 490GB(전체의 약 7%)의 중복 데이터가 존재함을 확인함.
→ 구조를 변경함. NAS를 영구 정본으로 삼고, 가상화 호스트의 고속 NVMe(읽기 859MB/s)를 전 노드가 공유하는 고속 작업 공간으로 정의함.

## 2. 이전 대상 데이터 분류와 아키텍처 재정립 (2026.10.07 ~ 2026.10.08)
- 작업 스토리지 내 6.5TiB(6.6TB) 데이터를 전수 조사하여 분류함.
  - 원천 연구 데이터셋 : 2488GB(320만 개 파일, 93%가 1MB 미만) 및 2208GB(665만 개 파일, 약 9200개 디렉터리) 선별.
  - 공개 벤치마크 데이터셋 4종 97GB(약 1.3만 개 파일) 선별.
- 합계 약 4.8TiB(4.8TB, 전체의 73%)에 달하는 원본 데이터를 선별함. 1MB 미만 소용량 파일만 약 950만 개(약 2.9TB)였음.
- 진행 중인 연구 프로젝트의 가공 데이터 및 체크포인트(주요 프로젝트 684GB, 일반 연구 534GB, 가공 데이터 313GB, 기타 430GB)는 작업 스토리지에 유지함.
→ 원본 데이터 4.8TB를 NAS의 전용 공유 디렉터리로 전량 안전 복사하기로 결정함.

## 3. 대용량 병렬 복사 수행 (2026.10.08)
- 4.8TB 대용량 및 9,868,823개 파일의 지연 없는 전송을 위해 작업을 50개 디렉터리 단위 197개 묶음으로 세분화함.
- 10개 병렬 rsync 프로세스로 전송 속도 약 230MB/s를 유지하며 NAS 2.5G 대역폭을 온전히 활용함.
- 가상화 호스트의 기존 원본 데이터는 읽기 전용으로만 참조하여 작업 중 데이터 오염 위험을 원천 차단함.
→ 에러 0건으로 복사를 완료함.

## 4. 2중 전수 무결성 검증 (2026.10.08 ~ 2026.10.09)
- 연구실 핵심 원본 데이터이므로 단 하나의 비트 오류도 용납할 수 없었음.
- 1차 검증 (sha256 전수 대조) : 9,868,823개 파일 전체 해시 대조 결과 불일치 0개 및 누락 0개와 메타데이터 차이 0개로 일치를 검증함.
- 디렉터리 메타데이터 크기에서 발생한 1,020,346줄의 차이는 ext4와 Btrfs 파일시스템 간 디렉터리 크기 기록 방식 차이로 인한 정상 동작임을 확인함.
- 2차 검증 (rsync 체크섬 전수 재대조) : 2026.10.09 동안 전체 파일의 블록 체크섬을 처음부터 다시 읽어 대조하여 차이 0줄, 실패 0건, 에러 출력 0바이트로 종료됨.
- 검증 신뢰성 실증 : 고의 변조 테스트 파일 주입 역검증 및 복사 시작 후 원본 신규 쓰기 0건 확인. 9,868,823개 파일의 해시 목록을 420MB 압축 파일로 영구 보관함.
→ 2중 전수 검증을 통과하여 안전한 원본 전환 근거를 확보함.

## 5. 읽기 전용 마운트 전환 및 심링크 호환성 확보 (2026.10.10)
- 원본 삭제 전 영향도를 전수 조사함. 연구실 파이썬 코드 21개 파일과 학습 목록 14개 파일이 기존 고속 NVMe 경로를 직접 참조하고 있었음.
- NAS 관리 설정에서 원본 저장소에 대한 접근 권한을 읽기 전용으로 설정하여 임의 변조 및 삭제를 차단함.
- 가상화 호스트의 NVMe에서 원본 데이터 3종을 삭제하고, 기존 경로에 동일한 이름으로 NAS 마운트 경로를 가리키는 심링크를 생성함.
- GPU 서버 2대와 제어 서버 각각에 NAS 읽기 전용 NFS 마운트를 연결하고 시스템 설정 파일에 영구 등록함.
- 코드 21개와 목록 14개의 수정 없이 원본 데이터 5개 하위항목 및 주요 데이터셋 9260개 디렉터리가 투명하게 조회됨을 확인하고 쓰기 시도시 에러로 차단됨을 실측함.
→ 기존 파일 경로를 100% 호환하면서 고속 NVMe 공간 4.7TB를 즉시 확보함.

## 6. 분산 잔여 사본 및 낡은 백업 정리 (2026.10.10 ~ 2026.10.11)
- 스토리지 정리의 일환으로 각 서버에 흩어져 있던 과거 중복 사본과 구형 백업 데이터를 전수 대조 후 정리함.
- 1번 GPU 서버의 로컬 공유 디렉터리(755GB) 정리 : 로컬 292,655개 파일과 중앙 스토리지 292,764개 파일을 전수 대조함.
- 과거 스토리지 이전 이후 로컬 경로에 직접 기록된 고유 파일 72개와 최신 파일 5개(총 77개 파일, 31MB)를 발견함.
- 유실 방지를 위해 77개 파일을 중앙 스토리지의 별도 보존 디렉터리로 복사하고 sha256 검증을 마침.
- 파일 점유 프로세스가 0개임을 확인한 후 로컬 디렉터리를 삭제하여 755GB를 회수함. 1번 GPU 서버 루트 디스크 사용률이 71%에서 28%로 감소함(사용량 476GB, 여유 1.3TB).
- 낡은 VM 백업 사본 364GB(75개 파일 해시 일치 확인 후 삭제) 제거 및 낡은 홈 백업 디스크 285GB(할당 1.49TB) 분리로 백업 디스크 풀 3.51TB를 회수함.
→ 전체 연구실 인프라의 잔여 데이터를 정리하고 스토리지 공간을 최적화함.

# 트러블슈팅
## 1. 다중 노드 환경 심링크 참조 실패
- 현상 : 가상화 호스트의 작업 스토리지에서 원본 데이터를 지우고 NAS 마운트 디렉터리를 가리키는 심링크를 생성했으나, GPU 서버들과 제어 서버에서 원본 디렉터리 접근 시 심링크가 깨진 링크로 표시되며 파일 목록을 읽지 못함.
- 원인 : NFS 프로토콜 특성상 서버에서 생성된 절대 경로 심링크는 클라이언트 노드의 로컬 파일시스템 루트를 기준으로 해석됨. 가상화 호스트에는 NAS 마운트 포인트가 존재했으나, 각 GPU 서버와 제어 서버 로컬에는 해당 마운트 경로가 아직 연결되지 않았기 때문이었음.
- 해결 : 1번 GPU 서버와 2번 GPU 서버 및 제어 서버 각각에 동일한 로컬 마운트 디렉터리를 생성함. 이후 NAS의 읽기 전용 NFS 마운트를 수동 연결하고 시스템 마운트 설정 파일에 등록하여 시스템 재부팅 후에도 유지되도록 조치함.
- 결과 : 모든 GPU 서버와 제어 서버에서 심링크를 통해 NAS의 원본 파일(원본 데이터 5개 항목, 주요 데이터셋 9260개 디렉터리 등)이 지연 없이 정상 조회됨. 기존 파이썬 학습 코드 21개와 목록 파일 14개의 경로 수정 없이 100% 정상 작동함을 확인함.

## 2. 이전 완료로 판단했던 로컬 디렉터리에서 잔여 쓰기 파일 발견
- 현상 : 한 달 전 중앙 스토리지로 이전 완료된 것으로 파악했던 1번 GPU 서버의 로컬 공유 디렉터리(755GB)를 일괄 삭제하려 했으나, 사전 안전 검사에서 중앙 스토리지에 없는 72개의 파일과 중앙보다 수정 시각이 더 최신인 5개의 파일이 감지됨.
- 원인 : 스토리지 이전 작업 이후에도 일부 연구원이 과거 경로 설정을 그대로 유지한 채 로컬 경로에 직접 연구 산출물(총 31MB)을 저장하고 있었음. 단순 삭제를 강행했을 경우 최근 연구 산출물이 영구 유실될 위험이 있었음.
- 해결 : 즉시 삭제 절차를 중단함. 누락된 72개 파일과 최신 버전 5개(총 77개 파일)를 추출하여 중앙 스토리지의 별도 보존 디렉터리로 원래 디렉터리 구조를 유지한 채 복사함. 양쪽의 sha256 해시를 대조하여 77개 파일의 완전 일치를 검증함. 이후 프로세스 점유가 0개임을 확인한 뒤 안전하게 삭제를 진행함.
- 결과 : 단 한 건의 연구 데이터 유실도 없이 755GB의 디스크 공간을 회수함. 1번 GPU 서버 루트 파일시스템 사용률을 71%에서 28%로 낮추고 1.3TB의 여유 공간을 확보함.

## 3. 대용량 소용량 파일 병렬 이전 초반의 특정 작업 병목
- 현상 : 4.8TB의 원본 데이터를 rsync로 복사하기 시작했으나, 초반 예상 시간이 수십 시간 이상으로 치솟으며 전송 속도가 불안정해짐.
- 원인 : 9,868,823개 파일 중 대부분이 1MB 미만의 극소용량 연구 데이터 파일(단일 데이터셋 665만 개 등)이었는데, 디렉터리 분할 단위가 너무 크게 잡혀 특정 단일 프로세스에 수백만 개의 파일 처리가 집중되며 병렬 처리의 이점을 살리지 못했음.
- 해결 : rsync 작업을 즉시 중단하고 디렉터리 분할 단위를 대폭 재조정함. 수백만 파일이 밀집된 구간을 50개 디렉터리 단위 197개 작업 묶음으로 세분화한 뒤, 10개의 rsync 프로세스가 균등하게 분담하도록 재배치함.
- 결과 : 전송 속도가 약 230MB/s로 안정화되어 NAS의 2.5G 물리 네트워크 대역폭 한계치에 근접한 속도로 밤샘 복사를 성공적으로 완료함.

# 결과
- 작업 스토리지(가상화 호스트 NVMe) 사용량 : 6.6TB (사용률 94%, 여유 503GB) → 1.9TB (여유 4.7TB 확보)
- 원본 데이터 안전성 : 백업 0벌 (단일 NVMe RAID0 의존) → 12TB HDD 2장 RAID1 미러링 영구 보존 정본 체계 구축
- 데이터 무결성 검증 : 9,868,823개 파일 전수 sha256 및 rsync 블록 체크섬 검증 완료 (불일치 0건, 누락 0건)
- 기존 학습 환경 호환성 : 파이썬 코드 21개, 학습 데이터 목록 14개 경로 수정 0건 (심링크 투명 연결 100% 호환)
- 1번 GPU 서버 로컬 여유 공간 : 사용률 71% (사용량 1.3TB, 여유 509GB) → 사용률 28% (사용량 476GB, 여유 1.3TB 확보, 755GB 회수)
- 연구실 백업 스토리지 회수 공간 : 구형 VM 백업 364GB 및 구형 홈 백업 디스크 285GB 정리로 백업 디스크 풀 3.51TB 회수
