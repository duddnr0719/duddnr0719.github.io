> 데이터베이스 설계는 요구 사항 분석부터 개념적·논리적·물리적 설계와 구현까지 5단계를 거친다. E-R 모델로 개념적 구조를 표현한 개념적 스키마(E-R 다이어그램)를 작성하고, 릴레이션 변환 규칙을 적용해 DBMS에 적합한 논리적 스키마(릴레이션 스키마)로 변환한 뒤, 물리적 구조 결정 후 SQL 문으로 실제 데이터베이스를 구축한다.

### 데이터베이스 설계 단계와 요구 사항 분석
- **데이터베이스 설계**
  - 사용자 요구 사항을 고려하여 데이터베이스를 생성하는 과정
  - E-R 모델과 릴레이션 변환 규칙을 이용해 체계적으로 진행
- 설계 5단계 과정
| 단계 | 명칭 | 주요 목적 | 산출물 |
|---|---|---|---|
| 1단계 | 요구 사항 분석 | 사용자 요구 파악 및 데이터베이스 용도 결정 | 요구 사항 명세서 |
| 2단계 | 개념적 설계 | DBMS 독립적인 개념적 구조 표현 (개념적 모델링) | 개념적 스키마 (E-R 다이어그램) |
| 3단계 | 논리적 설계 | DBMS가 지원하는 논리적 데이터 모델로 변환 (논리적 모델링) | 논리적 스키마 (릴레이션 스키마, 테이블 명세서) |
| 4단계 | 물리적 설계 | 하드웨어·OS 환경을 고려한 내부 저장 구조 설계 | 물리적 구조 (인덱스, 클러스터링 등) |
| 5단계 | 구현 | DBMS에서 SQL 문을 실행하여 데이터베이스 생성 | 실제 데이터베이스 |
- **1단계 : 요구 사항 분석**
  - 목적 : 개발할 데이터베이스 용도 파악 및 업무 데이터와 처리 형태 분석
  - 업무 데이터 파악 및 필요한 처리 형태 분석
  - 주요 작업
    - 데이터베이스를 실제로 사용할 주요 사용자 범위 결정
    - 사용자가 조직에서 수행하는 업무 분석
    - 면담, 설문 조사, 업무 관련 문서 분석을 통해 요구 사항 수집
    - 수집된 분석 결과를 정리하여 요구 사항 명세서 작성
  - 예시 (한빛마트 데이터베이스 개발)
    - 인터넷으로 회원들에게 상품을 판매하는 시스템 구축 요구 수집

### 개념적 설계와 E-R 모델링
- **2단계 : 개념적 설계**
  - 목적 : DBMS에 독립적인 개념적 스키마 설계
  - 요구 사항 분석 결과물을 개념적 데이터 모델을 이용해 개념적 구조로 표현
  - 일반적으로 **E-R 모델**을 주로 이용
  - 결과물 : 개념적 스키마 (E-R 다이어그램)
  - 주요 작업 : 요구 사항 분석 결과를 기반으로 개체 추출 및 개체 간 관계 결정 후 E-R 다이어그램 표현
- 작업 과정 3단계
  - **STEP 1) 개체와 속성 추출**
    - 개체 정의 : 저장할 가치가 있는 중요 데이터를 가진 사람이나 사물
      - 사람 예시 : 병원 운영에 필요한 환자, 의사, 간호사 등
      - 사물 예시 : 병실, 수술실, 의료 장비 등
    - 개체 추출 방법
      - 요구 사항 문장에서 업무와 관련이 깊은 의미 있는 명사 탐색
      - 업무와 관련이 적고 광범위한 명사는 제외 (예: '한빛마트'는 시스템 범위이므로 개체 제외)
      - 의미가 같은 명사가 여러 개면 대표 명사 하나만 선택
      - 찾아낸 명사를 대표 명사(개체)와 부수적 요소(속성)로 분류
      - 각 개체의 속성 중 식별 가능한 키 속성 선별
    - 한빛마트 개체·속성 추출 결과
      - 회원 개체 속성 : 회원아이디(키) · 비밀번호 · 이름 · 나이 · 직업 · 등급 · 적립금
      - 상품 개체 속성 : 상품번호(키) · 상품명 · 재고량 · 단가
      - 제조업체 개체 속성 : 제조업체명(키) · 전화번호 · 위치 · 담당자
      - 게시글 개체 속성 : 글번호(키) · 글제목 · 글내용 · 작성일자
  - **STEP 2) 개체 간 관계 결정**
    - 관계 정의 : 개체 간의 의미 있는 연관성
    - 관계 추출 방법
      - 요구 사항 문장에서 개체 간의 연관성을 표현한 동사 탐색
      - 단순 종속이나 상태 표현(입력해야 한다, 부여된다, 식별한다)은 개체 간 관계가 아니므로 제외
      - 의미가 같은 동사가 여러 개면 대표 동사 하나만 선택
      - 찾아낸 관계에 대해 매핑 카디널리티와 참여 특성 결정
    - 매핑 카디널리티 : 일대일(1:1), 일대다(1:n), 다대다(n:m)
    - 참여 특성 : 필수적 참여 / 선택적 참여
    - 한빛마트 관계 추출 결과
      - 주문 관계 : 회원과 상품이 맺는 다대다(n:m) 관계, 양쪽 모두 선택적 참여, 관계 속성(주문번호 · 주문수량 · 배송지 · 주문일자)
      - 공급 관계 : 상품과 제조업체가 맺는 일대다(1:n) 관계 (제조업체 1 : 상품 n), 상품은 필수적 참여, 제조업체는 선택적 참여, 관계 속성(공급일자 · 공급량)
      - 작성 관계 : 회원과 게시글이 맺는 일대다(1:n) 관계 (회원 1 : 게시글 n), 회원은 선택적 참여, 게시글은 필수적 참여
  - **STEP 3) E-R 다이어그램 작성**
    - 도출된 개체, 속성, 관계를 바탕으로 E-R 다이어그램 완성
    - 실무적 표기법 : 관계를 표현할 때 까마귀발 표기법을 주로 사용
    - ER 다이어그램 도구 : SQL Power Architect, MySQL Work Bench, ERWin, Draw.io

### 논리적 설계와 릴레이션 변환 규칙
- **3단계 : 논리적 설계**
  - 목적 : DBMS에 적합한 논리적 스키마 설계
  - 개념적 스키마를 논리적 데이터 모델을 이용해 논리적 구조로 표현
  - 일반적으로 관계 데이터 모델을 주로 이용
  - 결과물 : 논리적 스키마 (릴레이션 스키마), 테이블 명세서
  - 변환 규칙을 순서대로 적용하되 해당되지 않는 규칙은 제외
- **E-R 다이어그램을 릴레이션 스키마로 변환하는 규칙 5가지**
  - **(규칙 1) 모든 개체는 릴레이션으로 변환**
    - 개체 이름 → 릴레이션 이름
    - 개체의 속성 → 릴레이션의 속성
    - 개체의 키 속성 → 릴레이션의 기본키
    - 복합 속성 변환 : 복합 속성을 구성하는 단순 속성만 릴레이션 속성으로 변환
      - 예 : 주소가 우편번호 · 기본주소 · 상세주소로 구성된 복합 속성이면 주소는 버리고 세 속성만 릴레이션에 포함
    - 변환 예 : 상품(상품번호, 상품명, 재고량, 단가)
  - **(규칙 2) 다대다(n:m) 관계는 릴레이션으로 변환**
    - 관계 이름 → 릴레이션 이름, 관계 속성 → 릴레이션의 속성
    - 변환 절차
      - 관계에 참여하는 개체들을 규칙 1에 따라 릴레이션으로 변환
      - 참여 개체 릴레이션들의 기본키를 관계 릴레이션에 포함시켜 외래키로 지정
      - 외래키들을 조합하여 관계 릴레이션의 기본키로 지정
      - 관계에 대한 속성이 있으면 관계 릴레이션에 포함
    - 변환 예 (학생-과목 수강 관계)
      - 학생(학번, 이름, 학년, 학과)
      - 과목(과목코드, 과목명, 학점수)
      - 수강(학번, 과목코드, 성적) → 학번과 과목코드가 외래키이자 복합 기본키
  - **(규칙 3) 일대다(1:n) 관계는 외래키로 표현**
    - 일대다 관계는 외래키로만 표현
    - 다(n)측 릴레이션에 1측 릴레이션의 기본키를 외래키로 포함
    - 관계의 속성들도 n측 개체 릴레이션에 포함
    - **(규칙 3-1) 일반적인 일대다 관계는 외래키로 표현**
      - 1측 릴레이션의 기본키를 n측 릴레이션에 외래키로 지정
      - 관계의 속성들도 n측 릴레이션에 포함
      - 필수적 참여인 경우 외래키에 `NOT NULL` 제약조건 추가
    - **(규칙 3-2) 약한 개체가 참여하는 일대다 관계는 외래키를 포함해서 기본키로 지정**
      - 약한 개체는 오너 개체에 따라 존재 여부가 결정되므로 오너 개체의 기본키를 이용해 식별
      - 1측 개체 릴레이션의 기본키를 n측 개체 릴레이션에 외래키로 지정
      - 관계의 속성들도 n측 개체 릴레이션에 포함
      - n측 개체 릴레이션은 외래키를 포함하여 기본키를 지정
  - **(규칙 4) 일대일(1:1) 관계는 외래키로 표현**
    - **(규칙 4-1) 일반적인 일대일 관계는 외래키를 서로 주고받음**
      - 두 릴레이션이 서로의 기본키를 외래키로 주고받도록 구성
    - **(규칙 4-2) 필수적으로 참여하는 개체 릴레이션만 외래키를 받음**
      - 관계에 필수적으로 참여하는 개체 릴레이션에 외래키 지정
      - 관계의 속성들도 필수적으로 참여하는 개체 릴레이션에 포함하여 널 값 방지
    - **(규칙 4-3) 모든 개체가 필수적으로 참여하면 릴레이션을 하나로 합침**
      - 관계에 참여하는 두 개체의 속성들을 관계 릴레이션에 모두 포함
      - 두 개체 릴레이션의 키 속성을 조합하여 관계 릴레이션의 기본키로 지정
  - **(규칙 5) 다중 값 속성은 릴레이션으로 변환**
    - 릴레이션은 각 속성이 원자값만을 가져야 한다는 특성을 만족해야 함
    - 다중 값 속성을 단일 릴레이션에 두면 불필요하게 중복 저장되는 문제가 발생
    - 다중 값 속성과 함께 개체 릴레이션의 기본키를 외래키로 가져와 새로운 릴레이션 생성
    - 새로운 릴레이션의 기본키는 다중 값 속성과 외래키를 조합하여 지정
- **한빛마트 변환 종합 예제 (단계별 변환 절차)**
  - STEP 1) 개체 변환 (규칙 1 적용)
    - 회원(회원아이디 · 비밀번호 · 이름 · 나이 · 직업 · 등급 · 적립금)
    - 상품(상품번호 · 상품명 · 재고량 · 단가)
    - 제조업체(제조업체명 · 전화번호 · 위치 · 담당자)
    - 게시글(글번호 · 글제목 · 글내용 · 작성일자)
  - STEP 2) 다대다 관계 변환 (규칙 2 적용)
    - 주문(회원아이디 · 상품번호 · 주문번호 · 주문수량 · 배송지 · 주문일자)
    - 회원아이디와 상품번호를 외래키이자 복합 기본키로 지정
  - STEP 3) 일대다 관계 변환 (규칙 3 적용)
    - 공급 관계(1:n) : 상품 릴레이션에 제조업체명을 외래키로 추가 (필수적 참여이므로 NOT NULL 추가)
    - 작성 관계(1:n) : 게시글 릴레이션에 회원아이디를 외래키로 추가 (필수적 참여이므로 NOT NULL 추가)

### 논리적 설계의 기타 고려 사항과 테이블 명세서
- **기타 고려 사항**
  - 모든 관계를 독립적인 릴레이션으로 변환 가능 (속성이 많은 관계는 유형에 상관없이 릴레이션 변환 검토 가능)
  - **순환 관계**
    - 개체가 자기 자신과 관계를 맺는 순환 관계도 기본 규칙을 그대로 적용
    - 1:n 순환 관계(부하-상사 관계)에서 1측인 상사의 식별 속성을 n측 릴레이션의 외래키로 포함
- **테이블 명세서 작성**
  - 릴레이션 스키마 변환 후 속성별 설계 정보를 기술한 문서
  - 데이터 타입 · 길이 · 널 값 허용 여부 · 기본값 · 제약조건 등을 세부 결정하여 문서화

### 물리적 설계와 구현
- **4단계 : 물리적 설계**
  - 목적 : 하드웨어나 운영체제의 특성을 고려하여 물리적 구조 설계
  - 주로 성능 향상을 위한 제반 사항을 검토
  - 주요 작업
    - 전체 데이터베이스의 크기 결정
    - 인덱스 생성
    - 클러스터링 생성 등
- **5단계 : 구현**
  - 목적 : SQL로 작성한 명령문을 DBMS에서 실행하여 데이터베이스를 실제로 생성
  - 테이블 명세서에 따라 SQL 문을 작성하여 실행

### 학사 데이터베이스 설계 종합 예제
- **학사 운영 규칙 (요구 사항 명세)**
  - 학과 : 학사 운영 기본 단위, 학과이름으로 식별, 학과사무실 보유
  - 교수 : 학과당 여러 명 근무, 교수번호로 식별, 교수이름 보유, 여러 학생 지도 및 여러 교과목 담당
  - 학생 : 한 학과에만 소속, 학번으로 식별, 이름 입력 필수, 여러 과목 수강
  - 과목 : 한 학과에서만 개설 · 과목이름으로 식별 · 과목구분('교양', '학초', '전공') 보유 · 한 과목당 한 명의 담당 교수 지정 (학과의 소속 교수만 담당 가능)
  - 수강 : 학생과 과목 간 다대다 관계, 과목당 여러 수강생 존재
- **처리 업무 (요구 사항 명세)**
  - 특정 학과에 속하는 교수 명단 출력
  - 특정 교수의 지도 학생 명단 출력
  - 특정 학과의 교과목 개설 및 담당 교수 입력
  - 특정 학과에서 개설한 과목 이름 출력
  - 학생이 수강할 수 있는 과목명과 담당 교수 이름 검색 및 수강 신청
- **개념적 설계 결과 (개체 및 관계)**
  - 학과 개체 : 학과이름(키) · 학과사무실
  - 교수 개체 : 교수번호(키) · 교수이름
  - 학생 개체 : 학번(키) · 학생이름
  - 과목 개체 : 과목이름(키) · 과목구분
  - 관계 구조
    - 근무 : 학과와 교수 간 1:n 관계
    - 지도 : 교수와 학생 간 1:n 관계
    - 소속 : 학과와 학생 간 1:n 관계
    - 개설 : 학과와 과목 간 1:n 관계
    - 수강 : 학생과 과목 간 n:m 관계
- **논리적 설계 결과 (릴레이션 스키마 변환)**
  - 학과(학과이름, 학과사무실)
  - 교수(교수번호, 교수이름, 학과이름)
  - 학생(학번, 학생이름, 학과이름, 교수번호)
  - 과목(과목이름, 과목구분, 학과이름, 교수번호)
  - 수강(학번, 과목이름, 성적)
- **테이블 생성 SQL**
```sql
CREATE TABLE 학과 (
    학과이름    CHAR(15),
    학과사무실  NUMBER(3) NOT NULL,
    CONSTRAINT 학과_PK PRIMARY KEY (학과이름)
);

CREATE TABLE 교수 (
    교수번호  NUMBER(3),
    교수이름  CHAR(10) NOT NULL,
    학과이름  CHAR(15) NOT NULL,
    CONSTRAINT 교수_PK PRIMARY KEY (교수번호),
    CONSTRAINT 교수_학과_FK FOREIGN KEY(학과이름) REFERENCES 학과(학과이름)
);

CREATE TABLE 학생 (
    학생번호  CHAR(10),
    학생이름  CHAR(10) NOT NULL,
    학과이름  CHAR(15) NOT NULL,
    교수번호  NUMBER(3) NOT NULL,
    CONSTRAINT 학생_PK PRIMARY KEY (학생번호),
    CONSTRAINT 학생_학과_FK FOREIGN KEY(학과이름) REFERENCES 학과(학과이름),
    CONSTRAINT 학생_교수_FK FOREIGN KEY(교수번호) REFERENCES 교수(교수번호)
);

CREATE TABLE 과목 (
    과목이름  CHAR(10),
    과목구분  CHAR(10),
    학과이름  CHAR(15) NOT NULL,
    교수번호  NUMBER(3) NOT NULL,
    CONSTRAINT 과목_PK PRIMARY KEY (과목이름),
    CONSTRAINT 과목_교수_FK FOREIGN KEY(교수번호) REFERENCES 교수(교수번호),
    CONSTRAINT 과목_CK CHECK (과목구분 IN ('교양', '학초', '전공'))
);

CREATE TABLE 수강 (
    학생번호  CHAR(10),
    과목이름  CHAR(15),
    성적      NUMBER(3),
    CONSTRAINT 수강_PK PRIMARY KEY (학생번호, 과목이름),
    CONSTRAINT 수강_학생_FK FOREIGN KEY(학생번호) REFERENCES 학생(학생번호),
    CONSTRAINT 수강_과목_FK FOREIGN KEY(과목이름) REFERENCES 과목(과목이름),
    CONSTRAINT 수강_CK CHECK (성적 <= 100)
);
```
- **테이블 구조 변경 SQL (ALTER TABLE)**
```sql
-- 과목 테이블 속성 길이 변경 및 외래키 제약조건 추가
ALTER TABLE 과목 MODIFY (과목이름 CHAR(15));
ALTER TABLE 과목 ADD CONSTRAINT 과목_학과_FK FOREIGN KEY(학과이름) REFERENCES 학과(학과이름);
```
