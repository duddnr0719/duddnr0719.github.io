> 파일 시스템은 계층(논리 FS → 파일 구성 모듈 → 기본 FS → I/O 제어)으로 이름을 블록으로 바꾼다. 블록 할당은 연속(빠르지만 단편화)·연결(FAT)·색인(UNIX inode), 빈 공간은 비트맵·리스트로 관리하고, 깨짐은 저널링·섀도 페이징으로 막는다.
### 파일 시스템 구조
- 파일 = 의미 단위로 묶은 논리 저장 단위, 파일 시스템 = 사용자 관점(파일 이름, 바이트 위치)과 디스크 관점(블록 번호) 사이의 **매핑**
- 디스크는 제자리 덮어쓰기와 임의 접근이 가능, 전송 단위는 보통 512B 섹터(블록)
- **FCB(파일 제어 블록)**: 파일별 메타데이터 (UNIX의 inode)
### 계층 구조
- 응용 프로그램 → **논리 파일 시스템** → **파일 구성 모듈** → **기본 파일 시스템** → **I/O 제어** → 장치
  - I/O 제어: 장치 드라이버, 인터럽트 핸들러. "실린더 72, 트랙 2, 섹터 10 읽기" 같은 하드웨어 명령
  - 기본 FS: "블록 123 읽기" 같은 일반 명령을 드라이버에 전달, 버퍼·캐시 관리
  - 파일 구성 모듈: 파일의 논리 블록 번호 → 물리 블록 번호 변환, 빈 공간 관리
  - 논리 FS: 메타데이터 관리. 파일 이름 → FCB/inode, 디렉터리 관리, 보호
- 계층화: 중복 코드↓, 모듈성↑ / 계층을 지나는 오버헤드로 성능↓
| 계열 | 대표 | 특징 |
|---|---|---|
| UNIX (Solaris, BSD) | UFS, FFS | 전통적 inode 구조 |
| Linux | ext2/3/4 | 저널링, 큰 파일 |
| Windows | FAT, FAT32, NTFS | FAT 단순 / NTFS 보안·암호화·ACL |
| 광매체 | ISO 9660 | 읽기 전용 표준 포맷 |
| 차세대 | ZFS, Btrfs | 스냅샷, 풀링, 무결성 검사 |
### 디스크·메모리 자료구조
- 디스크
  - **부트 제어 블록**: OS 부팅 정보, 보통 볼륨 첫 블록 (UFS 부트 블록, NTFS 파티션 부트 섹터)
  - **볼륨 제어 블록**: 블록 수, 블록 크기, 빈 블록 수와 포인터, 빈 FCB 수 등 (UFS **슈퍼블록**, NTFS **MFT**)
  - **디렉터리 구조**: 이름 → FCB
  - **FCB**: 권한, 날짜(생성·접근·수정), 소유자·그룹·ACL, 크기, 데이터 블록 포인터 (NTFS는 관계형 DB 같은 MFT의 행으로)
- 메모리
  - **마운트 테이블**: 마운트된 볼륨들
  - 디렉터리 캐시
  - **시스템 전체 열린 파일 테이블**: 열린 파일들의 FCB 사본, 열린 횟수
  - **프로세스별 열린 파일 테이블**: 시스템 테이블 항목을 가리키는 포인터 + 파일 오프셋 등
  - 버퍼
- `open(name)`: 디렉터리에서 이름 검색 → FCB를 시스템 테이블에 적재(이미 열려 있으면 카운트만 증가) → 프로세스 테이블에 항목 생성 → 그 인덱스(**파일 디스크립터**, Windows는 파일 핸들) 반환
- `read(fd)`: 프로세스 테이블 → 시스템 테이블의 FCB → 데이터 블록 위치 → 버퍼·캐시를 거쳐 사용자 메모리로 복사
### 디렉터리 구현
- **선형 리스트** (이름 + FCB 포인터): 구현은 쉽지만 검색이 O(n)
- **해시 테이블**: 평균 O(1). 충돌은 체인(오버플로 버킷 연결 리스트)으로
- **B+ 트리**: 큰 디렉터리에서도 빠르고 정렬 상태 유지 (NTFS, ext4 등)
### 할당 방법
- **연속 할당**: 파일을 연속된 블록에. 디렉터리에 (시작, 길이)만
  - 예: count(0, 2), f(6, 2), tr(14, 3), mail(19, 6), list(28, 4)
  - 순차·직접 접근 모두 빠름(헤드 이동 최소), 메타데이터 단순
  - **외부 단편화**, 파일 크기를 미리 알기 어렵고 늘리기 어려움
  - 매핑(블록 크기 B): LA / B = 몫 Q, 나머지 R → 물리 블록 = 시작 + Q, 블록 안 위치 = R
- **익스텐트 기반**: 연속 블록 묶음(익스텐트) 여러 개로 파일 구성 → 연속의 성능 + 확장 유연성, 단편화↓. 요즘 파일 시스템의 표준 (ext4, NTFS)
- **연결 할당**: 블록마다 다음 블록 포인터, 마지막은 nil(−1). 디렉터리에 (시작, 끝)
  - 예: jeep = 9 → 16 → 1 → 10 → 25 → −1
  - 외부 단편화 없음, 아무 빈 블록이나 사용, 확장 쉬움
  - 임의 접근 불가(i번째 블록까지 체인을 따라가야 함), 포인터 공간 낭비, 블록이 흩어져 탐색↑, 포인터 하나만 깨져도 뒤가 다 날아감
  - 매핑(512B 블록, 포인터 1B라 데이터 511B): LA / 511 = Q, R → 체인의 Q번째 블록, 블록 안 위치 R + 1
  - 개선: 블록을 **클러스터**로 묶어 포인터·탐색 줄이기
- **FAT**: 연결 포인터를 블록에서 빼서 볼륨 앞의 **테이블**에 모음 (블록 번호로 인덱싱)
  - 디렉터리 항목엔 첫 블록 번호만: 217 → FAT[217] = 618 → FAT[618] = 339 → FAT[339] = −1(EOF)
  - FAT을 메모리에 캐시하면 디스크를 안 읽고 체인을 따라갈 수 있어 임의 접근이 빨라짐
- **색인 할당**: 파일마다 **색인 블록** 하나에 데이터 블록 주소를 모두 (책의 목차)
  - 예: jeep의 색인 블록 19 = [9, 16, 1, 10, 25, −1, −1, −1]
  - 임의 접근 가능, 외부 단편화 없음, 확장 쉬움
  - 작은 파일도 색인 블록 하나를 통째로 씀(낭비), 큰 파일은 한 블록에 다 안 들어감
  - 매핑(512B 블록): LA / 512 = Q(색인 블록 안 위치), R(데이터 블록 안 위치)
  - 큰 파일 대책
    - 연결 색인: 색인 블록 마지막 항목이 다음 색인 블록을 가리킴
    - 다단계 색인: 바깥 색인 → 안쪽 색인 → 데이터. LA / (512 × 511) = Q₁(바깥 색인 위치), R₁ / 512 = Q₂(안쪽 색인 위치), R₂(데이터 안 위치)
- **UNIX UFS 결합 방식(inode)**: 직접 포인터 12개 + 단일 간접 + 이중 간접 + 삼중 간접
  - 블록 4KB, 포인터 4B(32비트) → 색인 블록 하나에 포인터 1,024개
  - 직접 12 × 4KB = 48KB / 단일 간접 1,024 × 4KB = 4MB / 이중 1,024² × 4KB = 4GB / 삼중 1,024³ × 4KB = 4TB
  - 작은 파일은 직접 포인터만으로 빠르게, 큰 파일은 간접 단계로
### 성능: I/O는 비싸다
- CPU는 엄청 빠르고 디스크 I/O는 엄청 느림 → **I/O 횟수를 줄이는 게 핵심**. I/O 한 번을 줄일 수 있다면 코드가 좀 늘어도 거의 항상 이득
  - HDD(250 IOPS): I/O 한 번 기다리는 동안 CPU 명령 약 6.3억 개
  - SSD(60,000 IOPS): 약 265만 개 — SSD도 격차가 큼
- 접근 패턴에 맞게: 순차 위주면 연속(익스텐트), 임의 위주면 색인. 블록 클러스터링으로 한 번에 여러 블록
### 빈 공간 관리
- **비트맵(비트 벡터)**: 블록마다 1비트 (슬라이드 기준 1 = 빈 블록, 0 = 사용 중)
  - 첫 빈 블록 = (워드당 비트 수) × (0인 워드 수) + (첫 1비트의 위치). 워드 안 첫 1비트를 찾는 CPU 명령이 있어 빠름
  - 1TB 디스크, 4KB 블록 → 블록 2²⁸개(약 2.7억) → 비트맵 2²⁸비트 = **32MB**. 4블록씩 클러스터로 묶으면 8MB
  - 연속된 빈 블록 찾기 쉬움, 대신 메모리에 올려두는 비용
- **연결 리스트(free list)**: 빈 블록끼리 연결 → 추가 공간이 거의 없지만 연속 공간 찾기·전체 순회가 비효율 (보통은 첫 블록만 필요해서 큰 문제 아님)
- **그룹화**: 첫 빈 블록에 다음 n − 1개 빈 블록 주소 + 다음 그룹 블록 주소 → 빈 블록 여러 개를 한 번에 얻음
- **카운팅**: 연속된 빈 블록이 많을 때 (시작 주소, 개수) 쌍으로
- **ZFS 공간 맵**: 디스크를 메타슬랩으로 나누고 메타슬랩마다 공간 맵. 변경은 카운팅 형식 로그로 기록 → 필요할 때 메모리의 균형 트리로 재구성 → 거대한 볼륨도 효율적으로
### 효율과 성능
- 효율을 좌우하는 것: 할당·디렉터리 알고리즘, 디렉터리 항목에 무엇을 담을지(예: 마지막 접근 시각을 기록하면 읽을 때마다 쓰기 발생), 메타데이터를 미리 할당할지, 데이터와 메타데이터를 가까이 둘지
- **버퍼 캐시**: 자주 쓰는 블록을 메모리에
- 쓰기 정책
  - **동기 쓰기**: 디스크에 다 써야 반환 (DB 등 신뢰성 중요)
  - **비동기 쓰기**: 버퍼에 쓰고 바로 반환 (대부분, 빠름)
- **선행 읽기(read-ahead)**: 순차 접근이면 다음 블록들을 미리 읽어둠. 순차로 읽은 블록은 곧 버림(free-behind)
- **페이지 캐시**: 가상 메모리 페이지 단위 캐시. 메모리 맵 I/O에 사용
  - 버퍼 캐시(read/write용)와 따로 두면 같은 데이터가 두 군데 → **이중 캐싱**
  - **통합 버퍼 캐시**: 일반 파일 I/O도 메모리 맵 I/O도 페이지 캐시 하나를 공유 (Linux 등)
### 무결성: 백업과 복구
- 물리적 보호: 잠금장치, UPS(정전 대비), 원격 백업 사이트(재해 대비)
- 주기적 백업
  - 물리 백업: 저장 장치를 비트 단위로 그대로 복제
  - 논리 백업: 디렉터리 구조와 파일을 따라가며 (보통 압축·아카이브 형식으로)
  - 증분 백업: 지난 백업 이후 바뀐 것만
### 로그 기반 복구
- **원자적 트랜잭션**: 묶인 연산을 전부 하거나 전혀 안 하거나
  - 데이터를 직접 고치는 대신 연산을 **로그**에 먼저 기록 → 다 끝나면 **커밋** 표시를 로그에 → 영구 저장소로
  - 커밋 전에 고장 나면 그 트랜잭션은 무시(롤백)
  - **체크포인트**: 확실히 반영된 마지막 지점. 복구 시 그 이후 로그만 재처리하면 됨
- **저널링(로그 구조) 파일 시스템**: 모든 메타데이터 변경을 로그(전용 영역이나 별도 장치)에 순차로 먼저 기록 → 커밋되면 실제 구조에 반영
  - 충돌 후엔 로그의 남은 트랜잭션만 다시 수행 → 디스크 전체를 검사(fsck)할 필요 없이 빠르게 복구, 메타데이터 일관성 보장
  - 순차 쓰기라 오히려 빠르기도 함 (ext3/4, NTFS)
- **섀도 페이징**: 원래 블록을 덮어쓰지 않고 **빈 블록에 새로** 씀
  - 커밋: 메타데이터 포인터를 새 블록으로 바꾸고 옛 블록 해제
  - 실패: 새 블록만 해제하면 원상태 (ZFS, WAFL의 copy-on-write)
