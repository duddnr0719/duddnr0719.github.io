> 하드웨어 명령을 감싼 고수준 도구들. mutex(열쇠 1개, 스핀락) → 세마포(열쇠 꾸러미, 대기 큐로 바쁜 대기 제거, 하지만 실수하기 쉬움) → 모니터(상호 배제를 언어가 보장, 조건 변수로 세밀한 대기).
### 동기화 도구 개요
- 임계구역 문제(CSP)를 푸는 고수준 소프트웨어 도구
  - Mutex lock: 가장 간단
  - Semaphore: 어디든 쓸 수 있고 간편·효율적
  - Monitor: mutex·세마포의 단점(실수하기 쉬움) 해소
  - Liveness: 프로세스가 실제로 진행되도록 보장하는 성질
### Mutex lock
- Peterson이나 원자 명령을 직접 쓰는 건 복잡 → OS가 감싸서 제공
- 열쇠를 가지고 들어가고 나오면 반납: `acquire()` → 임계구역 → `release()`
```c
acquire() {
    while (!available)
        ;                 /* busy wait */
    available = false;
}
release() {
    available = true;
}

do {
    acquire();
        /* critical section */
    release();
        /* remainder section */
} while (true);
```
- acquire/release 자체가 원자적이어야 함 → compare_and_swap으로 구현
- 한계: **바쁜 대기** — 들어가려는 프로세스가 무한 루프를 돌며 CPU 시간을 낭비 (특히 한 코어에 여러 프로세스가 대기할 때)
- 그래서 이런 mutex를 **스핀락(spinlock)** 이라 부름. 오히려 유용한 경우
  - 멀티코어에서 잠금을 짧게만 잡는다면, 한 코어가 돌며 기다리다 풀리자마자 바로 진입 가능
  - 기다리는 동안 컨텍스트 스위치(대기 큐로 갔다 오기)가 없어서 그 비용을 아낌
### 세마포 (Semaphore)
- 신호기. 정수 변수 S + 원자 연산 두 개만 허용 (Dijkstra가 P(proberen) / V(verhogen)로 명명)
  - `wait(S)`: S를 1 줄이고, 자원이 없으면 대기 (자원 사용 시작)
  - `signal(S)`: S를 1 늘리고, 기다리는 프로세스를 깨움 (자원 반납)
- mutex가 열쇠 1개라면 세마포는 **열쇠 꾸러미**
```c
wait(S) {
    while (S <= 0)
        ;    /* busy wait */
    S--;
}
signal(S) {
    S++;
}
```
- 종류
  - 이진 세마포(0/1): mutex와 같은 역할
  - 계수 세마포: 임의 범위. 같은 자원 여러 개 관리 (프린터 5대 → S = 5로 초기화, 쓸 때 wait, 끝나면 signal)
- **실행 순서 동기화**: P1의 S1이 P2의 S2보다 반드시 먼저 실행되게
  - `synch = 0`으로 초기화 → P1: `S1; signal(synch);` / P2: `wait(synch); S2;`
  - 동기화는 "들어가냐 마냐"뿐 아니라 "무엇이 먼저냐"의 문제이기도 함
```c
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>
sem_t synch;

void *p1(void *a) { printf("S1\n"); sem_post(&synch); return NULL; }   /* signal */
void *p2(void *a) { sem_wait(&synch); printf("S2\n"); return NULL; }   /* wait */

int main() {
    pthread_t a, b;
    sem_init(&synch, 0, 0);
    pthread_create(&b, 0, p2, 0);   /* P2를 먼저 만들어도 */
    pthread_create(&a, 0, p1, 0);
    pthread_join(a, 0); pthread_join(b, 0);
    sem_destroy(&synch);            /* 항상 S1 → S2 순서로 출력 */
}
```
- `gcc sem.c -o sem -pthread && ./sem`
### 바쁜 대기 없는 세마포
- wait/signal 자체도 임계구역이라 원자적으로 보호해야 함 (test_and_set이나 mutex로). 이 부분은 짧아서 바쁜 대기가 거의 없음
- 문제는 **앱의 임계구역이 길 때** 기다리는 프로세스가 CPU를 계속 낭비하는 것 → 대기 큐 사용
  - `block()`: 자기 자신을 세마포의 대기 큐에 넣고 일시 중단
  - `wakeup(P)`: 대기 큐에서 꺼내 준비 큐로
```c
typedef struct {
    int value;
    struct process *list;   /* 대기 큐 */
} semaphore;

wait(semaphore *S) {
    S->value--;
    if (S->value < 0) {
        /* 이 프로세스를 S->list에 추가 */
        sleep();            /* block */
    }
}

signal(semaphore *S) {
    S->value++;
    if (S->value <= 0) {
        /* S->list에서 프로세스 P를 꺼냄 */
        wakeup(P);
    }
}
```
- 이 구현에선 value가 음수가 될 수 있고, 그 절댓값 = 기다리는 프로세스 수
### 세마포의 위험
- **교착 상태**: P0은 `wait(S); wait(Q);`, P1은 `wait(Q); wait(S);` → P0은 S를 쥐고 Q를, P1은 Q를 쥐고 S를 기다림 → 둘 다 영원히 대기
- **기아**: 대기 큐에서 계속 밀려 실행 기회를 못 얻음 (예: LIFO로 깨우면)
- **우선순위 역전**: 낮은 우선순위 프로세스가 높은 우선순위가 필요한 잠금을 쥐고 있고, 그 사이 중간 우선순위가 낮은 쪽을 선점 → 높은 쪽이 사실상 중간보다 늦어짐
  - 해결: **우선순위 상속** — 잠금을 쥔 동안 낮은 쪽이 기다리는 높은 쪽의 우선순위를 물려받음
- 흔한 실수 (타이밍 에러)
  1. `signal(mutex); … wait(mutex);` 순서를 뒤집음 → 상호 배제 위반
  1. `wait(mutex); … wait(mutex);` 중복 → 교착
  1. wait나 signal을 빠뜨림 → 교착이나 상호 배제 위반
  - 실수 하나가 시스템 전체를 망가뜨리고 재현도 어려움 → 모니터 등장
### 모니터 (Monitor)
- 세마포 오용을 막는 고수준 동기화 추상화. 클래스 같은 **추상 데이터 타입**
  - 내부 데이터는 정의된 프로시저로만 접근
  - **한 번에 하나의 프로세스만 모니터 안에서 활성** → 상호 배제를 컴파일러가 보장
```c
monitor monitor_name {
    /* 공유 변수 선언 */
    function P1(...) { ... }
    function P2(...) { ... }
    ...
    initialization_code(...) { ... }
}
```
- 구성: 공유 데이터, 연산(프로시저), 초기화 코드, 들어가려는 프로세스가 줄 서는 진입 큐
### 조건 변수
- 상호 배제만으로는 "조건이 될 때까지 기다리기"를 표현 못 함 → `condition x, y;`
  - `x.wait()`: 호출한 프로세스를 x에서 일시 중단 (모니터는 다른 프로세스에게 열림)
  - `x.signal()`: x에서 기다리는 프로세스 하나를 깨움. 아무도 없으면 **아무 일도 안 함** (세마포 signal과 달리 값이 쌓이지 않음)
- 조건마다 대기 큐가 따로 있음
- P가 `x.signal()`로 Q를 깨우면 둘 다 모니터 안에 있을 수 없음 → 누가 먼저?
  - **Signal and Wait**: P가 기다리고 Q 먼저 실행, Q가 끝나면 P 재개
  - **Signal and Continue**: P가 계속 실행, P가 나간 뒤 Q 재개 (Mesa, Java, C# 등 대부분 이 방식)
### 세마포로 모니터 구현
- `mutex`(초기 1): 모니터 상호 배제. 각 프로시저는 `wait(mutex)`로 시작해 나갈 때 해제
- `next`(초기 0): signal을 보낸 뒤 양보하고 기다리는 프로세스용, `next_count`: 그 수
- 프로시저 F의 틀
```c
wait(mutex);
    /* F 본문 */
if (next_count > 0) signal(next);   /* 양보하고 기다리던 프로세스 먼저 */
else                signal(mutex);
```
- 조건 변수 x마다 `x_sem`(초기 0), `x_count`
```c
/* x.wait() */
x_count++;
if (next_count > 0) signal(next);   /* 기다리던 signaler에게 넘기거나 */
else                signal(mutex);  /* 모니터를 엶 */
wait(x_sem);
x_count--;

/* x.signal() */
if (x_count > 0) {
    next_count++;
    signal(x_sem);   /* 대기자 하나 깨우고 */
    wait(next);      /* 나는 양보 (Signal and Wait) */
    next_count--;
}
```
### 재개 순서와 자원 할당 모니터
- 여러 프로세스가 같은 조건에서 기다릴 때 단순 FCFS 대신 **조건부 대기** `x.wait(c)`: 우선순위 번호 c가 가장 작은 프로세스부터 깨움
```c
monitor ResourceAllocator {
    boolean busy;
    condition x;

    void acquire(int time) {      /* time = 사용 예정 시간 (짧을수록 먼저) */
        if (busy) x.wait(time);
        busy = TRUE;
    }
    void release() {
        busy = FALSE;
        x.signal();
    }
    initialization_code() {
        busy = FALSE;
    }
}
```
- 사용: `R.acquire(t); … 자원 사용 … R.release();`
- 상호 배제는 모니터가 보장하지만, acquire 없이 쓰거나 release를 빼먹는 실수까지 막아주진 않음
