도커

  • 애플리케이션을 컨테이너 기술을 사용하여 개발, 배포, 실행할 수 있게 해주는 오픈소스 플랫폼
  • 컨테이너에서 제일 잘 나가는 제품이라고 생각

가상머신(Virtual Machine) vs 컨테이너(Container)

### VM(Virtual Machine) ![](/images/99183a26a68691b9.png) - 구조 : 하드웨어 → 호스트 OS → 하이퍼바이저 → 게스트 OS → 앱 - 작동 원리 : 하이퍼바이저라는 소프트웨어가 물리적 하드웨어를 쪼개서 가상의 컴퓨터를 만든다. - 장점 - 강력한 보안 → 커널까지 완전히 분리되어 있어 하나의 VM이 해킹당해도 호스트나 다른 VM으로 퍼지기 어렵다. - 다양한 OS 사용 → 윈도우 서버 위에서 리눅스를 돌리는 등 다양하게 활용이 가능하다. - 단점 - 무겁고 느리며, 자원 낭비가 심하다 → 단순한 앱 하나를 돌리기 위해 OS 전체를 띄워야 한다. ### Container ![](/images/50041107aa54f8fa.png) - 구조 : 하드웨어 → 호스트 OS → 컨테이너 엔진(Docker) → 앱 - 작동 원리 : 컨테이너 엔진이 호스트 OS의 커널을 공유하면서, 각 애플리케이션에 필요한 파일 시스템과 자원만 격리한다. - 장점 - 효율성 → 100개의 앱을 띄울 때 VM은 100개의 OS가 필요하지만 컨테이너는 1개의 OS만 있으면 된다. - 배포 용이성 → ‘이미지’만 있으면 로컬, 서버, 클라우드 어디서든 똑같이 실행된다. - 단점 - OS 의존성 → 호스트 OS가 리눅스라면 컨테이너도 리눅스 기반이어야 한다. (단, 도커 데스크탑 등은 내무적으로 경량 VM을 사용하여 이를 극복하기도 한다.) - 보안 → 커널을 공유하기 때문에 커널 자체에 취약점이 생기면 모든 컨테이너가 위험해질 수 있다. ### 언제 무엇을 써야할까 ? - 가상머신 : 서로 다른 OS를 써야 하거나, 금융/보안 등 완벽한 격리가 최우선일 경우 - 컨테이너 : 마이크로서비스 아키텍쳐(MSA), 잦은 배포가 필요한 웹 서비스, 자원 효율성이 중요한 클라우드 환경 --- ## 이미지와 컨테이너 - 이미지(Image): 애플리케이션 코드, 라이브러리, 설정 파일 등을 모두 포함한 읽기 전용(Read-Only) 파일 - 컨테이너(Container): 이미지를 실행한 상태 → 하나의 이미지로 여러 개의 컨테이너를 만들 수 있다 ## 도커 파일(Dockerfile) - 이미지를 어떻게 만들지 정의한 설계도 예시: "우분투 리눅스를 설치하고, 파이썬 3.9를 설치한 뒤, 내 코드를 복사해서 실행해라"라는 내용을 텍스트 파일(Dockerfile)에 작성하면, 도커가 이를 읽어 이미지를 생성한다. ## 도커 허브(Docker hub) - Docker에서 운영하는 Docker 이미지 저장소 서비스. 미리 만들어진 Docker 이미지를 사용할 수 있다. ![](/images/5e53fc4da1b6baba.png) --- ## 자주 사용하는 명령어 {toggle="true"} - 이미지 목록 보기 sudo docker images - 이미지 검색 sudo docker search \[이미지 이름\] - 이미지 받기 sudo docker pull \[이미지 이름\] : \[버전\] #latest 입력 시 최신 버전 다운로드 - 이미지 삭제 sudo docker rmi \[이미지 id\] - 이미지 삭제(컨테이너 삭제 전 컨테이너까지 강제 삭제) sudo docker rmi -f \[이미지 id\] - 컨테이너 목록 보기 sudo docker ps - 컨테이너 목록 보기(전체) sudo docker -a ps - 컨테이너 실행 sudo docker run (\[옵션\]) \<이미지 식별자\> (\<명령어\>) (\<인자\>) #() 생략 가능 - 옵션
**-d** 백그라운드에서 실행, -d없이 실행한다면 Citl+C를 눌러 빠져나오는 순간 해당 컨테이너 종료
-it -i + -t , 컨테이너를 종료하지 않은 채 터미널의 입력을 계속해서 컨테이너로 전달. 컨테이너의 표준 입력과 로컬 컴퓨터의 키보드 입력을 연결
**--name** 컨테이너의 이름 부여. docker kill이나 docker rm 에서 이름으로 사용가능
-e docker 컨테이너의 환경변수 설정 (dockerfile의 ENV 설정도 덮어써짐)
-p 호스트와 컨테이너의 포트를 연결 (포워딩)
-v 호스트 컴퓨터의 파일 시스템의 특정 경로를 컨테이너의 파일 시스템의 특정 경로로 마운트
-w dockerfile의 WORKDIR 설정을 덮어쓰기 위해 사용
--rm 컨테이너를 일회성으로 실행할 때 주로 쓰임. 컨테이너가 종료될 때 컨테이너와 관련된 리소스까지 깨끗하게 제거
- 컨테이너 시작 sudo docker start \[컨테이너 id 또는 컨테이너 이름\] ### docker run 과 docker start 의 차이 - docker run : 이미지 기반으로 새로운 컨테이너를 생성하고 실행 - docker start : 중지된 컨테이너를 시작 - 참고) docker restart : 실행 중인 컨테이너를 중지하고 다시 시작 - 참고) docker create : 새로운 컨테이너 생성, 즉시 실행은 하지 않음
  • 컨테이너 재시작 sudo docker restart [컨테이너 id 또는 컨테이너 이름]
  • 컨테이너 접속 sudo docker attach [컨테이너 id 또는 컨테이너 이름]
  • 컨테이너 정지 sudo docker stop [컨테이너 Id 또는 컨테이너 이름]
  • 컨테이너 삭제 sudo docker rm [컨테이너 id 또는 컨테이너 이름]
  • 모든 컨테이너 삭제 sudo docker rm ‘docker ps -a -q’
  • sudo 없이 docker 명령어 쓰기 sudo usermod -aG docker [사용자명] newgrp docker
  • 컨테이너 안에서 명령어 실행 docker exec [옵션] [컨테이너명] [명령어] docker exec ws3 pwd

멀티호스트 도커 플랫폼

- 도커 여러 대를 띄워 서비스를 분산되게 운영시키는 것 - 만약 도커 하나가 다운 되어도 시스템이 정상 동작할 수 있다.

문제점

  • 수십, 수백 개의 서비스라면 일일이 관리하기 어렵다.
  • 한 시스템에 여러 노드로 나뉘어져 있고 실행을 위해서 각 노드를 하나하나 접속해서 배포, 실행을 해야한다.
  • 유지보수 측면에서도 똑같이 하나하나 진행해야 한다.

컨테이너 오케스트레이션(Container Orchestration)

  • 중앙 관리자 → 복잡한 컨테이너 환경을 효과적으로 관리하기 위한 도구

기능

  1. 상태 관리
  2. 배포 관리 : 유휴 리소스를 관리하여 신규 컨테이너 생성 시 알맞은 서버에 배치
  3. 배포 버전 관리 : 배포 / 롤백 시 중앙에서 자동으로 진행
  4. 서비스 등록 및 조회 : 새로운 서비스가 추가된 경우 자동으로 해당 서비스에 대한 설정이 추가
